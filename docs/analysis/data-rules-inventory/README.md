## 口径和没覆盖的部分

- **怎么得来的**：表清单和事件矩阵由脚本对代码做静态扫描生成（ORM 元数据、迁移脚本、AST）；规则清单逐条读了代码，关键结论（试算表口径、自动映射、数据集版本、发布门、报表取数、事件断点等）都对着源码核过。
- **没有连生产库**。本机没有运行数据库。表的实际存在情况、行数、索引，需要在生产库上用 `information_schema` 现查一次再定稿；`linkage_audit_log` 这类「代码在写、仓库里没建表」的表尤其要确认。
- **前端计算的规则只记了入口**。底稿表单里的计算、底稿披露表 → 附注的同步载荷（`components/workpaper/composables/` 下约 70 个 `build*SyncPayload` 函数）由前端算好再提交，本清单没有逐条展开。
- **标「待核」的条目**只读到入口，没有逐行读完实现（如现金流量表工作底稿、抵销分录录入端点、一致性门禁结果落表）。

## 下午过会建议的讲法（5 分钟）

1. **规模**：400 张表、15 个业务域；核心链路是「账表 → 数据集 → 科目映射 → 试算表 → 调整分录 → 报表 → 附注 / 底稿 / 合并」，靠标准科目编码和「项目 + 年度」串起来。
2. **规则分两类**：配置驱动的（报表公式 1191 行、推送规则 268 条、底稿科目映射 1025 条等）和写死在代码里的（试算表口径、自动映射算法、40 项门禁、按底稿编码过滤的循环联动）。
3. **触发时点**：用户操作（导入、改映射、批准调整、点发布、保存底稿）→ 事件（`TRIAL_BALANCE_UPDATED`、`REPORTS_UPDATED`、`WORKPAPER_SAVED` 等）→ 下游重算；另有 18 个后台任务和启动时的迁移、事件回放。
4. **已发现的问题**：10 个事件没人发导致对应联动永远不跑；自动模糊映射不经确认就进试算表；科目映射不分年度；报表缺科目按 0 计还算成功。这几条可以直接解释「某些数为什么不对」。
5. **对线上改动的约束**：发版即自动跑迁移改库；146 张表没有回退脚本；重启会回放事件写库。所以线上改动前必须全库 + 文件存储备份，回滚靠备份不靠回退脚本。

## 重新生成

抽取与生成脚本放在仓库根 `tmp_rule_inventory/`（已被 git 忽略，可能被清理）。用仓库 `.venv` 一条命令全部重跑（几分钟，日志在 `tmp_rule_inventory/out/<脚本>.log`）：

```powershell
.venv\Scripts\python.exe tmp_rule_inventory\run_all.py
```

依次执行：表结构（`extract_tables`）→ 事件（`extract_events`、`analyze_events`）→ 配置文件（`extract_configs`）→ 附录 A~C（`gen_docs`）→ 接口（`extract_routes`）→ 前端调用（`extract_frontend_calls`）→ 外部调用（`extract_outbound`）→ 附录 D / D2（`gen_api_docs`、`gen_api_gaps`）→ 05 与附录 E（`gen_diagrams`）→ 条数复核（`verify_counts`）→ 知识库链接复查（`vault_verify`）。只跑其中几步：`run_all.py gen_api_docs gen_api_gaps`。

正文 01~04 是人工整理的，代码变了要手工更新。若要长期维护，建议把脚本挪到 `backend/scripts/analyze/` 作为正式工具，免得再被清理。
