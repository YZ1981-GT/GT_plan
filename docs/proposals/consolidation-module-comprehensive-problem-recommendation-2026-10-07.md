## 1. 结论先行

用户要实现的不是若干独立按钮，而是一条有明确身份、版本、状态和来源的业务链：

```text
项目模块的企业代码
  -> 自动识别企业关系与合并角色
  -> 生成稳定企业树和右侧上下文
四表库数据
  -> 导入批次 / 科目映射 / 借贷方向
  -> 试算表未审数
  -> 底稿明细表、披露表、审定表候选值
调整分录审批 / 审定表发布
  -> 试算表审计调整和审定数
  -> 底稿披露表 / 报表审定数 / 调整分录大厅
合并调整、抵消分录审批
  -> 合并试算表调整与抵消列
  -> 合并报表差额表
  -> 合并附注差额表
  -> 合并数、来源穿透和恒等式校验
```

当前仓库已经有可复用部件。本轮实际运行后的判断是：**计算读路径在少量合成数据上局部一致，但界面上下文、复杂表结构和推送失败状态存在已复现缺陷，不能宣称全链路打通。**

- **测试结果：** 七批后端现有白名单测试完整结束，累计 341 passed；前端五个文件共 46 passed。测试范围、隔离方式、warning 和首次超时的未定位限制见第 20 章。
- **树和节点语义：** 只读 API 返回 13 个节点；已有 `consol/consol_elim/parent/branch_elim/hq/branch/subsidiary` 角色。读时派生树不等于用户确认式持久化建树，也不证明“三角色只生成一次”已实施。
- **合并计算：** 根节点试算、报表差额表、普通合并报表和 SQL 在应收 1870 + 50 = 1920、应付 320 + 50 = 370 上逐值一致；129 行五列恒等式未见不等。正号来自现有分录输入，不能据此确认抵消业务正确，也不能外推多币种/跨年/真实集团。
- **右侧联动：** Playwright 已复现左树选择甲合并户后，合并试算表仍显示根节点 1920；报表差额表仍请求根 `node_key`。普通报表正确切到甲节点 500/40，说明问题有明确组件边界，不是所有读 API 都错误。
- **披露表与附注：** “披露表是审定后的”保留为目标约束；本轮未验收全科目权威来源。国企 `五-5-2` API 三层表头在页面降为两层；上市子表头进入数据行。真实 Word 渲染函数对上市六列输入只生成两列，五个金额标记仅保留一个；HTML 仍保留全部六列。
- **推送状态：** 当前 `_refresh_notes` 源码已包含逐节点附注填入及提交；本轮故障矩阵只执行真实 `_push_one` 并注入下一层统计，未运行该刷新器内部。`partial/failed/skipped` 结构化返回仍被报告为附注步骤 `succeeded` 和 `all_ok=true`。警告/明细有留痕，但状态未正确传播；外层最终 run 状态未在分析阶段执行。
- **验收边界：** 真实 PG 的两个 consolidated 项目均为 2098 年合成项目。没有执行真实刷新、审批、发布、完整导出端点、全权限/锁/CAS、全科目或 6000 并发验收。

建议先处理已复现的上市 Word 丢列、节点上下文脱节和失败状态误报，再推进以下业务决策；具体范围和验收见第 23 章。

1. **先统一树身份和右侧上下文，再做全链路刷新。** 没有稳定 `node_key`，报表和附注的自动联动不可审计。
2. **合并户、差额户、单体母公司户是计算角色，不是三个重复企业。** 企业身份去重，角色分开表达。
3. **合并调整/抵消分录只保留一个业务写入源。** 其他试算表、报表差额表、附注差额表均由公式编排投影，不能各自录入。
4. **披露表作为审定后附注取数的权威交接层。** 附注刷新读取披露表及明确的合并差额来源，不从页面临时状态取数。
5. **公式管理负责可追踪编排，不替代所有业务聚合规则。** 四表到 TB 未审数的科目映射、叶子去重和借贷方向归一属于硬业务聚合；审定数写入仍必须经过显式发布门。
6. **附注先规范化结构，再扩展公式数量。** 先解决 `section_id/table_id/row_id/col_id`、多级表头和合并单元格，再批量配置国企/上市公式。

### 4.3 本轮不应直接宣称完成的事项

以下是完整业务场景的未验收范围；本轮的只读局部通过和已复现缺陷均不能替代这些验收：

- 三企业代码在项目创建后是否自动、幂等、无重复地生成正确持久化树。
- 三码全相等时是否真的给用户确认，并在确认后仅生成一个企业身份。
- 合并户、差额户、单体母公司户是否只在合并确认时一次生成，而非每次读取时派生。
- 关闭底稿页面后，四表激活是否仍能完成全部下游刷新。
- 隔离测试之外，真实 PG 草稿调整/抵消是否不进入 TB、报表和附注。
- 新批准分录是否实际派发并逐值写入合并 TB、报表差额表、附注差额表；本轮只读验证了存量 approved 分录到报表及穿透。
- 国企和上市全部复杂章节是否无丢列、错层、合并范围和公式错误；本轮 canary 已复现失败，未做完整导出端点。
- 公式失败、整节人工覆盖、锁定、权限、CAS 冲突和重试是否在真实服务中正确传播、保值和恢复。
- 6000 并发目标是否满足；当前没有压测证据。

## 5. 自动建树目标模型

### 5.1 建树的业务入口

正常合并项目的树应由项目模块中的三个企业代码自动构建：

- `company_code`：本企业代码。
- `parent_company_code`：直接上级企业代码。
- `ultimate_company_code`：最终控制方企业代码。

项目创建、企业基础信息保存或合并范围确认完成后，系统应触发统一建树服务。用户需要确认的是识别结果和合并范围，不应再次手工维护一份与项目企业代码脱离的父子树。

自动建树应完成以下步骤：

1. 保存原始代码值和规范化代码值。
2. 校验代码格式、不可见字符、大小写和空值。
3. 读取企业名称、统一社会信用代码或其他主数据展示信息。
4. 按代码建立企业身份节点和直接父子关系。
5. 标记当前合并范围、范围外上级和待确认关系。
6. 生成 `tree_version`，将节点和关系写入一次运行批次。
7. 校验重复、环、孤立节点、跨项目错挂和多重最终控制方。
8. 只有校验通过且用户明确确认合并范围后，才生成计算角色节点。

外部企业主数据不可用时可以进入“待确认”，但不得用企业名称相似度静默替代企业代码，也不得把缺失代码默认当成集团根节点。

### 5.2 三码归一化和去重规则

| 条件 | 企业身份处理 | 用户交互 |
|---|---|---|
| `company_code != parent_company_code` | 建立本企业和直接上级两个身份，按关系连接 | 正常展示关系 |
| `company_code == parent_company_code` | 只建立一个身份节点，不复制父节点 | 可提示“本企业即直接上级” |
| `company_code == ultimate_company_code`，但上级不同 | 本企业是最终控制方链条中的一个节点，按实际关系判断角色 | 展示最终控制方标记 |
| 三个代码全部相等 | 只建立一个企业身份节点 | 必须提示并要求确认“本企业即最终控制方总部/母公司” |
| 上级代码在当前范围外 | 保留关系，但上级标记范围外 | 不得参与当前合并金额计算 |
| 代码缺失或格式非法 | 不生成可计算关系 | 阻断或进入明确待补录状态 |
| 关系形成环 | 不生成当前有效树版本 | 阻断并指出环路径 |

企业身份去重键应使用规范化企业代码结合项目/合并范围上下文，不能使用名称。角色是身份的附加语义，不能因为“合并户”和“差额户”显示名称不同而复制同一企业。

### 5.3 一次生成三个计算角色

系统识别出合并户且用户确认合并范围后，只在这次确认动作中一次性生成以下三个计算角色：

| 展示名称建议 | 角色 | 数据语义 |
|---|---|---|
| `企业名称（合并户）` | `consol` | 直接子节点汇总后叠加本级批准调整/抵消的合并结果 |
| `企业名称（差额户）` | `consol_elim` | 合并环节调整和抵消的虚拟承载角色，不承载独立四表个别数据 |
| `企业名称（单体母公司户）` | `parent_hq` | 母公司/本部自身的单体数据，不含子公司汇总 |

**这是目标角色契约，不是当前枚举的完成声明。** 本轮读到的实际角色是 `consol/consol_elim/parent/branch_elim/hq/branch/subsidiary`。母公司带分公司时，当前 `:parent` 是汇总层，下面包含 `:branch_elim`、`:hq` 和 `:branch`，并非本部单体；真正本部个别数据在 `:hq`。因此不能把当前 `parent` 直接改名为 `parent_hq` 后认为满足用户要求，实施时须先保留语义并明确兼容映射。分公司汇总层属于单体母公司的内部聚合，不应被当成第二个法律企业或额外的用户确认式合并身份。

“三个角色只在确认后一次生成”仍是用户明确要求。现有读时树派生成功只证明当前树可读，不证明已保存角色确认、`tree_version` 或生成批次。

展示名称可以带中文角色标记，但公式、接口和数据库关联必须使用稳定 `node_key`。重复执行确认或刷新建树只更新同一角色节点的版本和状态，不得重复插入三个节点，也不得保留多个当前有效节点。

建议角色节点唯一约束至少覆盖：

```text
(project_id, tree_version/current_scope, entity_code, role)
```

历史树版本可以保留旧节点用于追溯，但当前有效版本只能有一套当前角色。

### 5.4 母公司有多个分公司的递归规则

母公司有很多分公司时，仍按三个企业代码构建身份树，不另造第二套逻辑：

- 母公司本部的 `parent_hq` 角色只表示本部单体数据。
- 分公司按 `parent_company_code` 连接到母公司或其直接上级。
- 母公司合并后的 `consol` 角色表示本部与直接/递归子公司的抵消后汇总。
- 差额户只承载本层合并调整和抵消，不把子公司个别数当成差额。
- 每一层先按直接子节点递归求合并值，再叠加本级调整和抵消；不能把所有后代一次性加到每个父节点。

因此，“母公司数据”必须在界面上明确是“单体母公司户”还是“母公司合并户”。合并模块中的母公司合并户不是集团本部单体数的别名。

## 6. 节点、金额和四维表语义

### 6.1 企业身份与计算角色分离

建议在目标设计中明确区分以下两个概念：

- **企业身份：** 回答“这是哪个法律实体”，由企业代码和项目范围确定。
- **计算角色：** 回答“该企业在当前合并计算中以什么口径出现”，例如合并户、差额户、单体母公司户、分公司个别户。

统一上下文至少应包含：

```json
{
  "project_id": "项目 UUID",
  "year": 2025,
  "period_end": "2025-12-31",
  "tree_version": "树版本 UUID",
  "node_key": "企业代码:角色",
  "entity_code": "本企业规范化代码",
  "role": "consol|consol_elim|parent_hq|entity",
  "template_type": "soe|listed",
  "report_scope": "individual|consolidated|elimination|adjustment",
  "view_mode": "individual|adjustment|elimination|consolidated",
  "source_version": "数据批次或审定版本",
  "formula_version": "公式配置版本"
}
```

所有右侧查询、写入、事件和公式运行都应携带或可推导同一上下文。只在 URL 中传 `project_id` 或在前端保留一个标题变量，不足以证明数据隔离。

### 6.2 四个概念与当前五列业务分解

“四维表”在本文是个别、合并调整、抵消、合并四个概念的简称，不要求删掉当前五列。当前 `consol_calc_basis.py`/报表试算读路径将抵消拆成权益与交易两类，实际恒等式为：

```text
individual   = 合并范围内各叶子实体 trial_balance.audited_amount 的单体审定汇总
adjustment   = 合并环节已批准调整（不含已计入 audited_amount 的单体调整）
elim_equity  = 已批准权益类合并抵消
elim_trade   = 已批准交易类合并抵消
consolidated = individual + adjustment + elim_equity + elim_trade
elimination  = elim_equity + elim_trade
```

`elim_equity` 与 `elim_trade` 都是业务金额分解，**不是额外校验量**。可以给用户汇总显示抵消数，但必须保留分类及穿透来源；校验差额、借贷平衡差和来源计数则另列，不参与金额累计。

关键口径是 `individual` 已经取审定数：单体 AJE/RJE/`wp_adjustment` 已进入 `audited_amount` 的部分，不得作为合并 `adjustment` 再加一次。若界面需要展示“单体未审 + 单体调整 = 单体审定”，应在单体来源穿透中拆解，而不是更改合并基数或制造第二个写入方。

递归计算可以采用“直接子节点 `consolidated` 之和 + 本层合并调整/抵消”。对外五列则按同一子树线性分解，叶子单体审定数只计一次，子层抵消也只计一次。不能在子节点合并结果上再次加子层调整/抵消，不能把差额户视为有独立个别数的子企业。

本轮实际对账：根应收 `1870 + 0 + 0 + 50 = 1920`，根应付 `320 + 0 + 0 + 50 = 370`；129 行五列恒等式 `mismatch=[]`。这是合成项目少量整数数据的读路径证据，不证明正负方向符合真实内部交易，也不覆盖复杂会计处理、汇率与舍入。

### 6.3 不同角色的显示口径

| 角色 | 个别数基数 | 合并调整 | 合并抵消 | 对外结果 |
|---|---|---|---|---|
| 单体企业/本部单体角色 | 本企业自身 `audited_amount`，已包含生效单体调整 | 通常为零；单体调整只在来源拆解中展示 | 通常为零或不适用 | 等于该单体审定基数，不再加单体调整 |
| 差额户 | 零或显示“不承载个别数” | 本层已批准合并调整 | 本层已批准合并抵消，可拆权益/交易 | 本层调整与抵消之和 |
| 合并户 | 子树叶子实体单体审定数汇总 | 子树及本层已批准合并调整 | 子树及本层已批准合并抵消 | 五列恒等式结果 |
| 当前 `:parent` 分公司汇总层 | 本部及分公司单体审定数汇总 | 本层/子层合并口径调整 | 包含 `:branch_elim` 来源 | 分公司汇总结果，不等于 `:hq` 本部数 |
| 范围外上级 | 不参与计算 | 不参与计算 | 不参与计算 | 仅关系展示 |

负数不能通过前端统一取绝对值修复。每次返回金额必须同时返回 `direction`、币种、期间、来源批次和口径。

## 7. 左树到右侧报表、附注和底稿的联动

### 7.1 联动矩阵

| 左树选择 | 右侧页面 | 必须显示 | 必须支持的穿透 |
|---|---|---|---|
| 合并户 | 合并报表 | 个别、调整、抵消、合并四度量 | 报表行到直接子节点和分录 |
| 差额户 | 合并差额表/调整抵消汇总 | 本级调整和抵消明细 | 单元格到 `elimination_entries` |
| 单体母公司户 | 单体报表/附注 | 母公司本部审定数据 | 到本部底稿、披露表和调整 |
| 分公司个别户 | 单体报表/附注/底稿 | 当前企业自身口径 | 到四表、TB 和披露行 |
| 任意节点 | 合并试算表/四维表 | 科目、方向、期间和口径 | 到工作表节点和来源批次 |
| 任意节点 | 合并附注 | 当前节点、章节、表和列 | 到披露表或差额分录 |
| 任意节点 | 公式管理 | 当前有效 binding 和最近运行 | 到上游、下游、版本和状态 |

### 7.2 已复现的联动缺陷与局部通过

本轮在真实页面、网络请求和只读 API 中复现如下差异：

| 视图 | 左树选择甲合并户后的实际结果 | 裁定 |
|---|---|---|
| 合并试算表 | 左树高亮甲，仍显示根应收 1920；没有随节点选择发起新业务请求 | 已复现上下文脱节，不是仅静态风险 |
| 普通合并报表 | 切到报表 Tab 后请求甲 `node_key`，应收 500、应付 40 | 该场景局部联动通过 |
| 报表差额表 | 点击甲后仍请求根 `node_key`，仍显示根应收 1920 | 已复现错误节点查询 |
| 合并附注 | 根 `:hq` 只读 API 返回人工 11/20，与 PG 一致 | 证明显式节点取数；不证明所有树角色切换、刷新和公式运行均正确 |

根因定位到 `ConsolidationIndex.vue` 的试算/差额表挂点未传父级选中节点；两子组件各维护 `nodeKey=ref(null)`，试算组件只 watch 项目/年度。`onConsolTreeSelect` 的合并角色分支与各 Tab 的状态更新也未统一。后端在显式传甲 `node_key` 时返回 500/40，因此本次节点错误不能归因于合并算式本身。

- `ConsolReportBreakdownView.vue` 和 `ConsolTrialBalanceTab.vue` 应消费父级统一节点上下文，不各自默认根节点。
- 只修标题或只增加一个 watch 不够，需同时清理旧响应、取消旧请求，并保证较晚返回的旧节点响应不能覆盖新节点。
- `ConsolWorksheetTabs.vue` 的项目/年度作用域仍须核验；没有逐项操作全部底稿，不能写成所有底稿都已证实错节点。

修复后应逐值核对：

1. 左树选中的 `node_key`。
2. 右侧 API 请求的 `node_key`、`project_id`、`year`。
3. 后端查询过滤的节点和项目条件。
4. 返回数据的 `node_key` 和角色。
5. 公式运行记录和来源穿透中的节点身份。

### 7.3 页面行为边界

- 点击树节点只改变查询上下文，不自动写业务数据。
- “刷新当前节点/章节”必须是显式命令，并生成运行批次。
- `onMounted`、watch、防抖保存和路由切换不能直接发布审定数或抵消批准。
- 取消请求不能被记成失败；已取消任务和真正失败必须分开。
- 右侧切换企业、查看来源和查看公式都要反向更新统一上下文。

## 8. 四表库到试算表、底稿和附注的目标链路

### 8.1 分层事件图

```text
L0 输入层
  原始四表文件/数据集保存
  -> 字段识别、批次、校验、映射版本
  -> DATASET_ACTIVATED / LEDGER_DATASET_ACTIVATED

L1 未审数层
  科目映射聚合 + 借贷方向归一 + 叶子去重
  -> TrialBalance.unadjusted_amount
  -> TRIAL_BALANCE_UPDATED(kind=unadjusted)

L2 底稿候选层
  TB 未审数 / 明细账 / 辅助余额
  -> 明细表候选值
  -> 披露表候选值
  -> 审定表候选值

L3 审定与调整层
  调整分录审批 / 审定表显式发布门
  -> TB 审计调整 / audited_amount
  -> TRIAL_BALANCE_UPDATED(kind=adjustment|audited)

L4 报表和附注层
  TB 审定版本
  -> 报表审定数
  -> 审定后披露表
  -> 普通附注/国企或上市章节

L5 合并层
  子企业个别数 + 已批准合并调整/抵消
  -> 合并工作表
  -> 合并试算表
  -> 合并报表和报表差额表
  -> 合并附注和附注差额表
```

### 8.2 四表到未审数的公式边界

用户希望“推送都通过公式管理”，但这里需要做一个关键边界裁决：四表到 TB 未审数的核心过程是标准科目映射聚合，不应被任意公式配置替代。

未审数聚合至少包含：

- 标准科目编码映射。
- 父子科目叶子去重。
- 借贷方向归一。
- 未映射叶子的继承或异常处理。
- 余额、辅助维度和序时账发生额的不同口径。
- 导入批次和来源版本。

这部分应由固定的领域服务执行，并将映射规则、输入批次、未匹配和歧义结果暴露到公式管理的运行视图中。公式管理可以触发、编排、记录和推送下游，但不能允许一个页面公式直接覆盖 `unadjusted_amount`，否则会重新引入父子双计、漏映射和符号错误。

### 8.3 未审数到明细表、披露表和审定表

1. 保存原始导入行、导入批次和校验结果，不直接覆盖上一批有效数据。
2. 激活批次后生成映射快照和 `source_version`。
3. 重算 TB 未审数，发布带项目、年度、科目范围和版本的事件。
4. 公式 binding 生成明细表、披露表和审定表候选值。
5. 候选值必须带 `source_version`、`binding_id`、`formula_version` 和目标稳定身份。
6. 人工录入或人工锁定的单元格不被自动刷新覆盖。
7. 审定表通过显式确认和发布动作后，才产生 `audited_source_version`。
8. 披露表和报表审定数只消费审定版本，不消费草稿候选值。

### 8.4 调整分录审批链

```text
调整分录草稿
  -> 权限、期间、项目、借贷平衡校验
  -> 项目组确认
  -> ADJUSTMENT_APPROVED
  -> 重算审计调整和审定数
  -> 发布 TRIAL_BALANCE_UPDATED(kind=adjustment|audited)
  -> 审定表 / 披露表 / 报表审定数
  -> 国企/上市附注对应科目
  -> 调整分录大厅状态和来源链
```

草稿不得污染 TB、报表或附注。更正、撤回和反向分录应产生新版本，不能物理覆盖已审批记录。所有下游结果均应能反查原始调整分录行、审批人、审批时间和公式运行批次。

### 8.5 调整大厅的角色

调整分录大厅应读取同一个调整分录事实源和运行状态，不另存一份无法反查的展示副本。大厅需要展示：

- 草稿、待确认、已批准、已撤回、已更正状态。
- 影响的项目、企业、节点、科目和期间。
- 调整前、调整净额、调整后金额。
- 下游 TB、审定表、披露表、报表和附注的运行状态。
- 失败、跳过、CAS 冲突和重试入口。

## 9. 合并调整抵消分录的单一来源与闭环

### 9.1 单一写入方

合并工作底稿中的“调整抵消分录汇总表”是用户录入和查看的业务入口，但建议将真正的结构化事实源统一为 `elimination_entries` 或等价的合并分录实体。汇总表是其投影，不应再让合并试算表、报表差额表和附注差额表各自录入同一笔业务。

每条合并分录至少包含：

- `project_id`、`year`、`tree_version`、`node_key`。
- 借方科目、贷方科目、金额、币种、期间和方向。
- `entry_kind=consol_adjustment|consol_elimination`。
- 关联企业、内部交易类型、来源底稿和来源行身份。
- `review_status`、创建人、批准人、批准时间和版本。
- 反向分录或更正分录关系。

### 9.2 草稿、批准和消费口径

所有合并计算路径必须统一消费状态，建议只消费 `review_status=approved` 的分录：

- 草稿：可以预览影响，但不进入合并金额。
- 待复核：可以进入差异列表，但不进入正式报表和附注。
- 已批准：进入合并 TB、报表差额表、附注差额表和合并数。
- 已撤回/更正：由新版本或反向分录抵消，不直接删除历史。

必须对照工作表树、合并试算表和报表服务逐一确认过滤条件，避免一条路径消费全部分录、另一条只消费批准分录。

### 9.3 推送目标

公式编排按一个 `run_id` 将批准分录推送到：

1. 合并试算表调整列和抵消列。
2. 合并报表差额表对应科目。
3. 合并附注差额表对应 `section_id/table_id/row_id/col_id`。
4. 合并户的 `consolidated` 结果。
5. 调整抵消分录大厅的影响状态。

每个目标写入记录 `source_entry_ids`，用户可以从附注单元格回到具体分录汇总表行。一个科目影响多个附注章节时，必须使用多个明确 binding，不能按中文标题模糊扩散。

### 9.4 合并恒等式和差额表边界

合并户的合并值应满足：

```text
individual_sum + approved_adjustment + approved_elimination
  = consolidated
```

其中 `individual_sum` 必须是单体审定基数；`approved_adjustment` 只指合并环节调整，不再加已计入单体 `audited_amount` 的 AJE/RJE/底稿调整。当前抵消分解为 `elim_equity + elim_trade`，与第 6.2 节五列口径一致。

**差额户/差额列与差额表整张视图要区分。** 差额户不承载子企业个别数，只显示本层调整/抵消；整张报表差额表可以同时列出差额户、母公司分公司汇总层及子企业结果，再合成总额。本轮根 `:consol_elim` 为 0，但 `:parent` 已含分公司抵消 +50，因此不能要求整张差额表所有列都只有分录净额，或把合法的 parent/子企业列认成重复计数。

差额表的负数方向应由借贷方向和分录方向得出，不能将“差额表一般为负数”硬编码为所有科目的显示规则。本轮已批准分录的正向 +50 只证明输入被正确反映，不证明该内部往来抵消在业务上正确。

## 10. 附注模块现状与目标

### 10.1 单体附注与合并附注的分层

单体与合并附注应共享结构协议，但暂不强行合并所有物理表：

- 单体附注以 `DisclosureNote`、`sub_table_data` 等结构承载项目/年度范围的数据。
- 合并附注以 `ConsolNoteData`、`ConsolNoteFormula` 等结构承载节点、差额列和合并口径。
- 二者共享 `section_id/table_id/row_id/col_id/row_type/col_type`、模板变体、报告范围和来源版本。
- 合并附注的节点维度、差额列和抵消来源不能简单套用单体 JSON。
- 单体披露表是合并附注的输入之一，但不是合并差额表的替代。

### 10.2 披露表作为审定后权威源

用户要求附注刷新和披露刷新自动从底稿披露表获取数据。建议将职责固定为：

```text
底稿明细表 / 审定表
  -> 显式发布后的披露表
  -> 普通附注对应科目

合并批准调整/抵消分录
  -> 合并附注差额表
  -> 合并附注合并列
```

披露表不应是“页面打开后临时拼出的 JSON”，至少应具备项目、年度、`wp_code`、章节/表格、行列稳定身份、数值状态、来源版本、审定版本和人工覆盖信息。

普通附注中涉及报表项目的表格优先读取审定后的披露表，不再让用户在附注中重复输入同一报表项目。合并附注同时读取子企业审定披露表和合并层差额来源，二者必须在界面上分列显示。

### 10.3 国企和上市变体

国企和上市模板可以在以下方面不同：

- 章节编号和章节标题。
- 专用披露章节。
- 表头层级和列顺序。
- 合计、小计和比较期列。
- 应收账款、关联方、金融工具等专项表的行列结构。

差异必须由 `template_type=soe|listed`、模板版本和明确 binding 表达。不能用“标题包含某几个中文词”决定写入哪一版，也不能让国企章节因标题相似误写到上市章节。

### 10.4 当前静态模板事实

当前仓库存在以下 Word 变体文件：

- `soe_standalone.docx`
- `soe_consolidated.docx`
- `listed_standalone.docx`
- `listed_consolidated.docx`

- `consol_note_sections_soe.json`：221→321 表，multi_header 4→37
- `consol_note_sections_listed.json`：282→432 表，multi_header 13→115

## 11. 附注模板真源和格式裁决

### 11.1 建议采用四层模板体系

```text
原始模板文件（Word/XLSX/Markdown）
  -> 结构事实抽取（标题、表、合并、公式、格式差异）
  -> 规范化模板（section/table/row/column identity）
  -> 项目运行实例（用户数据、来源、覆盖、版本、状态）
```

- 原始文件用于人工复核和版本归档。
- 事实抽取产物用于验证实际模板结构，不直接等同于运行时主源。
- 规范化模板供前端、HTML、Word、XLSX 和公式引擎共同使用。
- 运行实例保存某个项目、年度、节点和模板版本下的真实数据。

生成器必须幂等，模板没有变化时不得因为 `generated_at` 变化造成无意义 diff；应提供 `--check` 检查源文件漂移。

### 11.2 Word、Markdown、XLSX 的能力差异

| 格式 | 适合承载 | 必须显式处理的限制 |
|---|---|---|
| Word | 标题层级、段落、复杂表格、多级表头、合并单元格、版式 | 需要保留 `rowspan/colspan` 等结构，不能只抽文本 |
| Markdown | 简单表格、正文和轻量模板 | 原生无法完整表达复杂合并单元格、样式和多层表头 |
| XLSX | sheet、合并范围、公式、隐藏行列、格式和 A1 地址 | A1 地址是文件定位，不是跨版本业务身份；需保留公式和合并范围 |
| JSON | 运行时结构和稳定身份 | 不能只保存扁平 `headers/rows` 而丢失结构层级 |

Markdown 模板缺失需要按实际调用路径判断影响，不能仅凭解析器存在推断当前附注生成依赖它。当前解析器默认声明四个文件：`附注模版/国企报表附注.md`、`附注模版/国企报表附注_单体.md`、`附注模版/上市报表附注.md`、`附注模版/上市报表附注_单体.md`；这四个文件在当前工作区均未找到，`parse()` 在文件缺失时记录 warning 并返回空列表。另一方面，静态追踪显示 `DisclosureEngine.generate_notes()` 调用 `_load_templates()`，该生产主路径读取 `note_template_soe.json` / `note_template_listed.json`（项目自定义模板另走 JSON/service 路径）；`backend/app` 中未发现对 `NoteMDTemplateParser` 或其 `get_parser()` 的生产调用，`select_md_template()` 只返回模板类型和 scope。故本次确认的是**遗留解析器入口与声明源文件缺失的治理问题**，不是当前 JSON 主链已受影响或刷新已假成功的证据。若未来重新接入 Markdown，应将“文件缺失”返回为明确的未配置/阻断状态，不得与合法空模板混为一谈。

### 11.3 标题、序号和章节身份

将以下概念拆开：

- `section_id`：稳定机器身份，不因“第五章/第八章”显示变化而改变。
- `section_number`：展示编号，可按国企/上市和模板版本变化。
- `section_title`：展示标题，可随模板文字变化。
- `display_index`：当前表格中的展示序号。
- `row_id`：业务行身份，不随插入或排序变化。

标题行、注释行、空白分隔行、数据行、小计行和合计行必须由 `row_type` 区分。序号不能作为公式目标主键；标题不能作为唯一章节主键。

## 12. 多级表头、合并单元格和应收账款子表

### 12.1 多级表头规范

规范化模板必须保留：

- 表头层级路径。
- 叶子列稳定 `col_id`。
- 叶子列的显示文本、业务度量和期间。
- `rowspan`、`colspan` 或 `_column_groups` 关系。
- 本期、上期、期末、合计、差额、比例等列类型。
- 空列名、重复列名、多期末列和多个合计列的歧义状态。

“看起来能解析出第一行表头”不代表可安全写入。遇到叶子列无法唯一识别时，应标记 `skipped_ambiguous`，不得默认取第一列。

### 12.2 Word 与 HTML 的一致性问题

生产函数实际输出已经证明差异，不再仅是静态风险。本轮将 `五-5-2` 的二维行适配为 `label/cells`，每个金额叶子列注入不同非零标记，实际调用 `NoteWordExporter(None)._render_table()` 与 `_table_to_html()`；Word 保存到 BytesIO 后再读，统计真实表格列数和标记保留：

| 输入 | Word 实际输出 | HTML 实际输出 | 结论 |
|---|---|---|---|
| 国企：11 列、3 行 multi_header | 11 列、2 行表头，10/10 金额标记保留 | 11 列、1 行表头，10/10 标记保留 | 层级降级已复现；本标记场景未丢金额列 |
| 上市：6 列，无 multi_header/groups | 2 列、1 行表头，1/5 金额标记保留 | 6 列、1 行表头，5/5 标记保留 | Word 丢失 4 个金额叶子列已复现 |

这是生产渲染函数输入输出证据，**不是完整 Word/HTML 导出 API 验收**；不能据此断言用户当前某份完整报告已丢列，也不能因 HTML 列数保留就认定表头结构正确。已有导出定向回归通过未覆盖这个上市输入形态，不能用测试数量否认反例。

建议从共同表格契约解决：

1. 从规范化模板取得相同的表头树，并核对 headers、叶子列和每行 cells 的数目/身份。
2. HTML 按表头树生成多行 `<thead>` 和正确的 `rowspan/colspan`；不能表达时明确报结构差异。
3. Word 按同一表头树生成合并单元格；无分组表头也必须保留全部叶子列。
4. XLSX 导入/导出按相同叶子列 `col_id` 对账，而非按输出列字母猜业务列。
5. 用每叶子列不同标记、保存后再读的结果做回归；发生丢列应阻断正式输出，不静默压成两列。

### 12.3 应收账款专项

应收账款及其子表应作为优先 canary，因为它同时覆盖：

- 主表和多个子表。
- 账龄区间、期末/期初、坏账准备或减值列。
- 多级表头和合并单元格。
- 关联方或客户维度的可扩展行。
- 合计行与比例行。
- 国企和上市模板的列名、章节和展示差异。
- 可能来自披露表的报表项目值与来自明细表的辅助信息。

建议为主表和每个子表分别定义 `table_id`，为账龄区间和业务列定义 `col_id`，为客户/账龄行定义稳定 `row_id`。新增客户、排序客户或缺少某个账龄区间不能导致已有人工值错位。

### 12.4 空值、零值和合计行

- `0` 是有效计算结果，不得渲染为空。
- `NULL`、未绑定、无来源、被跳过和不适用必须有不同状态。
- 合计行必须明确子行范围，并能与下钻明细逐值对账。
- 小计和合计不能同时被自动公式和人工合计重复写入。
- 行被删除、隐藏或不适用时必须保留迁移和审计信息。

### 12.5 `五-5-2` 的 API、DOM 与源模板边界

两套合并章节只读 API 都返回 `section_id="五-5-2"`，但结构表示与实际 DOM 不同：

- 国企 `/api/consol-note-sections/soe/五-5-2` 返回 11 列、3 行 `multi_header`，期末/期初各 span 5。页面 `<thead>` 实际只有 2 行，显示期末/期初分组后直接到金额/比例/信用损失率等叶子列，缺少账面余额、坏账准备、账面价值中间层。列数保留不等于层级保留。
- 上市 `/api/consol-note-sections/listed/五-5-2` 返回 6 列、`multi_header=null`、无分组；“账面余额/坏账准备/账面价值”和“金额/比例”等子表头仍在 `rows` 前两行。重新选择章节后，页面只有一行表头（类别、期末余额及四个空头），上述两行进入 `<tbody>`。这是本轮已复现的结构缺陷，不再写成“可能错位”。
- `ConsolNoteTab.vue` 的 `parsedMultiHeader` 优先处理 `_column_groups`，该分支只构建 group→leaf 两层，没有同时保留国企 `multi_header` 的中间层；上市两种元数据都缺失时进入扁平分支。`_ensure_row_types()` 没有 `header` 类型，不能自动将 rows 中的子头升级成表头元数据。
- 切换国企到上市时只重新拉取上市目录，当前已选章节的表格仍保留国企旧配置及两层 DOM，直到重新选择章节。已复现界面变体不一致；本轮未编辑/保存，不能宣称已造成跨模板写库。
- `note_table_headers_source_facts.json` 是 2026-08-07 的源 Word 事实快照：国企对应表 11 列/2 行表头，上市 6 列/2 行表头，均有分组。它不是本轮重抽的文件事实。API 的国企三层、旧 Word 两层、页面两层须分别记录，不能把三者都叫“源模板三层”，也不能认定 6 列与 11 列本身就是错列。
- Word/HTML 生产函数实际降层和上市丢列见第 12.2 节；完整导出端点尚未运行。Word 零留白、HTML 零显示 `-` 是本轮看到的展示差异，需按业务展示规则裁决，不能直接归类成会计金额错误。

治理目标是同一 `table_id` 的源文件、规范化结构、API、DOM、Word 与 HTML 逐列/逐层对账。表头不能表示、空列语义不明确或 cells 超出输出列数时，应明确失败或差异提示，不允许静默截断。

## 13. 公式管理目标设计

### 13.1 Binding 最小契约

建议普通和合并公式在逻辑上统一为以下结构，物理表可以暂时不同：

```json
{
  "binding_id": "稳定 ID",
  "source_scope": "tb|tb_balance|tb_ledger|tb_aux_balance|workpaper|report|consol_elimination",
  "source_selector": {
    "project_id": "context.project_id",
    "node_key": "context.node_key",
    "wp_code": "可选",
    "account_codes": ["1122"],
    "dimension_filters": {},
    "period": "current"
  },
  "target_scope": "workpaper|trial_balance|report|note|consol_note",
  "target_identity": {
    "section_id": "稳定章节",
    "table_id": "应收账款主表",
    "row_id": "trade_receivable",
    "col_id": "current_period_consolidated"
  },
  "formula_kind": "sum|report|aging|formula|consolidation",
  "measure": "individual|adjustment|elimination|consolidated",
  "template_type": "soe|listed",
  "report_scope": "individual|consolidated|elimination|adjustment",
  "version": 1,
  "status": "active"
}
```

一个目标存在多个候选来源时必须进入歧义状态，不能依赖 registry 顺序、文件顺序或中文标题排序自动选一个。`priority` 只能表达有书面业务依据的覆盖关系。

### 13.2 触发器矩阵

| 触发事件 | 允许刷新 | 不允许直接做的事 |
|---|---|---|
| 四表批次激活 | TB 未审数及其候选下游 | 不得直接写审定数 |
| `TRIAL_BALANCE_UPDATED(unadjusted)` | 明细表、披露候选值、审定候选值 | 不得绕过发布门 |
| 调整分录批准 | 审计调整、审定候选、报表/披露下游 | 草稿不得进入正式输出 |
| 审定表显式发布 | `audited_amount`、披露表权威版本、报表审定数 | 不得由 watch/onMounted 触发 |
| 合并抵消批准 | 合并 TB、报表差额表、附注差额表和合并数 | 不得消费未批准分录 |
| 树版本变化 | 重新规划节点相关 binding | 旧树结果不得覆盖新树 |
| 模板/binding 发布 | 新版本计划和受影响目标 | 不得静默改变历史运行结果 |
| 用户显式刷新 | 当前节点/章节或全量运行 | 必须生成 run 记录 |

### 13.3 运行批次和幂等

每次刷新都应生成可查询的运行记录，至少包含：

- `run_id`、触发事件和触发用户/系统身份。
- 项目、年度、树版本、节点、模板和报告范围。
- 输入 `source_version`、`audited_source_version`、`formula_version`。
- 计划目标数、实际写入数、未变化数、人工跳过数、歧义数、缺失数和失败数。
- 开始/结束时间、重试次数和错误详情。
- 幂等键，例如 `project + year + node + event + source_version + formula_version`。

重复消费同一个事件不能重复插入、重复累计或重复生成角色节点。SSE 只负责通知进度，数据库运行记录才是审计和恢复事实。

### 13.4 人工覆盖、锁定和 CAS

自动刷新优先级建议为：

```text
冻结/锁定单元格
  > 整节人工覆盖
  > 单元格人工覆盖
  > 当前公式自动值
  > 默认值或空值
```

自动写入前必须比较读取到的版本、更新时间或数据版本。发现用户已在刷新期间修改时，返回 CAS 冲突，保留用户值，并记录自动结果未写入。人工覆盖至少保留自动值、人工值、操作者、时间、理由、来源版本和恢复自动动作。

### 13.5 失败和跳过结果

统一结果分类：

- `persisted`：按预期写入。
- `unchanged`：输入和目标版本相同。
- `skipped_manual`：人工覆盖或锁定保护。
- `skipped_ambiguous`：来源、目标、表头或公式有歧义。
- `skipped_missing`：缺少章节、表、行、列、节点或上游数据。
- `skipped_out_of_scope`：范围外节点或不适用模板。
- `failed_validation`：项目、期间、方向、模板或版本校验失败。
- `failed_write`：事务、约束或外部服务失败。

批量接口即使 HTTP 200，也必须返回上述结果摘要和可定位明细，不能用“成功调用”代替“成功写入”。

### 13.6 已复现的附注子状态传播缺陷

本轮实际调用生产 `_push_one`，使用隔离 SQLite 集团与真实 worksheet/trial/report 服务，仅在下一层 `_refresh_notes` 注入统计返回，不替换被测 `_push_one`。结果如下：

| `_refresh_notes.note_status` | refreshed / failed / skipped | 附注 step.status | `_push_one` 的 all_ok |
|---|---|---|---|
| persisted | 6 / 0 / 0 | succeeded | true |
| partial | 4 / 2 / 0 | succeeded | true |
| failed | 0 / 6 / 0 | succeeded | true |
| skipped | 0 / 0 / 6 | succeeded | true |
| 下一层抛 RuntimeError | 不适用 | failed | false |

根因是 `notes()` 将统计转成 detail 字符串，`_push_one` 只有抛异常时才改 failed/all_ok；函数正常返回时无条件 record succeeded，未消费结构化 `note_status`。failed 场景的 detail 含“刷新 0，失败 6，附注状态=failed”，warnings 也有失败信息，所以这是**状态误报而非无留痕**。

建议保留已有 run/step/SSE 机制，传递结构化结果并按有效目标汇总：部分写入和失败为 partial；应刷新目标全部失败为 failed；合法范围外跳过可独立 skipped，但缺树/缺模板/缺上下文不可与合法跳过混为成功。外层运行记录、SSE 和页面均应消费同一分类，不能仅把 warning 拼在成功消息后。

本轮没有执行外层最终 run 落库、SSE 或真实刷新端点，因此“最终 run 已观测为 succeeded”不是本轮结论；这是下一轮必须端点级补强的验收项。

- 真实 TestClient 端点调用，不能只测 service 或路由数量。
- Playwright 左树、刷新、公式管理、附注穿透和错误展示测试。

## 17. 迁移、兼容和回滚

### 17.1 双读和逐项目迁移

建议采用“新增字段、双读、对账、切换、清理”的顺序：

1. 新增稳定身份、树版本、模板变体、来源版本和运行批次字段，旧数据允许为空。
2. 从现有企业代码、父子项目和角色生成历史映射。
3. 输出重复节点、无法归属、旧根节点和标题/行号定位的数据清单。
4. 新读路径优先稳定身份；缺失身份只进入明确 legacy 分支并记录待迁移。
5. 双读期间逐值比较旧位置和新稳定身份，不一致不自动覆盖。
6. 按项目、年度、节点和模板变体分批回填。
7. 观察期结束后禁止新数据继续写入无身份路径。
8. 只有历史数据完成对账后，才归档旧字段和旧转换器。

### 17.2 回滚和补偿

- 树构建失败：不切换当前树版本，保留旧版本和错误报告。
- 单章节/单底稿失败：回滚当前 SAVEPOINT，保留其他独立成功结果。
- 关键合并步骤失败：停止后续步骤，记录已完成步骤和补偿任务。
- CAS 冲突：不覆盖用户值，要求重新规划并显示冲突来源。
- 错误公式：停用新 binding，保留旧版本结果和回滚指针。
- 错误业务分录：创建更正或反向版本，不物理删除已批准记录。
- 重试必须使用同一输入版本和新运行批次，不能重复累计金额。

## 18. 风险和外部依赖

### 18.1 主要风险

- **节点身份漂移：** 企业名称、中文标题、数组下标或旧根节点被误当作主键。
- **重复写入：** 审定发布、自动保存、公式推送和页面刷新存在多个写入方。
- **合并重复计量：** 把差额户作为普通子企业，或把后代直接加到每层父节点。

- **版本覆盖：** 旧树或旧批次异步任务晚到，覆盖新结果。

## 19. 端到端验收标准

### 19.1 场景 A：自动建树

准备一个最终控制方、一个母公司、两个子公司和一个多分公司母公司场景，覆盖：

- 本企业代码等于上级代码。
- 三个代码全部相等。
- 上级范围外。
- 递归子公司和母公司多个分支。
- 缺码和环关系。

逐值断言：

- 项目确认后产生当前有效树版本。
- 本企业等于上级时只有一个企业身份节点。
- 三码全相等时先提示确认，确认后企业同时具备最终控制方和总部/母公司语义。
- 合并确认恰好生成合并户、差额户、单体母公司户三个角色节点。
- 重复确认不增加节点、不重复累计金额。
- 每个节点的代码、角色、直接父节点和范围状态与输入一致。
- 缺码或成环阻断并给出中文原因。

### 19.2 场景 B：四表到未审数

导入包含普通科目、父子科目、备抵科目、借贷方向、辅助维度、序时账和未匹配行的数据。

逐值断言：

- 原始行、批次、映射版本和 `source_version` 可查。
- 未匹配、歧义和自动映射数量与独立 SQL 聚合一致。
- TB 未审数与独立聚合结果一致，方向没有重复转换。
- 重复激活同一批次不重复累计。
- 事件携带项目、年度、版本和受影响范围。
- 不打开底稿页面，下游候选刷新仍可继续。

### 19.3 场景 C：未审数到审定披露表

使用包含明细行、合计行、可扩展行和人工覆盖的底稿。

逐值断言：

- 明细表自动值和 TB 来源一致。
- 披露表行列稳定身份正确。
- 审定表发布前不会改变正式审定数。
- 人工覆盖保留人工值和被覆盖自动值。
- 关闭页面后触发刷新与打开页面触发结果一致。
- 披露表只有审定版本才可被附注正式取数。

### 19.4 场景 D：调整分录

创建草稿、批准、更正和撤回场景。

逐值断言：

- 草稿不进入 TB 审计调整、审定表、报表和附注。
- 批准只产生一次有效事件和一次对应下游版本。
- 调整前、调整净额、调整后逐科目一致。
- 调整大厅、披露表、报表和附注可反查同一分录版本。
- 更正/撤回保留历史，不直接覆盖原审批事实。

### 19.5 场景 E：合并抵消分录

录入一条内部往来抵消和一条内部投资/重复确认抵消，覆盖正负方向。

逐值断言：

- 草稿抵消不进入合并正式数。
- 合并 TB 调整/抵消列等于批准分录明细。
- 合并报表差额表不重复加子企业个别数。
- 合并附注差额表目标身份与 binding 完全一致。
- 每个受影响科目满足四度量恒等式。
- 从附注单元格可反查 `source_entry_ids`。
- 重复刷新不重复累计，锁定单元格不被覆盖。

### 19.6 场景 F：国企/上市附注

各选择以下章节：

- 一个应收账款主表及子表。
- 一个复杂多级表头。
- 一个合计/小计表。
- 一个合并差额表。
- 一个含人工覆盖的表。

逐值断言：

- `section_id` 稳定，展示编号和标题按变体正确。
- 叶子列、期间列、合计列、差额列无错位。
- 合并单元格结构保持，不能表达的部分进入差异报告。
- 序号变化不改变 `row_id`。
- 单体审定披露值和合并调整/抵消值分列展示。
- 国企和上市不因中文标题相似互写。
- 刷新和披露刷新读取同一审定披露源。

### 19.7 场景 G：失败、锁定和重试

制造缺章节、缺列、来源歧义、无树、无节点、人工锁定、CAS 冲突、单章节写入异常和旧模板版本。

逐值断言：

- 每个故障有明确 `skipped_*` 或 `failed_*` 状态。
- 批量接口返回各类数量和明细。
- 单章节失败不污染其他独立章节。
- 重试只处理失败项，不重复写入成功项。
- CAS 冲突不覆盖用户最新值。
- 公式版本停用后不再产生新写入。
- 失败页面不能保留旧值并显示“刷新成功”。

### 19.8 场景 H：Playwright

真实页面至少操作：

1. 打开/创建合并项目，确认自动树。
2. 点击合并户、差额户、单体母公司户。
3. 切换四维表企业、期间和度量。
4. 查看合并报表、报表差额表、合并附注差额表。
5. 打开公式管理查看来源、版本和运行结果。
6. 批准调整/抵消并观察下游运行。
7. 锁定附注单元格后刷新。
8. 触发失败项并重试。

浏览器断言必须结合网络请求和数据库逐值结果，不能只检查页面出现“成功”。
