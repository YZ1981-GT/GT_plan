# 合并模块“四表入库 → 试算表 → 底稿 → 披露表 → 审定表 → 报表/附注”公式与附注链路闭环建议

**日期：** 2026-10-07  
**文档类型：** 现状分析、目标架构与实施建议  
**适用范围：** 合并模块、单体/合并附注、公式管理、四表入库、试算表、底稿数据联动  
**本轮结论：** 本文只提出修复和收口方案，不直接修改业务代码。

## 一、执行摘要

当前平台已经具备多条可复用的链路：四表数据激活后可以进入自动匹配和试算表未审数重算；试算表更新可以通过 `TRIAL_BALANCE_UPDATED` 触发报表计算；报表更新可以进入 `DisclosureEngine`；调整分录审批和审定表发布也已经具备进入试算表更新事件的入口。普通附注有 `DisclosureNote.sub_table_data` 写入路径，合并附注有独立的 `ConsolNoteData`、`ConsolNoteFormula` 和按 `node_key` 刷新的路径。合并树也已经使用企业代码和角色生成 `node_key`。

这些能力还没有形成一条可证明、可恢复、可审计的统一闭环。当前主要问题不是缺少单个函数，而是上下文、稳定身份、公式来源、事件边界和失败可见性没有完全统一：同一企业在左侧树、合并工作表、合并报表、合并附注中的身份需要由同一个 `node_key` 传递；单体附注、合并附注和 Word/Markdown/XLSX 模板需要共享结构协议；四表入库、调整分录和抵消分录需要分别定义未审数、调整数、抵消数和合并数的来源；每次自动刷新需要记录公式版本、输入版本、写入结果、跳过原因和人工覆盖。

建议将目标拆成五个收口面：

1. 以项目模块中的本企业代码、上级企业代码、最终控制方企业代码自动构建幂等的企业树，并在树中区分企业身份节点和合并计算角色节点。
2. 以 `node_key + project_id + year + template_type + report_scope + source_version` 作为所有右侧数据视图和公式计算的统一上下文。
3. 将四表入库、试算表、底稿明细/披露/审定表、调整分录、抵消分录、合并报表和合并附注纳入有向的公式编排，而不是依赖页面打开或局部事件的隐式刷新。
4. 建立单体/合并、国企/上市、Word/Markdown/XLSX 之间的规范化附注模型，解决表格标题、序号、多级表头、合并单元格、合计行和可扩展行的身份漂移。
5. 用真实 PG、真实模板、真实浏览器操作和逐值断言验收整条链路，明确区分“静态代码存在”“配置已登记”“运行时实际命中”和“用户界面已经可用”。

## 三、目标链路与成功定义

### 3.1 用户目标翻译为可验收链路

目标链路应当同时支持单体项目和合并项目，但两者在数据语义上分开：

```text
四表库项目数据
  → 数据集激活 / 自动匹配
  → 试算表未审数
  → 底稿明细表、披露表、审定表
  → 项目组确认调整分录
  → 试算表审计调整列
  → 底稿审定表、披露表与报表审定数
  → 调整分录模块大厅
  → 国企/上市附注对应科目

合并项目：
子企业个别数 + 合并调整 + 合并抵消
  → 合并试算表
  → 合并报表与报表差额表
  → 合并附注各 node_key 的个别/调整/抵消/合并维度
```

验收时必须能够从一个用户动作追踪到所有受影响对象。例如用户在合并工作底稿的调整抵消分录汇总表输入一条科目为 `1122` 的抵消分录，系统应能说明：该分录属于哪个项目、哪个企业代码、哪个 `node_key`、哪个合并期间、哪个公式 binding、进入合并试算表哪一列、影响合并报表哪一行、影响附注哪个 `section_id/table_id/row_id/col_id`，以及哪些人工锁定单元格被跳过。

### 3.2 成功定义

“链路完全打通”必须同时满足以下条件：

- 数据从四表库进入试算表未审数后，不依赖用户打开某个底稿页面才能生成后续数据。
- 调整分录只有在明确的审批或发布门通过后才进入审计调整、审定数和下游报表/附注；草稿不能污染审定结果。
- 抵消分录只有在合并规则允许的状态下进入合并抵消列和合并附注差额表，并能追溯到原始分录。
- 同一 `node_key` 在树、合并工作表、报表、附注和右侧详情中含义一致，点击树节点后右侧上下文不会落回项目根节点或历史节点。
- 国企和上市模板的章节、列、行、表头及公式口径可以不同，但每一个差异都通过模板 variant 和 binding 表达，不能依赖中文标题模糊匹配。
- 人工录入、人工覆盖、锁定单元格、整节覆盖和冲突 skip 均可见、可解释、可恢复。
- 重复触发同一事件不会产生重复行、重复分录、重复节点或重复写入；失败重试不会覆盖人工修改。
- 真实 PG 和浏览器验收可以逐值证明输入、过程和输出，而不是只证明请求返回 200。

## 四、当前架构盘点

### 4.1 四表入库、自动匹配与试算表

当前可识别的主链路是：数据集激活或数据导入事件进入自动匹配，匹配结果由 `TrialBalanceService.recalc_unadjusted` 汇总到试算表未审数，随后发布 `TRIAL_BALANCE_UPDATED`。报表引擎监听该事件并更新报表，完成后发布 `REPORTS_UPDATED`，附注引擎再根据报表更新事件刷新可计算附注单元格。

这条链路的设计方向符合“数据只录入一次、下游自动刷新”的目标，但目前必须把以下事实分别核验，不能以事件处理器存在替代实际运行证明：

- `LEDGER_DATASET_ACTIVATED`、`DATA_IMPORTED` 是否覆盖所有四表导入入口，以及导入重试时是否幂等。
- `auto_match` 是否能对所有目标项目、期间、科目和借贷方向生成稳定映射。
- `recalc_unadjusted` 是否同时处理普通余额、辅助维度余额和序时账发生额，是否会把借贷方向或负号重复转换。
- `TRIAL_BALANCE_UPDATED` 的 payload 是否带有项目、年度、受影响科目和来源版本，能否让下游只刷新受影响范围。
- 报表引擎和附注引擎失败时，事件结果是否持久化，重试是否从同一输入版本重新开始。

建议把四表输入统一形成 `source_version`，并将数据集版本、导入批次、映射版本、期间和科目范围写入事件。后续公式运行都必须携带这个版本，避免用户看到“刷新成功”但实际读取的是上一批数据。

### 4.2 底稿、披露表和审定表

底稿链路至少包含明细表、披露表和审定表三类业务载体。披露表是附注取数的重要上游，用户要求附注刷新直接从审定后的披露表取数，因此披露表不能继续被当成仅供页面展示的临时 JSON。它应当具备项目、年度、`wp_code`、`section_id/table_id`、行列身份、数值状态、来源版本和审定状态。

当前 `wp_disclosure_sync_service.sync_from_workpaper()` 已提供从底稿向 `disclosure_notes` 的主要写入路径，并处理 `sub_table_data`、列信息、行范围、共享章节、人工覆盖、准则冲突、软删除复活和空载荷 no-op。该能力适合成为单体附注披露表的写入基础，但仍需补齐“哪一次审定变更触发了哪一行披露表刷新”的持久化证据。

当前普通 `formula_push.engine` 能根据规则把底稿内容推送到附注表，并在单底稿范围使用 SAVEPOINT 隔离失败；`note_writer.locate_table()` 只接受 `_source` 为 `workpaper` 或 `workpaper_html` 的表数据。这个限制有利于防止把不明来源的表写进附注，但也意味着 F1 顶层 `rows/_tables` 结构不能直接依赖普通公式推送完成，需要明确 F1 的专用适配器或将其登记为暂不自动推送的结构。

审定表发布必须保持显式发布门。审定数进入 `trial_balance` 的路径只能经过确认后的发布动作，不能在 `watch`、`onMounted`、防抖保存或页面刷新回调中直接写入。自动计算可以准备候选值、标记差异和发布待确认结果，但不得绕过用户确认改变审定数。

### 4.3 调整分录与抵消分录

调整分录和抵消分录必须在数据模型上区分：

- 调整分录属于项目或企业的审计调整，经过项目组确认后进入试算表审计调整列、审定表、披露表和报表审定数。
- 抵消分录属于合并层面的合并调整或抵消，通常挂在差额户/差额节点，用于把子企业之间的内部交易、投资关系、重复确认或其他合并调整从个别数据中消除。
- 合并附注差额表只承载合并层面的调整和抵消结果，不应把子企业个别数再次填入差额表。
- 合并数应满足 `individual_sum + adjustment + elimination = consolidated`；差额表的调整和抵消一般按能够使合并结果成立的方向填列，负数不是固定显示规则，最终应由借贷方向和分录方向计算得出。

当前 `consol_push_service._push_one()` 已按“合并工作表 → 合并试算表 → 合并报表 → 标记附注过期”的顺序编排，并将关键步骤结果写入 `ConsolPushRun`、通过 SSE 广播。该流程适合做合并层级的显式编排，但它与合并附注公式刷新 handler 之间仍需要统一运行批次和版本标识，避免报表已经更新而附注刷新读取旧的合并试算表。

### 4.4 普通附注和合并附注

普通附注使用 `DisclosureNote` 及其 `sub_table_data` 等结构，公式刷新由 `DisclosureEngine` 处理。该引擎可以读取附注中的 `_tables`，退回顶层 `rows`，对 `auto` 单元格进行 `sum`、`report`、`aging`、`formula` 等类别的计算，并跳过人工单元格。缺数据时存在 fail-open 或 skip 结果，必须把这些结果作为用户可见状态。

合并附注使用独立的 `ConsolNoteData` 与 `ConsolNoteFormula`。`consol_note_formula_service.plan_seed()` 会在报表行、取数列、合计行和科目口径唯一时生成种子公式；多级表头可以转换为 `_column_groups`；遇到空列名、多期末列、多个合计行或公式歧义时会 skip。`fill_by_formula()` 按节点写入合并附注数据，保留 `manual_cells`，`fill_note_sections()` 按章节使用嵌套事务隔离失败。

合并附注刷新 handler 主要响应 `TRIAL_BALANCE_UPDATED`，对 `WORKPAPER_SAVED` 则要求事件显式声明 `consol_note_refresh`、`consol_note_affected` 或 `affects_consol_note`。它会建立新的数据库会话，按节点和章节处理，能够对无树、无有效 `node_key`、无章节或关闭 V2 的场景返回结构化 skip。下一阶段应把这些 skip 与公式管理界面统一展示，不能只留在日志中。

## 五、自动构建合并树的目标规则

### 5.1 建树输入

正常合并项目建树的唯一业务入口应是项目模块中的三个企业代码：

- `company_code`：本企业代码。
- `parent_company_code`：上级企业代码。
- `ultimate_company_code`：最终控制方企业代码。

项目建立或合并范围确认后，系统应自动拉取和校验企业名称、统一社会信用代码、层级关系、项目期间和有效状态，生成树节点及其关系。用户不应再次手工编辑企业层级来“补建”正常树；用户确认的动作应是确认系统识别的本企业、最终控制方和合并范围，而不是重新维护一套与项目企业代码分离的树。

企业代码字段为空、代码自相矛盾、存在环、跨项目引用不一致或无法拉取企业主数据时，应生成阻断状态和可解释原因。不能把缺失代码静默当作项目根节点，更不能用企业名称相似度自动替代企业代码。

### 5.2 三码归一化规则

每个项目企业先经过代码归一化，再进入建树：

1. 代码必须按同一规范去除不可见字符、校验格式和大小写规则；保留原始输入以便审计，规范值用于比较。
2. `company_code == parent_company_code` 时，本企业与上级企业是同一业务实体，只创建一个企业身份节点，不创建重复的父节点。
3. `ultimate_company_code` 与 `company_code`、`parent_company_code` 均相同，系统应识别“本企业即最终控制方总部或母公司”场景，生成待确认提示；用户确认的是该业务判断，确认后将其标记为最终控制方和总部/母公司角色。
4. 只有当代码代表不同企业实体时才创建不同身份节点；角色可以多个，身份不能因为角色不同而复制成互相独立的企业。
5. 同一代码从多个项目分支出现时，以企业代码作为实体主键，以项目和合并范围作为关系上下文，不能依赖名称作为去重键。
6. 上级企业不在当前合并范围时，应保留外部上级关系并标记“范围外”，不能为了让树完整而虚构一个可计算的子节点。

### 5.3 一次生成的三个合并角色节点

当系统识别出合并户并且用户确认合并范围后，应一次生成三个具有明确名称和角色标识的计算节点：

- **合并户节点**：表示抵消后的合并结果，金额语义是直接子节点合计叠加本级合并调整/抵消后的审定数据。
- **差额户节点**：表示合并环节调整和抵消的虚拟承载节点；它不是一个有独立四表个别数据的企业，主要承载调整分录和抵消分录。
- **单体母公司户节点**：表示本部/母公司自身的单体数据来源；在母公司有多个分公司时，该节点的自身数据仍来自母公司本部，不能误写成集团合并汇总。

三个角色节点应共享企业代码身份或通过明确的 `entity_code + role` 组合区分。展示名称可使用“企业名称（合并户）”“企业名称（差额户）”“企业名称（单体母公司户）”，但名称只用于展示，公式和关联必须使用稳定的 `node_key`。

合并户、差额户和单体母公司户只能在确认合并场景后一次性生成，重复执行建树必须幂等。再次执行应更新关系、版本和校验结果，不得重复插入节点或把历史节点留成当前有效节点。

### 5.4 递归母公司和分公司规则

母公司拥有多个分公司时，应与集团合并使用同一套三码建树逻辑：每个项目企业先根据本企业代码、上级代码和最终控制方代码确定实体关系，再递归向上构建父节点，最后在当前合并范围内生成计算角色。

母公司节点在合并模块中的含义需要明确分层：

- “单体母公司户”是母公司本部的单体数据。
- “合并户”是母公司与直接或递归子公司的抵消后汇总数据。
- 右侧显示的“母公司数据”如果位于合并工作表上下文，默认应指合并户的母公司层级结果，不能把单体母公司户的数据混入合并户结果。

对每个父节点，直接子节点的合并值应先汇总，再叠加该父节点自身承载的本级调整/抵消结果。递归关系必须按照直接子节点逐层计算，禁止把所有后代直接汇总到每一层而造成重复计量。

## 六、树节点数据语义与统一上下文协议

### 6.1 节点角色与金额语义

建议把“企业身份”和“计算角色”拆开建模。企业身份回答“这是哪个企业”，计算角色回答“这个企业在当前合并计算中以什么口径出现”。至少保留以下字段：

| 字段 | 含义 | 约束 |
|---|---|---|
| `project_id` | 项目范围 | 所有查询和写入必须带项目隔离 |
| `entity_code` | 规范化企业代码 | 企业身份去重主键之一 |
| `company_code` | 项目输入的本企业代码 | 保留原值和规范值 |
| `parent_company_code` | 项目输入的直接上级代码 | 用于构建直接父子关系 |
| `ultimate_company_code` | 项目输入的最终控制方代码 | 用于识别最终控制方和范围 |
| `node_key` | 树内稳定节点身份 | 建议为 `{entity_code}:{role}`，在项目内唯一 |
| `role` | `consol`、`consol_elim`、`parent/hq`、`subsidiary/branch` 等 | 受枚举约束，不能使用自由文本 |
| `relation_to_parent` | `parent`、`subsidiary`、`branch` 等 | 表示关系，不替代角色 |
| `is_in_scope` | 是否属于当前合并范围 | 范围外节点只能作关系展示，不能参与金额计算 |
| `tree_version` | 本次建树版本 | 支持幂等更新和回滚 |
| `source_version` | 企业代码和数据来源版本 | 下游公式输入版本必须一致 |

合并角色的核心金额语义如下：

```text
individual_sum(node)
  = 本节点及其直接业务子节点的个别数据汇总口径

adjustment(node)
  = 本节点已批准的合并调整分录净额

elimination(node)
  = 本节点已批准的合并抵消分录净额

consolidated(node)
  = individual_sum(node) + adjustment(node) + elimination(node)
```

对于差额户，`individual_sum` 应为零或明确标记为不可用；差额户只贡献 `adjustment + elimination`。对于合并户，`individual_sum` 由直接下属节点的合并值和本部/母公司自身个别数据按既定关系计算，不能把差额户作为一个普通企业再次计入个别数。

合并试算表、合并报表和合并附注必须共用上述四度量语义。若某个显示表只显示其中两列，也必须能通过 provenance 找回另外两列及其计算规则。现有合并内核中若继续使用“五度量恒等式”校验，应在实现和界面文档中明确：用户可见的主表仍是四个业务度量，额外的一项只能表示差额/校验结果，不能作为第五种业务金额来源，也不能再参与合并求和。

### 6.2 统一右侧上下文

左侧树点击、合并报表切换、四维表或试算表切换、附注章节切换都应使用同一份上下文协议。建议所有查询、事件和前端路由携带：

```json
{
  "project_id": "项目 UUID",
  "year": 2025,
  "tree_version": "树版本 UUID",
  "node_key": "10000001:consol",
  "entity_code": "10000001",
  "role": "consol",
  "template_type": "soe",
  "report_scope": "consolidated",
  "period_end": "2025-12-31",
  "source_version": "数据批次或公式输入版本",
  "formula_version": "公式配置版本",
  "view_mode": "consolidated|individual|elimination|adjustment"
}
```

约束如下：

- `node_key` 是树内计算身份；企业代码、名称和展示标签不能单独替代它。
- `template_type` 只表示国企/上市等报告模板变体，不能用来推断节点身份。
- `report_scope` 区分 `individual`、`consolidated`、`elimination`、`adjustment` 等口径，不能把差额户和合并户混在同一金额列。
- `year` 与 `period_end` 必须从项目实际期间得到，不能从页面默认年份猜测。
- `tree_version` 和 `source_version` 用于防止树变化后旧公式结果覆盖新树。
- 所有写入都必须校验上下文与数据行的项目、年度、节点和模板变体一致。
- 页面切换只改变查询上下文，不触发隐式写入；刷新动作应产生显式命令和运行批次。

### 6.3 左树联动右侧数据

左树点击后，前端应将统一上下文传入右侧各模块：

- 合并报表：显示当前 `node_key` 的个别、调整、抵消、合并四度量，并支持穿透至直接子节点。
- 合并试算表或四维表：显示当前节点、科目、期间和口径，保留借贷方向、来源批次和差异。
- 合并附注：显示当前节点下对应 `section_id/table_id` 的数据；差额户只显示调整/抵消列，合并户显示合并结果。
- 底稿详情：显示与当前企业和项目范围相符的底稿，禁止因为 `wp_code` 相同而读取其他企业的行。
- 公式管理：只列出当前上下文有效的 binding，并显示上游地址、下游地址、公式版本和最近运行结果。

右侧任何表格的“切换企业”“查看来源”“查看公式”操作都应反向更新统一上下文，让用户从附注单元格返回左树时仍停留在原节点。

## 七、四表到报表和附注的公式编排方案

### 7.1 分层事件图

建议把数据流拆成五层，每层只消费已经确认状态的上游结果，并产生可重放的运行记录：

```text
L0 输入层
  DATA_IMPORTED / LEDGER_DATASET_ACTIVATED
  → dataset_version / mapping_version

L1 未审数层
  auto_match
  → TrialBalance.unadjusted_amount
  → TRIAL_BALANCE_UPDATED(kind=unadjusted)

L2 底稿层
  unadjusted TB
  → 明细表候选值
  → 披露表候选值
  → 审定表待发布值

L3 审定与调整层
  审定表 publish gate / ADJUSTMENT_APPROVED
  → TrialBalance.audit_adjustment / audited_amount
  → TRIAL_BALANCE_UPDATED(kind=adjustment|audited)

L4 报表与附注层
  TRIAL_BALANCE_UPDATED
  → ReportEngine
  → REPORTS_UPDATED
  → DisclosureEngine / note bindings

合并专用层
  子企业 individual data + approved adjustment/elimination
  → ConsolWorksheet
  → ConsolTrialBalance
  → ConsolReport
  → ConsolNoteData(node_key)
```

事件 payload 必须包含 `run_id`、`project_id`、`year`、`source_version`、`formula_version`、受影响 `node_key`/科目范围、触发原因和幂等键。事件消费者需要记录 `received/running/succeeded/partial/failed/skipped` 状态，避免只通过 SSE 告知前端而没有持久化事实。

### 7.2 四表入库到未审数

实施时应把四表导入划分为“原始数据保存”和“业务激活”两个动作：

1. 保存导入文件、批次、校验结果和原始行，不直接覆盖上一批有效数据。
2. 完成字段识别、科目映射、借贷方向和期间校验。
3. 用户或自动策略激活批次，发布 `LEDGER_DATASET_ACTIVATED`。
4. `auto_match` 生成映射快照，记录未匹配、歧义和手工覆盖。
5. `TrialBalanceService.recalc_unadjusted` 在同一 `source_version` 下重算未审数。
6. 发布 `TRIAL_BALANCE_UPDATED(kind=unadjusted)`，由下游编排继续刷新。

未匹配或歧义行不能被静默丢弃。系统可以按规则把它们排除出自动计算，但必须在导入批次和公式管理中显示数量、金额和原因。

### 7.3 未审数到明细表、披露表和审定表

底稿自动刷新应使用公式 binding，而不是组件内各自拼接取数：

- 明细表 binding 从 `tb`、`tb_balance`、`tb_ledger` 或 `tb_aux_balance` 读取，并明确 `direction`、科目范围和辅助维度。
- 披露表 binding 从明细表或试算表读取，带有 `wp_code`、`section_id/table_id`、行列身份和来源规则。
- 审定表先生成候选值，显示未审数、调整数和候选审定数；用户确认后才发布。
- 发布后的审定表应生成一个可追踪的 `audited_source_version`，下游披露表和报表引用该版本。
- 自动刷新只能写入标记为 `auto` 且未人工锁定的单元格；人工覆盖必须保留原始自动值、覆盖者、时间和理由。

### 7.4 调整分录审批到下游

调整分录流程建议固定为：

```text
草稿分录
  → 借贷平衡、期间、项目和权限校验
  → 项目组确认
  → ADJUSTMENT_APPROVED
  → 写入审计调整列
  → 重算审定数
  → TRIAL_BALANCE_UPDATED(kind=adjustment|audited)
  → 底稿审定表 / 披露表
  → 报表审定数 / 附注对应科目
  → 调整分录大厅状态更新
```

草稿状态和批准状态必须在服务层过滤，不能只由前端按钮隐藏。审批事件要有版本和幂等键；撤回或更正应生成反向或新版本分录，不能无审计地覆盖原分录。

“项目组确认”与“合并抵消批准”可以有不同权限和状态，但都必须清楚地进入下游：普通调整进入项目审计调整口径，合并抵消进入差额户和合并抵消口径。审定数、披露表和附注中的每个自动数都要能显示“调整前、调整净额、调整后”的来源。

### 7.5 抵消分录到合并试算表、报表差额表和附注差额表

合并工作底稿中的调整抵消分录汇总表应作为抵消明细的业务输入或唯一汇总来源，不能让合并试算表、报表差额表、附注差额表各自再录一遍。每条分录至少要带：

- `project_id`、`year`、`tree_version`、`node_key`。
- 借方科目、贷方科目、金额、币种、期间和借贷方向。
- `entry_kind=consol_adjustment|consol_elimination`。
- 内部交易或抵消类型、关联企业、来源底稿和来源行身份。
- `review_status`、创建人、批准人、批准时间、版本和反向分录关系。

公式管理以该来源表为输入，分别推送：

1. 合并试算表的调整列/抵消列，并保留借贷方向和五度量校验。
2. 合并报表差额表的对应科目明细；差额表只呈现合并层调整/抵消，不重复显示各企业个别数。
3. 合并附注差额表的对应科目行和列，按 `section_id/table_id/row_id/col_id` 定位。
4. 合并户的 consolidated 值，并由 `individual_sum + adjustment + elimination` 校验。

如果一个科目同时影响多个附注章节，必须由多个明确 binding 表达，而不能依赖中文标题或模糊科目名称自动扩散。每个下游写入结果都要记录 `source_entry_ids`，让用户能从附注差额单元格反查到调整抵消分录汇总表的具体行。

## 八、附注模型和模板标准化

### 8.1 单体与合并的分层关系

单体附注和合并附注应共享模板事实、表格结构和公式协议，但保留不同的运行时存储模型：

- 单体附注以 `DisclosureNote` 为业务容器，披露表和普通公式推送主要写入 `sub_table_data`。
- 合并附注以 `ConsolNoteData` 为业务容器，公式定义存于 `ConsolNoteFormula`，数据必须带 `node_key`。
- 二者共享 `section_id/table_id/row_id/col_id/row_type/col_type` 等结构身份，以及 `template_type/report_scope/source_version` 等上下文。
- 不建议当前阶段强制合并为一张数据库表；先用统一协议和转换层收敛，再根据真实运行数据评估物理合表。

单体披露表是合并附注取数的输入之一，但不能直接把单体章节 JSON 当作合并附注模板。合并附注有自己的差额列、节点维度、多级表头和合并角色。

### 8.2 模板事实源与运行时主源

`note_table_headers_source_facts.json` 可以作为从 DOCX 等文件提取出来的标题、表格、表头和合并单元格事实源，用于对账和生成规范化模板。当前静态分析尚未证明它是运行时渲染主源，因此实施时要显式选定：

- 原始模板文件：用于人工复核和版本归档。
- 事实抽取产物：记录 heading path、table、header、merge 等结构事实。
- 规范化模板：供运行时渲染、公式定位和导出使用。
- 运行时实例：保存项目实际生成的章节、表格和用户数据。

规范化生成器必须输出稳定、可复现的结果。模板内容不变时不应因为生成时间变化而产生无意义 diff；需要提供 `--check` 模式检测模板漂移。

### 8.3 稳定身份模型

每个可写入的附注单元格和每个公式 binding 都应使用以下身份组合：

| 身份 | 作用 |
|---|---|
| `section_id` | 规范化章节身份，与国企/上市 variant 关联 |
| `table_id` | 同一章节内具体表格身份 |
| `row_id` | 表内业务行身份，不依赖当前行号 |
| `col_id` | 表内业务列身份，不依赖 A/B/C 列字母 |
| `row_type` | `data/subtotal/total/header/footnote/placeholder` 等 |
| `node_key` | 合并树节点身份；单体场景可为空或使用单体上下文 |
| `template_type` | `soe/listed` 等模板变体 |
| `report_scope` | `individual/consolidated/elimination/adjustment` |
| `source` | `workpaper/workpaper_html/formula/report/tb/manual` 等来源 |
| `source_version` | 输入或公式运行版本 |

中文标题、序号、当前行位置和 Excel 列字母可以作为显示或导入辅助信息，不能作为复杂公式的唯一主键。模板迁移时若标题或序号改变，只要稳定身份不变，既有 binding 和人工覆盖就应可迁移；若业务行真正改变，必须生成显式迁移映射，不能静默按位置挪动数据。

### 8.4 标题行、序号和多级表头

标题和序号需要分离成三类信息：

1. `section_number`：章节展示编号，例如国企历史章节可能从“五、N”映射到当前“八、N”。
2. `section_title`：用户可见标题，可随模板变体和法规版本变化。
3. `section_id`：稳定机器身份，用于 binding、查询、导出和迁移。

表格内的序号也要区分 `display_index` 和 `row_id`。新增、删除或排序行不能改变已有业务行的身份。合计和小计必须通过 `row_type` 明确标识，并定义其覆盖范围、是否可被公式写入、是否允许人工覆盖。

多级表头不能把合并单元格展开成多个重复列名后再按位置写入。应保留：

- 表头层级路径。
- 叶子列的 `col_id`。
- 每个叶子列的显示文本、业务度量和期间。
- `rowspan`、`colspan` 或 `_column_groups` 的结构关系。
- 多期末列、合计列、差额列和比例列的明确类型。

`multi_header_to_column_groups()` 等现有能力可以作为转换基础，但必须加入重复叶子列、空列名、多个期末列和列组歧义的阻断结果；不能在无法确定列含义时取第一列继续写入。

### 8.5 Word、Markdown、XLSX 的差异处理

三种格式都应先转换到同一规范化结构，再由格式适配器导入或导出：

- Word 重点保留段落层级、标题、`rowspan/colspan`、表格合并单元格和文本格式。现有 `note_word_exporter.py` 已支持多级表头、标题层级和合计行，应作为导出适配器而不是唯一事实源。
- Markdown 适合表达简单表格和文本，但无法完整表达复杂合并单元格、样式和多层表头。导入时需要显式声明降级信息，不能把 Markdown 表头位置直接视为完整模板结构。
- XLSX 需要保留 sheet、合并范围、公式、隐藏列/行、格式和实际单元格地址，同时将地址映射到 `section_id/table_id/row_id/col_id`。Excel A1 地址只能是文件层定位，不能成为跨模板版本的业务身份。

导入器应输出“结构差异报告”，至少列出无法表达的合并单元格、重复标题、无稳定行身份、公式丢失、隐藏内容和未知 sheet。差异未经处理时，公式 binding 不得标记为可自动运行。

## 九、公式管理、四维表和数据溯源

### 9.1 四维表的显示口径

合并模块的“四维表”建议固定为四个相互独立、可加总校验的度量：

1. **个别数（individual）**：各企业自身或各直接子节点的个别数据汇总。
2. **调整数（adjustment）**：已批准的合并调整和审计调整中属于当前合并口径的部分。
3. **抵消数（elimination）**：已批准的内部交易、投资关系、重复确认等抵消分录净额。
4. **合并数（consolidated）**：前三项按统一方向口径计算后的结果。

显示层必须明确当前表是“分项四维表”还是“差额表”：

- 合并户可以显示四列，合并数应与后三列的恒等式一致。
- 差额户主要显示调整数和抵消数，个别数应为零或显示“差额户不承载个别数”。
- 单体母公司户显示本部个别数，不应把子公司汇总结果显示在该角色下。
- 报表差额表、附注差额表只显示调整/抵消来源；它们不是合并户完整四维表的替代。

每个数值单元格应同时显示或可展开查看：借贷方向、币种、期间、来源批次、公式版本、`source_entry_ids`、人工覆盖状态和最近刷新时间。负数显示规则必须由金额口径和借贷方向决定，不能通过统一取绝对值修复视觉问题。

### 9.2 四维表常见显示和修复点

建议按以下规则修复和验收四维表显示：

- **节点切换**：点击树中的企业后，四列必须按当前 `node_key` 重查；不得只更新标题而保留上一个节点的数据。
- **差额节点**：差额户不得出现重复的子企业个别数；合并户不得把差额户当普通子企业再次求和。
- **母公司节点**：母公司本部数据和母公司合并数据要通过角色或 `view_mode` 明确区分。
- **方向列**：科目值必须和 `direction` 一同返回，借贷方向不能由前端根据金额正负猜测。
- **零值和空值**：零应显示为可计算的零，空值应说明“未绑定、无数据、被跳过或不适用”，不能都渲染成空白。
- **合计和小计**：合计应明确子行范围，且与下钻明细逐值相等；不得通过页面端再次累加已经汇总的合并节点。
- **期间**：当前期、上期和期末列要由 `col_id` 区分，不能依赖列位置；多期末模板中必须阻断歧义。
- **人工覆盖**：覆盖值和自动值同时可见，刷新后锁定的覆盖值不被自动结果替换。
- **加载状态**：`running`、`partial`、`failed`、`skipped` 要有明确展示；不能在后端失败时保留旧值并显示“已刷新”。
- **精度**：金额计算使用统一精度和舍入策略，逐行明细与总计的差额应显示为舍入差异或阻断，不应无提示地调整最后一行。

### 9.3 Binding 最小结构

普通和合并公式 binding 建议收敛到统一的逻辑协议。物理存储可以不同，但至少包含：

```json
{
  "binding_id": "稳定 UUID 或规范化名称",
  "source_scope": "tb|tb_balance|tb_ledger|tb_aux_balance|workpaper|report|consol_elimination",
  "source_selector": {
    "project_id": "从上下文取得",
    "node_key": "当前节点或节点集合",
    "wp_code": "可选",
    "account_codes": ["1122"],
    "dimension_filters": {},
    "period": "current"
  },
  "target_scope": "workpaper|trial_balance|report|note|consol_note",
  "target_identity": {
    "section_id": "八、1",
    "table_id": "receivable",
    "row_id": "trade_receivable",
    "col_id": "current_period_consolidated"
  },
  "formula_kind": "sum|report|aging|formula|consolidation",
  "measure": "individual|adjustment|elimination|consolidated",
  "template_type": "soe|listed",
  "report_scope": "individual|consolidated|elimination|adjustment",
  "priority": 100,
  "version": 1,
  "status": "active"
}
```

binding 必须由唯一来源、唯一目标和明确版本组成。一个目标存在多个候选来源时，应进入歧义队列，不得依赖注册表顺序。`priority` 只能用于有明确业务规则的覆盖关系，不能成为隐藏冲突的通用排序字段。

### 9.4 触发器和刷新范围

触发器分为三类：

- **数据事件触发**：四表激活、试算表未审数更新、调整审批、抵消审批、审定表发布。
- **结构事件触发**：树版本变化、模板版本变化、binding 发布、项目报告类型变化。
- **显式用户触发**：公式管理中的“刷新当前节点”“刷新当前章节”“全量重算”“重试失败项”。

触发器不应因页面打开、组件挂载或普通防抖保存而直接发布审定数或合并抵消。`WORKPAPER_SAVED` 若影响合并附注，必须由保存方在事件中显式声明影响范围；系统可以根据声明做校验，但不能把所有保存事件都当作全量合并刷新。

建议每次触发生成 `FormulaRun` 或对应领域运行记录，包含：触发事件、上下文、输入版本、binding 版本、计划写入数、实际写入数、人工跳过数、结构跳过数、失败数、耗时和重试次数。SSE 只用于实时通知，数据库运行记录才是审计和恢复依据。

### 9.5 人工覆盖、锁定和 CAS

自动刷新遵循以下优先级：

```text
冻结/锁定单元格
  > 整节人工覆盖
  > 单元格人工覆盖
  > 当前公式自动值
  > 缺省或空值
```

实际写入前必须使用 CAS 或版本条件检查：读取时的 `data_version`、`updated_at` 或公式版本与写入条件不一致时，返回冲突并保留用户最新值。自动刷新不得覆盖用户在刷新期间录入的值。

人工覆盖记录至少应保存旧自动值、新值、操作者、时间、理由、来源版本、目标身份和是否允许后续恢复自动。解锁或恢复自动必须是显式动作，不能因为下一次事件到达就自动删除覆盖记录。

### 9.6 失败、跳过和可见性

当前代码中已经存在缺表、标题不匹配、公式歧义、无树、无节点和无章节等 skip 分支。建议统一成可查询的结果分类：

- `persisted`：已按预期写入。
- `unchanged`：输入未变化或目标已是相同版本。
- `skipped_manual`：人工覆盖或锁定保护。
- `skipped_ambiguous`：来源、目标、列或公式存在歧义。
- `skipped_missing`：缺少章节、表、行、列、节点或上游数据。
- `skipped_out_of_scope`：数据属于范围外节点或不适用变体。
- `failed_validation`：项目、期间、借贷方向、模板或版本校验失败。
- `failed_write`：事务、约束或外部服务写入失败。

前端公式管理应能按运行批次筛选这些结果，并提供“查看原因”“查看输入”“查看目标”“重试”入口。任何返回 200 的批量刷新接口都必须在响应中返回失败和跳过摘要，不能仅返回成功数量。

### 10.1 主要差距清单

### 10.2 阶段 0：基线和数据契约

目标是把现状变成可测量基线，先不改变业务语义。

1. 盘点所有四表导入入口、事件发布方、试算表重算方、底稿同步方、审定发布方、合并推送方和附注刷新方。
2. 为事件、binding、附注实例、树节点和合并分录定义统一字段契约，明确项目、年度、`node_key`、模板变体、范围和版本字段。
3. 编写只读盘点脚本，分别统计：binding 总数、已登记数、实际命中数、skip 数、stale 数、无目标数、歧义数和失败数。统计结果必须区分源码静态登记、数据库实际记录和运行时执行结果。
4. 对已有模板 JSON、DOCX 抽取事实和 XLSX 模板生成规范化身份草稿及差异报告。
5. 建立一组最小合成集团：一个最终控制方、一个母公司、两个子公司，覆盖“本企业=上级”“三码全相等”“母公司多分支”“范围外上级”和递归子公司。

阶段 0 的交付是契约和基线报告，不应以“所有函数已找到”作为完成标准。

### 10.3 阶段 1：自动建树和统一上下文

1. 将三码归一化、企业主数据读取、环检测、范围判断和树版本化集中到建树服务。
2. 实现企业身份节点去重，确保 `company_code == parent_company_code` 不产生重复节点。
3. 在合并确认动作中一次生成三种角色节点，并保证重复执行幂等。
4. 把 `node_key`、树版本、模板类型、报告范围和期间写入所有合并查询和写入。
5. 统一左树选择状态和右侧报表、四维表、附注、底稿详情、公式管理的请求上下文。
6. 对旧的没有 `node_key` 的历史合并附注数据建立明确兼容策略：可读的 legacy 行只作为迁移输入，不允许新写入继续落到无节点根行。

阶段 1 的出口条件是：同一企业关系重复建树不重复插入；树节点切换后所有右侧请求带同一 `node_key`；范围外节点不会进入金额汇总。

### 10.4 阶段 2：四表到底稿和审定表

1. 给数据集导入和激活增加可重放的 `source_version` 和映射快照。
2. 统一余额、明细账和辅助余额的取数口径，所有 TB 读取返回 `direction` 和来源批次。
3. 通过公式 binding 生成明细表、披露表和审定表候选值，写入行列稳定身份。
4. 审定表发布保持显式二次确认，发布后生成审定版本并发布 `TRIAL_BALANCE_UPDATED`。
5. 调整分录审批进入同一审定版本，草稿只能显示候选影响，不得写入审定数。
6. 让调整分录大厅读取同一分录和运行状态，不再由大厅另存一份无法反查的副本。

阶段 2 的出口条件是：关闭底稿页面后，激活一批四表数据仍能完成未审数、明细、披露和审定候选刷新；审批调整后逐值对账四表、TB、审定表和披露表。

### 10.5 阶段 3：抵消分录与合并四维表

1. 确定合并工作底稿调整抵消分录汇总表的唯一写入和审批来源。
2. 为每条分录建立科目、关联企业、`node_key`、分录类型和来源行身份。
3. 公式管理按四维度把批准分录推送到合并试算表、合并报表差额表和合并附注差额表。
4. 对每个节点和科目执行 `individual_sum + adjustment + elimination = consolidated` 校验。
5. 将合并推送的多个独立 commit 关联到一个 `run_id`，为失败步骤提供重试和补偿，而不是只留下后续步骤未执行的状态。
6. 让四维表显示来源、方向、期间、人工覆盖和分录明细，支持从差额表反查汇总表。

阶段 3 的出口条件是：一条批准抵消分录可以在同一运行批次内追踪到合并 TB、报表、附注和调整大厅，重复执行不重复累计，撤销或更正有完整历史。

### 10.6 阶段 4：附注模板和公式管理收口

1. 建立 `section_id/table_id/row_id/col_id/row_type` 规范化模板层，登记国企/上市 variant 和报告范围。
2. 将普通附注和合并附注的 binding 转换为统一逻辑协议，物理存储继续分开。
3. 对标题、序号、合计、小计、可扩展行、差额列和多级表头建立迁移映射。
4. 为 F1 顶层 `rows/_tables` 结构明确专用适配器或登记为显式不自动推送的范围，避免普通 `note_writer` 的表定位规则误判为成功。
5. 将普通附注从披露表获取的数据与合并附注差额表的调整/抵消数据分开展示，避免同一表格同时混入单体审定数和合并差额数。
6. 在公式管理中展示 binding、版本、触发来源、执行结果、skip 原因、stale 状态和人工覆盖。

阶段 4 的出口条件是：国企和上市各选至少一个复杂多级表头章节、一个合计/小计章节、一个差额表章节和一个人工覆盖章节逐值通过。

### 10.7 阶段 5：全链路验收和性能收口

1. 在真实 PG 上执行最小集团、真实单体/合并模板和真实权限。
2. 使用 Playwright 从项目创建、自动建树、选择节点、导入四表、刷新、审批调整、批准抵消、查看报表/附注、打开公式管理和重试失败项完整走通。
3. 对每个关键写入执行数据库逐值断言，不把 UI 文字或 HTTP 200 作为唯一证据。
4. 执行失败注入、并发刷新、重复事件和人工锁定场景。
5. 在目标数据规模下进行 PG、Redis、队列、SSE 和前端渲染性能测试，再评估 6000 并发目标。

## 十一、迁移策略、权限、性能和回滚

### 11.1 迁移和兼容

建议采用“新增字段、双读、校验、切换、清理”的迁移顺序：

1. 新增树版本、`node_key`、模板变体、报告范围、来源版本、公式版本和运行批次字段，允许旧行为空以便迁移。
2. 从现有企业代码和角色生成历史节点映射，输出重复、冲突、无法归属和 legacy 根节点清单。
3. 新读路径优先读取稳定身份；缺失身份时进入明确 legacy 分支并记录待迁移，不在新写入中继续扩大 legacy 数据。
4. 双写期间比较旧位置身份和新稳定身份的结果，逐值一致后切换读取。
5. 按项目和年度分批回填附注、合并分录和公式 binding，失败批次可以单独重跑。
6. 观察期结束后禁止无身份新数据写入，再删除或归档不再使用的旧字段和旧路径。

运行时迁移继续遵守仓库的 `V*.sql`/`R*.sql` 配对、数字版本唯一和 `IF NOT EXISTS` 约束。涉及 PostgreSQL 专有类型、索引、约束或 JSONB 的迁移必须提供 SQLite 测试替代或明确仅 PG 执行路径。

### 11.2 权限和隔离

所有按项目、企业、节点或底稿读取的端点都必须做数据层过滤。路径中的 `project_id`、`node_key` 或 `wp_id` 不能替代实际查询条件。建议至少区分：

- 项目只读：查看树、TB、报表、附注和公式运行结果。
- 底稿编辑：修改明细表、披露表和审定表候选值。
- 调整分录录入：创建草稿调整分录。
- 项目组确认：批准调整分录和发布审定数。
- 合并抵消编辑/审批：维护和批准合并调整抵消。
- 公式管理员：发布 binding、模板版本和刷新策略。
- 质量复核/审计留痕：查看全部来源、覆盖、冲突、失败和版本历史。

前端应根据权限隐藏不可执行操作，后端仍需在端点、服务和写入层重复校验。自动刷新以执行者身份记录；系统事件不能使用固定用户 ID 伪造操作者。

### 11.3 性能和并发

合并树、TB、报表和附注刷新不能每次都全项目全节点全章节重算。建议按事件 payload 计算受影响集合：项目、期间、节点、科目、章节和 binding。常用查询需要围绕 `project_id/year/node_key/section_id/source_version` 设计索引，并观察锁等待和长事务。

大批量刷新使用后台任务或分批处理，前端通过 SSE 订阅运行进度；单章节、单节点失败不能回滚已经成功的独立章节，但必须能从运行批次中重试。数据库写入使用短事务和嵌套保存点，避免把整项目刷新包进一个长事务。

6000 并发只是目标，不是本轮静态分析的已验证结论。真正评估前需要准备真实规模的企业、科目、附注章节、公式 binding 和并发用户数据，并分别测量 PG、Redis、事件队列、SSE 连接、后端 CPU/内存、前端渲染和锁竞争。

### 11.4 回滚和补偿

每个公式运行、树构建、合并推送和模板迁移都要有 `run_id` 与输入版本。失败处理按层执行：

- 结构校验失败：不写业务数据，只记录失败和修复建议。
- 单底稿或单章节失败：回滚当前 SAVEPOINT，保留其他成功结果。
- 关键合并步骤失败：停止后续步骤，保留已完成步骤的版本和补偿任务。
- 发现版本冲突：不覆盖新数据，生成 CAS 冲突并要求重新规划。
- 发现错误公式：停用 binding 新运行，保留旧版本结果和回滚指针。
- 需要撤销业务分录：创建反向或修订版本，禁止直接物理删除已审批分录。

回滚验收必须证明：人工值、锁定状态、审计日志和旧版本结果仍可读取；重试不会重复累加金额；旧版本可以作为对照重新计算。

## 十二、端到端验收场景与逐值断言

以下验收必须在真实 PG、真实后端服务和真实前端页面上执行。单元测试或内存 SQLite 可以作为局部防回归，但不能替代这些场景。

### 场景 A：自动建树和三码去重

准备一个最终控制方、一个母公司和两个子公司，分别覆盖：本企业代码等于上级代码、三个代码全部相等、母公司有多个分支、范围外上级和递归孙公司。

逐值断言：

- 项目确认后自动生成当前有效树版本。
- `company_code == parent_company_code` 只存在一个企业身份节点。
- 三码全相等时系统给出待确认提示；用户确认后该企业同时具备最终控制方和总部/母公司角色。
- 合并确认后恰好生成合并户、差额户、单体母公司户三个计算角色，重复确认不增加节点。
- 每个节点的 `node_key`、角色、企业代码、直接父节点和范围状态与输入逐值一致。
- 存在环或缺码时建树被阻断并显示明确原因。

### 场景 B：四表入库到未审数

导入一批包含普通科目、备抵科目、借贷方向、辅助维度和序时账发生额的四表数据，保留未匹配和歧义行。

逐值断言：

- 原始导入行、批次和 `source_version` 已保存。
- 激活后自动匹配映射数量、未匹配数量、歧义数量和金额合计可查询。
- `TrialBalance.unadjusted_amount` 与独立 SQL 聚合结果一致，方向列没有被遗漏或重复转换。
- 重复激活同一批次不重复累计。
- `TRIAL_BALANCE_UPDATED` 的项目、年度、版本和受影响科目范围正确。
- 在不打开底稿页面的情况下，后续自动任务仍可继续执行。

### 场景 C：未审数到明细表、披露表和审定表

使用同时包含普通明细、可扩展行、合计行和人工覆盖的底稿模板。

逐值断言：

- 明细表自动值和 TB 源值一致，行身份不是依赖当前行号。
- 披露表从明细表或指定 TB binding 获取正确科目，`section_id/table_id/row_id/col_id` 正确。
- 审定表显示未审数、调整候选值和审定候选值，尚未发布时不改变 TB 审定数。
- 人工覆盖单元格保留人工值，并能查看被覆盖的自动值。
- 关闭页面后直接触发刷新，结果与打开页面触发一致。

### 场景 D：调整分录审批闭环

创建一条草稿调整分录，确认草稿未进入审计调整列；批准后再观察下游。

逐值断言：

- 草稿分录可被权限允许的用户修改，但不影响审定数、报表审定数和附注审定数据。
- 审批后只产生一次 `ADJUSTMENT_APPROVED` 和对应的 `TRIAL_BALANCE_UPDATED`。
- TB 审计调整、审定表、披露表、报表审定数、附注对应科目和调整大厅状态均与分录逐值一致。
- 借方、贷方、方向和净额保持一致，调整前后恒等式成立。
- 更正或撤回产生可追溯的新版本，不覆盖原审批记录。

### 场景 E：抵消分录推送到合并差额表

在合并工作底稿调整抵消分录汇总表录入一条内部交易抵消和一条内部投资抵消，分别覆盖正向和负向净额。

逐值断言：

- 分录只在批准后进入合并层。
- 合并试算表调整/抵消列与分录明细逐科目相等。
- 合并报表差额表逐科目等于分录影响，且不重复加子企业个别数。
- 合并附注差额表的目标 `section_id/table_id/row_id/col_id` 与 binding 一致。
- 合并户每个受影响科目满足 `individual_sum + adjustment + elimination = consolidated`。
- 从附注单元格可以反查 `source_entry_ids` 和汇总表行。
- 重复刷新不重复累计；人工锁定单元格不被覆盖。

### 场景 F：国企/上市附注和多格式模板

国企和上市各选择一个复杂多级表头、一个合计/小计表、一个差额表和一个含合并单元格的章节；分别使用规范化 JSON、Word、Markdown 和 XLSX 作为输入或导出格式。

逐值断言：

- 章节使用稳定 `section_id`，显示编号和标题按 variant 正确显示。
- 多级表头的叶子列、列组、期末列、合计列和差额列没有错位。
- 合并单元格导入/导出后 `rowspan/colspan` 结构保持或明确报告降级。
- 合计/小计行按 `row_type` 和行范围计算，序号展示变化不改变 `row_id`。
- 国企和上市的专有章节不会因中文标题相似而互相写入。
- Word、Markdown、XLSX 的结构差异都在报告中可见，不能无提示丢公式或合并单元格。

### 场景 G：公式管理、skip、stale 和失败恢复

制造缺少章节、缺少列、来源歧义、无树、无节点、人工锁定、CAS 冲突、单章节数据库异常和旧模板版本等故障。

逐值断言：

- 每个故障对应明确的 `skipped_*` 或 `failed_*` 状态和中文原因。
- 批量接口返回 persisted、unchanged、skipped、failed 的数量和明细。
- 一个章节失败不污染其他独立章节，重试只处理失败项。
- CAS 冲突不覆盖用户最新值。
- stale 标记能从触发事件追溯，成功刷新后状态按定义清除或更新版本。
- 公式版本停用后不会继续产生新写入，旧结果仍可对照。

### 场景 H：Playwright 页面验收

Playwright 至少覆盖以下用户动作：

1. 创建或打开合并项目，确认系统自动生成树。
2. 点击合并户、差额户和单体母公司户，检查右侧标题、请求参数和金额口径。
3. 在四维表切换企业、期间和度量，检查数据随 `node_key` 更新。
4. 打开合并报表、报表差额表、合并附注差额表，进入公式管理查看来源。
5. 输入或审批调整/抵消分录，观察运行批次和下游结果。
6. 锁定一个附注单元格并刷新，确认人工值不变且界面显示跳过原因。
7. 触发一个已知失败项，查看失败明细并执行重试。

浏览器断言必须结合网络请求和数据库结果，检查是否出现包装体解包错误、取消请求被误报失败、组件挂载时意外写入、旧节点数据残留、英文用户可见文本或按钮权限错误。

## 十三、风险、外部依赖和暂缓项

### 13.1 主要风险

- **树身份漂移**：如果部分路径继续使用企业名称、中文标题或位置索引，右侧页面可能显示另一企业的数据，且表面上请求仍返回成功。
- **双重写入**：审定表发布门、公式推送和页面自动保存若存在多个写入方，可能互相覆盖，造成审定数与披露表不一致。
- **合并重复计量**：把差额户当普通子企业、把母公司合并数据当本部个别数据或把后代直接汇总到每个父节点，都会造成合并数偏大。
- **模板错位**：国企/上市标题相似、Word/Markdown/XLSX 表头表达能力不同、合并单元格展开方式不同，可能让公式写入错误列而不报错。
- **fail-open 假成功**：缺少绑定、缺少列或运行失败时如果保留旧值并返回成功，用户会误以为附注已刷新。
- **版本覆盖**：旧树、旧公式或旧数据批次的异步任务晚到时，可能覆盖当前版本；必须用树版本、输入版本和 CAS 阻断。
- **大事务和锁竞争**：全项目全章节同步会拖长事务并锁住人工录入，需采用增量集合、短事务和分批任务。
- **真实数据分布未知**：静态模板数量和现有代码不能证明真实项目中每个 binding 都被命中，必须用真实 PG 统计实际命中、stale、skip 和失败。

### 13.2 外部依赖

- 企业代码、企业名称和最终控制关系需要项目基础数据或外部主数据源；外部服务不可用时应允许用户核对原始代码并进入待确认状态，不能静默使用模糊匹配。
- Word 和 XLSX 解析/导出依赖对应库和文件格式能力；无法表达的结构必须输出差异报告，不能把解析空结果当作模板为空。
- 真实 PG、Redis、SSE、任务队列和前端开发服务是端到端验证前提；本轮只执行了真实 PG 只读数据库核验，未执行依赖真实服务运行的端到端验证。
- 合并附注中的复杂法规判断、特殊披露口径和多币种/折算规则需要审计专业人员确认，公式引擎不能自行推断业务政策。

### 13.3 暂缓项

在核心闭环稳定前，以下事项建议暂缓或单独立项：

- 立即把单体和合并所有物理表强制合并。
- 用 AI 或模糊标题匹配替代稳定身份和明确 binding。
- 在没有真实模板和业务复核的情况下批量自动生成复杂法规公式。
- 为了追求全量自动化而绕过审定发布门、调整审批或抵消审批。
- 在没有真实规模数据和锁竞争指标前承诺 6000 并发。
- 继续扩展新的附注章节，直到现有国企/上市核心章节的绑定、刷新和逐值追溯通过验收。

## 十四、建议的交付物和完成判据

建议最终交付以下产物：

1. `requirements.md`：用户目标、范围、权限、状态、非功能要求和验收场景。
2. `design.md`：树模型、三码规则、`node_key` 协议、事件图、公式 binding、附注规范化模型和迁移方案。
3. `tasks.md`：按阶段拆分且每项任务绑定代码、迁移、测试和真实环境验收证据。
4. 树构建与节点上下文的迁移和契约测试。
5. 四表导入、TB、底稿、调整、抵消、报表和附注的链路集成测试。
6. 国企/上市、多级表头、合并单元格、标题/序号和 Word/Markdown/XLSX 的模板对账报告。
7. 公式运行批次、skip/stale/failed 可见性和人工覆盖/CAS 的端点级测试。
8. 真实 PG 验收数据、Playwright 运行记录、逐值 SQL 对账结果和失败恢复记录。
9. 运行时监控指标：运行批次耗时、受影响节点数、实际命中 binding 数、skip 数、stale 数、失败数、重试数和锁等待。

完成判据不能只写“代码已合并”或“测试通过”，应逐条绑定证据：

- 代码路径和迁移已进入目标分支。
- 端点级测试真实调用依赖链并检查权限和响应数据。
- 真实 PG 检查输入与输出的逐值相等、恒等式和版本一致性。
- Playwright 检查用户动作、页面上下文、网络请求和错误展示。
- 失败注入证明 skip/failed 不是恒绿分支，重试不会重复写入。
- 模板变体和格式差异有实际文件对账，不只检查 JSON 字段存在。
- 运行时统计区分静态登记数量与实际命中数量，并保留运行批次。

只有当上述证据同时具备，才可以把“四表入库 → 试算表 → 底稿 → 披露表 → 审定表 → 报表/附注/调整大厅/合并”的链路标记为已闭环。

## 十五、结论

当前平台的主要基础已经存在：数据导入和试算表事件、报表与普通附注刷新、底稿披露同步、合并树、合并工作表/报表推送和合并附注公式服务都已经提供了可复用部件。下一步的重点是把这些部件放入统一的身份、版本、公式和运行批次协议中，并用真实 PG 和浏览器证明它们在同一用户场景下可以连续运行。

建议先完成自动建树和 `node_key` 上下文，再收口四表到审定表的单体链路，随后打通抵消分录到合并差额表和附注差额表，最后统一附注模板与公式管理。每一阶段都要保留人工覆盖、显式审批、失败可见和可回滚能力。这样才能实现用户要求的“数据一次录入、公式管理自动刷新、报表和附注可追溯”，同时避免把局部源码能力误认为完整生产闭环。

该分录的金额已经反映到两行 `consol_trial.consol_elimination=50.00`，所以“已批准抵消分录→当前合并试算抵消金额”在这两个科目上可以逐值对拍。但来源字段为空，当前无法从合并试算或报表行反向定位到这条分录的稳定来源身份，也无法证明它属于哪个树版本、差额节点或具体附注目标。建议把 `source_entry_ids`、`node_key`、`tree_version`、批准版本和目标 binding 作为强制 provenance，缺失时将运行标记为 `failed_validation` 或 `skipped_missing`，不能继续显示为完整成功。

另一个身份问题出现在 breakdown 与来源试算表之间。`consol_trial.consolidation_breakdown` 使用企业代码和节点键，例如 `91110000100000000R:hq`、`911100002000000005:branch` 和 `911100005000000007:subsidiary`；但相关来源项目的 `trial_balance` 行中，`company_code` 实际均为 `'001'`，而不是 breakdown 中的企业代码。相关来源项目的 `tb_balance` 和 `ledger_datasets` 也均为 0 行。因此当前可以确认金额拆分结果存在，不能确认“四表来源行→企业身份→合并节点”的身份映射已经闭合。这是建议文档中必须保留的真实数据风险，不能用名称或来源项目 ID 推断身份映射已经正确。

`consol_worksheet` 记录了 13 个角色化节点、2 个科目。它能证明当前测试数据里存在 `hq`、`parent`、`consol`、`consol_elim`、`branch` 和 `subsidiary` 等角色，但 13 行不能直接解释为 13 个企业，也不能直接证明已经严格按“企业身份节点 + 合并户/差额户/单体母公司户”三类目标角色建树。实现和验收时应分别统计企业身份节点、计算角色节点和兼容角色节点。

### 16.6 对原建议的修正结论

真实 PG 结果支持并强化原文的基本判断：链路部件确实存在，合并试算到合并报表的局部结果可以对拍，但“四表入库 → 试算表 → 底稿明细/披露表 → 审定表 → 报表/附注”的生产闭环尚未被真实运行证据证明。需要把原文中的证据等级进一步改成以下表述：

| 链路范围 | 本次证据 | 当前判定 |
|---|---|---|
| 合并试算四度量恒等式 | 1122、2202 两行独立 SQL 计算 gap 均为 0 | 局部通过 |
| 合并试算 → 合并报表 | BS-006、BS-045 逐值相等，352 行报表均非 stale | 当前测试项目局部通过 |
| 抵消分录 → 合并试算 | 1 条 approved 分录的 1122/2202 金额反映为 50 | 金额局部通过，provenance 未闭合 |
| 四表导入 → 未审数 | 无项目级 import batch、active ledger dataset、tb_balance 证据 | 未证明 |
| 未审数 → 底稿明细/披露/审定表 | 项目对应底稿与披露计数为 0，未发现项目运行记录 | 未证明 |
| 合并公式 → 附注数据 | 51 条全局 seed 公式存在，但 3 条附注数据全部 stale | 未证明，且当前未刷新 |
| 合并推送整体状态 | 2 次 `consol_push_run.succeeded` | 只能解释为报表完成、附注标 stale |
| 生产真实集团 UAT | 选定项目为 2098 测试/合成项目 | 未执行 |

基于这次核验，建议将合并运行成功状态拆成至少三种互不替代的结果：

```text
report_succeeded       = 合并报表已按当前合并试算生成并通过基本校验
note_marked_stale      = 附注已被准确标记为需要刷新
note_refreshed         = 附注按项目/年度/节点/公式版本实际写入，并通过逐值校验
```

只有 `note_refreshed=true` 且 stale 行清零或被明确分类为人工锁定/不适用/跳过时，才可以向用户显示“附注刷新完成”。`consol_push_run.status='succeeded'` 应改为聚合状态，至少同时返回上述三个结果以及 persisted、unchanged、skipped、failed 明细。

### 16.7 对实施方案的新增验收要求

真实项目核验后，阶段 0 至阶段 5 的出口条件应追加以下硬性要求：

1. **四表前置证据**：真实验收项目必须存在有效导入批次、激活的数据集、`tb_balance` 或等价四表原始余额、映射版本和项目级事件记录；只有 `trial_balance` 预置行不能通过四表链路验收。
2. **身份一致性**：来源 TB 行的企业身份必须与 breakdown 的 `company_code`/`node_key` 可通过数据库字段或明确映射表逐值连接；`company_code='001'` 之类的占位身份不能直接视为企业代码已闭合。
3. **抵消 provenance**：每个 `consol_elimination` 非零值都必须能反查到已批准分录、分录行、关联企业、差额节点、树版本和公式目标；任一缺失都要进入结构化失败或跳过清单。
4. **附注刷新结果**：验收必须分别断言实际写入数、未变化数、人工保护数、歧义跳过数、缺失跳过数、失败数和刷新后 stale 数，不能只断言运行接口返回成功。
5. **计数口径**：运行摘要必须同时给出 distinct section、node instance、cell、写入和 stale 状态计数；“3 章”不能同时代表 1 个 section 和 3 个节点实例。
6. **公式上下文**：全局 seed 公式可以作为模板版本，但执行时必须绑定 `project_id`、`year`、`node_key`、`template_type`、`tree_version`、`source_version` 和 `formula_version`，或者明确记录全局公式版本与运行时上下文解析结果。
7. **真实项目分级**：2098 测试/合成项目只能作为冒烟和局部回归样本；生产 UAT 必须另选有真实四表导入批次、企业范围、底稿和人工审批记录的集团项目。

本节的真实 PG 结果修正了“只做静态分析、尚无真实数据库证据”的旧描述，但没有改变本文的总判定：当前能证明若干合并计算和报表输出局部正确，不能证明用户要求的完整四表到附注自动闭环已经在生产环境打通。
