# 平台全局体验与一致性建议书

> 视角：资深合伙人 / 系统总负责人
> 日期：2026-06-23
> 定位：本文聚焦**用户实际使用体验、5 角色差异化、前端呈现一致性与美观、全局横切功能、上线后可维护性**。
> 与既有 `docs/architecture-improvement-proposals.md`（后端 19 模块技术架构）**互补不重叠**——那份讲"代码怎么写更对"，本文讲"人用起来顺不顺、看起来一不一致、上线后好不好养"。

---

## 〇、一句话结论

平台的**底层基础设施已经相当成熟**（GT 设计 token 系统、暗色模式、显示偏好 store、79k 节点的联动图、熔断/降级/限流齐全）。当前的主要欠债**不在"缺能力"，而在"能力没有被一致地用上"**——同一件事在不同页面有不同实现、不同角色挤在同一套界面里、好的全局组件造好了却没被普遍引用。

因此本文的主轴是三个词：**收口（单一真源）、分层（角色差异化）、贯通（联动闭环）**。

## 一、最扎眼的一致性硬伤（已实证，建议优先）

这一节每条都附了代码证据，是"用户一眼能看出来不对"的问题，改动小、收益最直观，建议作为第一批。

### 1.1 🔴 审计循环颜色在 4 个地方各定义一套，色值互相打架

| 定义处 | D 循环色值 | 用途 |
|--------|-----------|------|
| `views/workpaper-list/WorkpaperWorkbenchView.vue` `CYCLE_COLORS` | `#E8590C`（橙） | 底稿工作台分组卡片 |
| `components/panorama/colorMaps.ts` `CYCLE_COLOR_MAP` | `#1976D2`（蓝） | 联动全景图 |
| `components/workpaper/WorkpaperDependencyGraph.vue` `CYCLE_PALETTE` | 本地另一套 | 底稿依赖图 |
| `components/dashboard/projectGanttUtils.ts` `CYCLE_COLOR_MAP` | 又一套 | 项目甘特图 |

**用户实感**：同一个"D 销售循环"，在工作台看是橙色，切到全景图变蓝色，进甘特图又变了。颜色是审计人员建立空间记忆的锚点，颜色不稳定 = 认知负担。

**建议**：把循环色板提到 `styles/gt-tokens.css` 作为 CSS 变量（`--gt-cycle-D` … `--gt-cycle-N`）+ 一份 `constants/cyclePalette.ts` 单一真源，4 处全部引用它。这是纯收口，无逻辑风险。

### 1.2 🔴 金额格式化绕过 `displayPrefs`，单位切换不跟随

平台已有设计极好的全局显示偏好（`stores/displayPrefs.ts`：万元/元、字号、小数位、负数红、密度），并提供了 `prefs.fmt(v)` 统一格式化。但实测大量页面**直接写裸 `toLocaleString('zh-CN', { minimumFractionDigits: 2 })`**：

- `TrialBalance.vue`：公式详情、汇总明细、收入/费用/净利润明细弹窗共 10+ 处裸格式化
- `qc/ClientQualityTrend.vue`：`{ style: 'currency', currency: 'CNY' }`（带 ¥ 符号，与平台"元/万元"规范冲突）
- 各 Dashboard、Penetration 多处

**用户实感**：用户在顶部把单位切成"万元"，主表跟着变了，但点开"公式详情/汇总明细"弹窗里的金额还是"元"，且小数位、负数红也不统一。审计人员核对数字时这种不一致很容易看错量级。

**建议**：
- `prefs.fmt()` 作为唯一金额出口，禁止业务代码裸调 `toLocaleString`/`toFixed` 格式化金额
- 加一条 ESLint 自定义规则或 CI grep 守卫：`.vue` 内出现 `toLocaleString.*minimumFractionDigits` 即告警
- 时间格式化同理收口到一个 `formatDateTime()`（现在每个页面各写一份 `new Date().toLocaleString('zh-CN', {...})`，格式参差）

### 1.3 组件内硬编码颜色（多数有 token fallback，少数裸值）

实测 `var(--gt-x, #hex)` 这种带兜底的写法占多数（可接受）。但有裸硬编码：
- `WorkpaperEditor.vue` 弹窗头 `linear-gradient(135deg, #6750A4 0%, #8b5cf6 100%)`、`background: #fafafa`
- `WorkpaperWorkbenchView.vue` 进度条 `#67c23a`/`#4b2d77`、图例 `#6750A4`/`#E8590C`/`#2E7D32`

**建议**：裸值替换为 token；`el-progress` 这类组件色统一走 `--gt-color-success`/`--gt-color-primary`。配一个 Storybook 视觉回归或 stylelint `color-no-hex` 限定只在 token 文件允许 hex。

## 二、5 角色视角：当前"一套界面塞所有人"，建议分层

这是本文最重要的一节。平台已经有角色基础设施（`stores/roleContext.ts`、`useProjectRole`、`useRoleViewPreset`、`permission_matrix`），也已经出现了 **9 个 Dashboard**：

```
Dashboard / PersonalDashboard / ProjectDashboard / ManagerDashboard /
ManagementDashboard / PartnerDashboard / PartnerProjectDashboard /
QCDashboard / RoleWorkbench
```

问题不是"没做角色"，而是**角色入口碎片化又彼此重叠**——9 个仪表盘之间职责边界模糊，新人/运维搞不清谁该进哪个；而真正进入底稿、复核等核心工作区后，5 个角色看到的又几乎是同一套界面 + 按钮靠权限禁用。

下面按角色给"他每天打开平台最想要什么"，以及当前缺口。

### 2.1 审计助理（现场执行，使用频率最高、停留最久）

**核心诉求**：少找、少等、少跳。打开就知道"今天该做哪几张底稿"，取数快，保存稳，联动清楚。

**当前缺口与建议**：
- **统一"我的任务"入口**：现在任务分散在 `MyProcedureTasks` / `TaskTreeView` / 各 Dashboard。建议助理登录默认落地一个"我的底稿待办"工作台（按循环分组 + 完成率 + stale 提醒 + 一键进入编辑）。
- **取数失败要显性**：`auto_data_resolvers` 静默返回 0 或空（见架构文档 §4.8/§3.4）对助理最致命——他以为取到数了，其实是 0。建议预填单元格对"取数失败/超时"用 `--gt-marker-prefill-error` 明确标红，而非显示 0。
- **保存反馈一致**：四条保存路径（HTML/Univer/OnlyOffice/cell-writeback）的成功/冲突提示文案与交互各不相同（架构文档 §2.17）。助理在不同底稿间切换时，"保存成功"的体验应当完全一致。

### 2.2 现场经理（项目管理：进度、分派、一级复核）

**核心诉求**：全局进度一眼清、瓶颈在哪、谁卡住了、复核意见批量处理。

**当前缺口与建议**：
- **进度真实性**：进度条要反映"实质完成"而非"打开过"。建议完成率口径文档化（已编制 vs 已复核 vs 已签字），并在 `useWpCompletionRate` 统一，避免各 Dashboard 各算各的。
- **分派与工时联动**：分派底稿（scope_cycles）应自动带出预算工时，经理在一个界面看到"分派—预算—实际工时—完成率"四联视图，而不是工时（`WorkHoursPage`）与底稿分派两套割裂界面。
- **一级复核批量化**：`ReviewWorkbench` 已有，但建议支持"按循环/按助理批量打勾 + 批量回退"，经理复核 50 张底稿不应点 50 次。

### 2.3 质控复核合伙人（QC 28 条 + 独立质量复核）

**核心诉求**：规则结果可信、问题可追溯、巡检不漏。

**当前缺口与建议**：
- **QC 规则结果要能下钻到底稿**：`QCDashboard` 显示"警告 N 条"，应每条都能 chip 跳转到触发它的底稿/单元格（复用 `address_registry` 的 jump_route），而不是只给个数字。
- **python 规则的安全与可信**（架构文档 §11.1）：dotted-path 加载 + 仅超时不是沙箱。质控合伙人需要知道"这条规则是谁、什么时候、改了什么"——建议规则变更走版本留痕 + 仅 admin 可编辑 python 类规则。
- **"假绿"防护**：质控最怕指标显示通过但实际没查。建议 QC 通过态要绑定证据（哪些底稿、什么时间检查的），与归档门禁（consistency_gate）共用同一套证据链。

### 2.4 项目合伙人（审计判断、签字、对外承担责任）

**核心诉求**：少看细节、多看结论与风险；签字前要有"全绿才能签"的确定性。

**当前缺口与建议**：
- **合伙人不该被 9 个 Dashboard 绕晕**：`PartnerDashboard` 与 `PartnerProjectDashboard` 职责需合并/明确。合伙人要的是"项目健康度一屏"：意见类型、KAM、重大错报、未决事项、各角色签字状态、归档就绪度。
- **签字流的确定性**：`PartnerSignDecision` 签字前应强制展示阻断项清单（重大错报未处理、QC 阻断规则未过、独立性未声明），全绿才放行签字按钮。A1-11 签发流转表（当前在做的 spec）正是这条链路的载体，建议把"签字前置校验"做成可复用的 `useSignoffChecklist` 统一组件，partner/manager/qc/eqcr 共用。
- **金额单位对合伙人尤其敏感**：见 §1.2，合伙人看汇总数时单位不一致是高风险。

### 2.5 EQCR 技术复核人（独立复核，影子计算）

**核心诉求**：独立、不被项目组数据污染、能对比差异。

**现状评价**：这是设计最好的角色之一——`eqcr_shadow_compute_service` 提供独立取数通道（影子计算不写项目组数据），职责分离清晰。

**建议**：
- 影子计算限流 Redis 故障时 fail-open（架构文档 §12.1），建议降级为进程内计数兜底而非完全放开。
- EQCR 的"差异对比"结果建议也接入 chip 跳转，让复核人从差异直接跳到团队底稿对应单元格。

### 2.6 角色分层的统一建议

- **收敛 9 个 Dashboard 为 1 个 `RoleWorkbench` + 角色 preset**：用 `useRoleViewPreset` 驱动同一个工作台壳，按角色装配不同卡片（助理=我的底稿、经理=进度分派、QC=规则巡检、合伙人=健康度签字、EQCR=影子差异）。一个入口、按角色变脸，而非 9 个入口互相重叠。
- **权限基建要"强制接入"而非"造好备用"**（架构文档 §17.1）：`permission_matrix` 单一真源已存在，但部分端点绕过它（§5.12 IDOR、§5.13 越权）。建议 CI 守卫：敏感端点必须声明 operation code。这对 5 角色的边界正确性是地基。

## 三、全局横切功能：建议建立"平台级单一真源"清单

你点名的那些维度（项目/人员/工时/底稿/附件/复核/枚举/年度/编辑/显示/字体字号/权限/查询/知识库/对话/LLM/数值/复制/四表联动），它们的共同问题是**横切关注点没有统一治理点**。下面逐项给现状判断与建议。

### 3.1 显示 / 字体字号 / 数值处理 —— 基建好，落地未收口
- ✅ 已有 `displayPrefs`（字号/单位/密度/小数/负数红/高亮阈值）+ `gt-tokens.css`（完整字号梯度 xs~3xl）。
- ❌ 落地不彻底（§1.2）。**建议**：金额、时间、百分比三类格式化各设唯一出口函数，全局禁止裸格式化。

### 3.2 枚举 / 字典 —— 双层设计好，前后端仍手动同步
- 后端 `_DICTS` + DB override 双层（好），但前端 `dictLabels` 注释明写"与后端手动同步"，函证枚举还有两份漂移文件（架构文档 §6.1/§6.2）。
- **建议**：字典中文名也由后端 `/dicts` 返回；删除重复的 `confirmationEnums.ts`；评估"可运营扩展字典"（回函方式/差异类型）改为 DB 完全可增删。

### 3.3 年度 —— 多年度共存有串数风险
- 🔴 报表缓存 key 缺 year → 跨年度串数据（架构文档 §9.1）。这是正确性 bug，最高优先。
- **建议**：建立"年度上下文"统一约定——所有缓存 key、所有查询入口强制带 year，CI 守卫缓存 key 构造必须含 year。

### 3.4 权限 —— 真源已有，未强制
- 见 §2.6。`permission_matrix` + `usePermission`/`usePermissionMatrix` 已存在，问题是覆盖不全。
- **建议**：建立"敏感端点授权矩阵"文档，逐端点核对"项目成员校验 + operation code 校验"两层是否都在。

### 3.5 四表 ↔ 未审报表 ↔ 审定表 ↔ 底稿 ↔ 调整分录 ↔ 附注 联动穿透 —— 平台核心价值，但 stale 图分裂
- 这是平台**最核心的价值主张**（memory：联动是核心价值，孤立底稿=无价值）。基建强（`address_registry` 79k 节点、`ref_index` chip、`StalePropagationEngine`）。
- ✅ **2026-06-23 已完成两项关键收口**（codegraph 实证，见 §七）：孤立 EventBus 已删除（`custom_query/metrics.py` 留注释追溯）、四条写入路径（HTML/Univer/OnlyOffice/cell-writeback）已**全部收口到 `WorkpaperSaveOrchestrator.after_save`**。这是 `single-source-cleanup` + `workpaper-save-orchestrator` 两个 spec 的成果。**本条原列为最高优先，现已大部完成，降级。**
- ❌ 仍存在的问题：stale 传播仍有**多个引擎入口并存**——`StalePropagationEngine.on_change`（事件订阅统一入口）、`wp_formula_dependency.mark_stale_downstream`（仅 `incremental_refresh` 调用）、`prefill_engine.mark_stale`，加上静态 `unified_dependency_graph.json` + 运行时图。这些目前是**分层协作**（非简单重复），但缺一份"谁负责哪层、入口是哪个"的权威说明，新人改 stale 逻辑容易改错层。
- 🔴 **新发现死代码**：`backend/app/services/stale_incremental_propagation.py`（86 行，3 个 `propagate_stale_by_*` 函数）**零引用**（codegraph callers + grep 双重确认无人 import）。极易误导后人以为这是 stale 入口。
- **建议**（仍值得投入，但聚焦点变了）：
  - **删除死代码** `stale_incremental_propagation.py`（先确认无动态分发引用，已确认）。
  - **写一份 stale 分层文档**：`StalePropagationEngine` 为唯一对外入口，其余为其内部分层（公式层 `wp_formula_dependency` / 预填层 `prefill_engine`），并在代码注释标注调用关系。
  - 用户实感目标：**改任何一处数字，所有引用它的地方都会变灰提示"需刷新"，无一例外**——现在写入收口已达成，重点转为"传播层次清晰、可维护、无死代码误导"。

### 3.6 编辑 —— 三套锁 + 四套乐观锁字段，缺统一仲裁
- `editing_lock` / `wp_cell_lock` / `wp_sheet_lock` 三套锁无层级协调；四条写入路径用 4 种乐观锁字段（架构文档 §2.17/§2.18）。
- **建议**：锁层级化（资源 > sheet > cell）；乐观锁统一字段（`file_version`）；前端 `useConflictGuard`/`useEditStateMachine` 对接统一冲突响应，让"冲突提示"在所有底稿一致。

### 3.7 复制 / 粘贴 —— 有 composable，需确认跨组件一致
- 已有 `useCopyPaste` / `usePasteImport`。**建议**：确认所有表格类组件（audit-sheet / Univer / d-form-table / confirmation-*）复制粘贴行为一致（含金额单位还原、格式保留），避免"这张表能粘那张表不能"。

### 3.8 附件 / 附注 —— 入口多、命名爆炸
- 附件有 `AttachmentHub` / `AttachmentManagement` / `PrivateStorage` / `useRowAttachment` 多入口；附注有 50+ `note_*` 服务（架构文档 §8.2）。
- **建议**：附件统一一个"项目附件中心"+ 行级附件复用同一上传组件；附注服务按职责子包化（fill/formula/resolve/export）。

### 3.9 工时 / 工时管理 —— router 碎片化，与底稿割裂
- 6 个工时 router（approve vs approval 命名歧义，架构文档 §16.1）。
- **建议**：合并 router；工时与底稿分派/项目预算打通成一个视图（见 §2.2）。

### 3.10 知识库 / 对话 / LLM 辅助 —— 韧性好，facade 层深，出口需全过审
- ✅ 熔断/超时/降级三件套齐全；有 `ai_content_gate` + watermark + log。
- ❌ facade 叠 4 层（架构文档 §19.2）；LLM 配置 import 时读取，改模型需重启。
- **建议**：对外只暴露 `unified_ai_service`；LLM 配置运行时可 reload；**确保所有 LLM 出口（a17/note_ai/wp_ai/doc_ai_chat）无旁路地经过 gate + watermark**——审计场景 AI 内容必须留痕，这是合规底线。知识库检索建议统一一个入口（`useKnowledge`），避免各模块各接一套 RAG。

### 3.11 查询（高级查询）—— 攻击面最集中，优先加固
- 🔴 IDOR + 跨项目写 + SQL f-string（架构文档 §5.12/§5.13/§5.1）。
- **建议**：作为安全第一批整改（见 §五）。

### 3.12 项目 / 人员 —— 标准 CRUD，建议核对项目职责维度
- `permission_matrix` 目前主要按系统角色映射，项目职责（scope_cycles）维度是否参与权限判断需确认（架构文档 §17.2）。
- **建议**：明确两层授权模型（系统角色能力 + 项目成员范围），让"现场经理只能改自己分派循环的底稿"这类约束可表达。

## 四、上线后可维护性（运维便利性）

6000 并发目标 + 内网全栈部署，运维便利性决定上线后能否扛住。

### 4.1 多 worker / 分布式就绪度（规模化前的硬阻断）
平台大量关键状态是**进程内内存态**，与多 worker 部署矛盾（架构文档 §7.1/§3.7/§3.12/§18.1）：
- 导入并发闸门、取消信号在进程内 → 多 worker 下并发上限失效、取消送不达
- 地址库/公式/字典缓存 per-process → 缓存踩踏、N 倍重建
- OCR 引擎 per-process ~500MB × worker → 内存瓶颈

**建议**（规模化专项，需压测）：
- 盘点"哪些状态必须外置到 PG/Redis"，建一张"进程内状态清单"逐项判断。
- 项目级互斥用 PG advisory lock；全局并发用 DB/Redis 计数；取消信号走 DB 标志位轮询（cancel_requested 列今天刚补上，方向对）。
- OCR 抽为独立服务容器，所有 worker 共享。
- 缓存加 single-flight + 增量失效。

### 4.2 静态资源热重载缺失（运营改配置就得重启）
反复出现的模式（架构文档 §3.2/§13.1/§15.1/§19.1）：override / prompt / questions / rules / LLM config 散落各处，多数 import 时加载，改一处要重启整个后端。对 6000 用户系统，重启=全员中断。
**建议**：沉淀**一个统一的"mtime 热重载 JSON 资源加载器"基础设施**，所有静态资源复用（`wp_code_override_loader` 已是好范本）。运营调 prompt/规则/字典不停服。

### 4.3 巨型文件维护风险
后端 6 个 >1500 行 god 文件（`event_handlers` 1929 行 / 132 依赖符号最危险）、前端 5 个 >1700 行巨型 Vue（`LedgerPenetration` 3977 行）。
**建议**：按架构文档 §1.1/§1.2 渐进拆分；新代码立"单文件软上限"（service ≤ 800 行、.vue ≤ 800 行）并在 CI 告警，先止血再清存量。

### 4.4 目录组织到极限
`services/` 622 文件扁平、`routers/` 270+ 文件碎片化、`views/` 88 顶层文件。新人定位困难、易删错（consol orchestrator 曾被误删重建）。
**建议**：按域子包化（架构文档 §1.4/§1.5），每个子包 README 标 DAG/依赖关系图。

### 4.5 迁移与 schema 漂移治理
今天刚遇到 V092 重号 + cancel_requested 列漂移。MigrationRunner 已有重号检测（好），但 schema drift 仍需人工看日志。
**建议**：把"启动期 schema drift 检测"结果接入健康检查端点 + 告警；迁移文件加 CI 守卫（重号、缺配对 R 回滚脚本即 fail）。
