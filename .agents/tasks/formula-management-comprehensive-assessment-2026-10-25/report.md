## 0. 审计口径、证据等级与限制

### 0.1 四层实现状态

本文不以“有文件、有组件、有测试”替代用户链路验收，所有能力按以下最高证据层定性：

- **L1 已编码**：生产源码、迁移或模型存在。
- **L2 已挂载**：路由已注册、前端生产宿主已挂载、请求契约闭合；迁移已应用、表已存在等部署事实也只到此层。
- **L3 已运行**：生产函数在真实项目数据上运行过（含在不提交的事务内调用后回滚），或 live PostgreSQL 中有业务数据经过该能力并经只读探针验证（§1.2 规则（2））。
- **L4 业务闭环**：真实用户完成定义、预览、发布、冲突处理、执行、写入、传播和溯源，并可复验结果。

自动化绿测是支撑材料，不单独提升层级；OpenAPI、Mock、SQLite、直接 mount 组件也不等于 L4。**按本口径，当前没有任何能力达到 L4**（未做登录态写入型 UAT）。

- **B（中）**：生产源码、注册、生产挂载和契约闭合，但缺写入型 UAT 或运行证据。

1. **反证封顶**：主路径存在已复现或契约闭合的确定性错值、错误成功（含假空、假通过）、不可控写入或跨项目泄露项目业务数据的路径，且该路径在正常权限/数据前置下可触发（如用户写了不支持的函数或悬空引用、并发修改同一公式），修复前该项最高 1 分；只在请求本身异常失败（如 403/500、网络中断）时才出现的假空或假成功不触发本规则，登记为 P2/P3（R3-04 补写；复核现有各项，封顶都满足这一条件）。本规则与 P 级无关：P 级衡量对业务数值/权威写入/安全隔离的影响面，本规则衡量该能力本身是否可信。
2. **采用门槛**（P1R-01 改写）：该能力在 live 库中没有任何业务数据经过（相关业务行为 0，或从未在真实项目数据上运行），且没有真实用户写入证据时，最高 2 分。迁移已应用、表已存在、路由已注册、组件已挂载都是部署事实，只证明 L2。研究者在真实项目数据上调用生产函数（含不提交的回滚事务）可证明执行类能力的 L3；以用户定义为考核对象的检查项（用户规则、项目适配、模板）按其用户数据是否为 0 判断。登录态写入型 UAT 是 4 分的必要条件，不是 3 分的必要条件。
3. 只有局部真实运行、没有完整用户链，最高 3 分。
4. 测试数量不加分。
5. **组合项按较弱子能力计分**：一个检查项含多个子能力时，取各子能力得分的最小值（关闭 F-02）。**子能力的粒度**（R3-01）：子能力只指检查项名称中并列列出的能力，依据栏写出决定得分的最弱子能力（第 20、21 项列出全部子能力的得分）。按域或作用范围的覆盖缺口（如第 13 项 Runtime/Tier A 不读全局层、第 16 项合并附注没有项目入口、第 17 项只有 3/7 域接推广）记为“局部”，在该项分值内体现，不另拆成子能力；同一能力下的不同规则来源（如第 12 项的内置规则与用户规则）也不拆。
6. **缺陷归属**：缺陷计入其根因所在执行项及写入该值的传播项；可观测类检查项（第 21~24 项）衡量“展示/记录是否忠实反映同一次求值或真实事件”——被观测引擎自身的错值计入执行项，展示与求值不一致、假空或跨项目暴露才触发本项封顶。门禁类检查项（第 25 项）衡量“目标出错时门禁会不会变红”：代表测试在已证实的错值、假空面前仍全绿，属门禁自身的假通过，按规则（1）计入本项。共享根因在其他执行器上的表现未复现的，登记为待核风险（§6.6），不提前封顶。

## 6. P0~P3 缺陷与修法

### 6.1 统一分级标准

- **P0**：生产入口可达、正常权限/数据前置可满足时，缺失约束会确定地影响以下任一项：①**业务数值**（产出或交付错误业务数值，含以成功/fresh 状态返回或展示，无论是否落库）；②**权威写入**（权威业务表或公式定义被错误写入，或权威写方被绕过却报成功）；③**安全隔离**（跨项目暴露项目业务数据或客户资料——报表、底稿、附注、附件等——或越权写入）。无需已有事故样本。定级证据须为生产函数级复现，或从生产入口到错误结果的契约闭合。
- **P1**：高概率造成跨域不一致、传播丢失、审计可信度/可观测性失真（含不改业务值也不破坏权限的假空、假通过）或恢复失败；或影响面符合 P0 但可达性/确定性证据尚不足，须写明升级条件。
- **P2**：产品闭环、权限一致性、模板体验、局部可达性或规模性能缺陷。
- **P3**：命名、展示、测试治理和技术债。

**按收窄标准的明确裁定：**

1. **UnifiedLineage 少参（P1-1）与 timeline 字段漂移（P1-2）保留 P1。** 两者都确定性返回假空，属“错误成功”，但影响的是审计可信度与可观测性——用户看不到数据来源和变更历史——不改变业务数值、不写权威表、不突破项目权限。两者改动小、风险低，放入近期 R4/R5 与 P0 同批修复；按 §1.2 规则（1），它们仍使第 23、24 项封顶 1。
2. **P0-5 附件跨项目泄露仍为 P0**：属安全隔离。
3. 门禁假通过（P1-11）、审计链分叉与审计记录可被 edit 成员任意提交、年度不入哈希（P1-3）同属审计控制可信度，不改业务值、不跨项目，列 P1；`[V]` 单列为 P1 的 N2/N4/N5 确定性改变报表业务值，按收窄定义归入 P0-4 统一修复验收，P0 机制数仍为 6。
4. **P1-4 拆分（按结果是否被改成 0 划界，R3-06）**：参数个数不符时 L1 直接返回 0 且 ok 的情形——`IF` 不是 3 个参数（少参或多参）、`MAX`/`MIN` 少于 2 个参数、`ROUND()` 无参数、`AUX` 只给科目（预载只识别两参及以上写法，取值键为空）——与 `1/0`、缺行同属“错误业务数值以成功状态返回”，按 P0 ① 并入 P0-2（R2 验收同此）。`[V]` 实测 `IF(1>0,1)`、`MAX()`、`AUX('1122')` 均为 0 且 ok，源码确认这几种与上下文数据无关；`IF` 多参、`MAX`/`MIN` 单参、`ROUND()` 为源码判定（§11.3 第 19 条）。系统定义里没有这些函数（推送规则 IF/ROUND 0 处、预填映射只有一处说明文字提到 IF、报表 318 条公式只用 TB/SUM_ROW/ROW/SUM_TB，§11.3 第 10 条），暴露面只在用户自写公式，与 P0-1 同属“现网暴露 0 但正常前置可满足”。`ROUND` 银行家舍入留在 P1-4：`ROUND(1.005,2)=1.00` 是否算错误业务数值取决于平台舍入口径，而平台没有书面口径（银行家舍入本身是一种合法规则，会计与 Excel 习惯四舍五入得 1.01），须 §10 拍板；拍板为四舍五入后即按 P0 ① 并入 P0-2。多余参数被静默忽略、值不受影响的情形（`TB('1001','期末余额','x','y')`=123 且 ok；`NOTE` 的第 4 个参数同样被忽略）属校验缺口，留 P1-4。`[V]` 对 `NOTE('五、1','合计','期末','多余')` 测得 0，是因测试上下文没有附注数据（属 P0-2 已有的“缺引用返回 0”），不是参数个数造成的，故不再作 P0-2 的例子。
5. **发布记录读取过宽（P2-5）列 P2**：本次窄查确认 `GET /api/formula-settings/publishes` 只要求登录、不按项目成员过滤（§11.3），但暴露对象是公式治理元数据（公式位、定义、项目 UUID、候选备注），不含业务数值或客户资料，且真库 0 行；与 P0-5 同批修复（R4）。若备注被用来记录客户信息，或拍板视为项目敏感信息，按 P0 处理。合并附注全局层允许 partner/manager 写（P2-1）是否越权取决于 §10 拍板，拍板前按权限一致性列 P2。

7. **试算平衡表手工值读不回与公式模块的假保存（P2-3）不属 P0**（R3-05）：① 针对平台产出或交付错误业务数值。试算平衡表重载后显示的是平台按试算表现算的值，断开标记一并消失，页面状态与该行从未断开时一致——这不是错算出的数，丢的是用户的手工覆盖；没有公式的行重载后为空白，用户看得见；保存值只被高级查询 `_query_tb_summary` 读取（读的是库里保存值），报表、附注、底稿与交付件都不读这张表（§11.3 第 20 条）⇒ 后果是用户输入读不回，属产品闭环缺陷。公式历史回滚、保存全部与新增报表行被服务端拒绝时什么都没写，界面误报成功，没有错误数值被产出，也不是 ② 所说的“权威写方被绕过”。两者现网暴露都为 0，但定级依据是影响的性质而不是暴露面（P0-1 同样暴露 0，仍为 P0）；P 级与计分脱钩，落在检查项主路径上的假成功照样按规则（1）封顶该项（第 16、20 项）。升级条件见 §6.6：试算平衡表导出被用作交付件，或出现把保存值当权威数的下游。

## 8. 目标统一架构

| 层 | 唯一职责/来源 | 现有能力处理 |
|---|---|---|
| Definition Repository | 不可变版本定义：domain/slot/scope/expression/disabled/owner/approval/base/version；物理可分表，只能经统一 Repository/Effective API | 保留强化 V199；封装 report/wp/consol 特殊表，禁止旁路写（含 `report_config` 迁移与 `fill_all_formulas` 路径） |
| Typed Resolver | ACNR `addr_id` 为稳定身份；统一 TB/ROW/REPORT/NOTE/WP/AUX/PREV/ADJ，返回 value/missing/error/source metadata；TB 一律叶子聚合 | 保留 TrialBalanceResolver、strict preload、ACNR；V1/V2/V199 dependency 转派生视图 |
| Execution Contract | 单 parser/grammar/arity/registry/status/Decimal/预算；预览与写入消费同一次 evaluation result | 合并 L1/report/strict WP/note/cell 公共语义；Runtime 修复前禁止写 |
| Check Contract | 类别（取数/逻辑/提示）与严重度（阻断/警告/提示）两维分离；缺数=未执行，不得记通过；校对类永不回写；结论落库，目录与执行同源 | 收敛门禁、QC、XR、附注校验、表间审核与报表审核；附注预置自然语言规则转写或下线 |
| Authority Writer | 每个 `domain+target+field` 唯一写方；统一 CAS、人工覆盖、locked、审计和 stale | 保留 push 四阶段/report fail-visible；裁定 note builder/push ownership |
| Durable Propagation | 定义与 outbox 同事务；按 definition version/run id 幂等，状态 pending/running/succeeded/blocked/failed；并发上限与分批 | EventBus/SSE 只通知；退役 marker-only 成功；“标过期”入发布事务 |
| Lineage Read Model | 持久化 formula_version/evaluated_at/run_id/writer/inputs/steps/manual_override/error | 合并 trace、refs、push state、source_accounts、audit；最终值直接读取 |

统一治理动作：`validate → preview values+impact → permission/approval → CAS publish → conflict → authority writer/outbox → evaluation result → stale transition → audit+provenance → rollback as new version`。

**保留：**V199、TrialBalanceResolver、strict preload、ACNR、push 四阶段、report fail-visible、EventBus/SSE 通知。  
**合并：**多套 grammar、resolver、status、校对执行器和 lineage。  
**冻结后改造：**Formula Runtime mutation apply。  
**退役候选：**常量 wired、marker-only 成功、客户端任意 rollback target、无 handler 假入口、无明确客户需求的伪全局 custom function API、只写不读的报表 Redis 缓存（`get_report_cached` 零调用方）。

设计依据：`[A] §二~六、§八`；`[C] §3、§6、§10`；`[D] §2~3、§6`；`[M] §六~七`；`[N] §1`。

## 10. 需要用户拍板的清单

P0 定义已按复核收窄（§6.1），不再列为待决。

| 决策 | 推荐 | 替代方案与 trade-off |
|---|---|---|
| 冲突默认行为 | 默认 ask+保留本地；旧 revision 禁采用；inherit/follow 可自动 | 自动 adopt 操作少但可能覆盖项目判断；默认 keep 更安全但积累漂移 |
| 预设停用语义 | `{disabled:true}` tombstone；空值仅未定义/回退；记录原因版本 | 清空即停用直观但无法区分删除、回退、禁用 |

| Runtime 冻结方式 | 服务端直接拒绝（可被测试证伪） | feature flag 默认关，回退方便但易被误开 |

## 12. 最终结论

公式管理确实具备成为平台“灵魂”的基础：V199 治理、模板订阅/冲突、严格取数部件、Formula Push、CAS 与局部审计能力值得保留。但当前**结构/证据分 36/100（1.8/5），风险调整后为“集成原型级”**：错误 Runtime 与 Draft Refresh 未冻结，跨项目隔离、业务回滚与登录态写入 UAT 均未证实。当前优先事项不是继续增加函数、规则、模板和入口，而是冻结已知错写路径，修复跨项目隔离与陈旧冲突决策，统一求值/失败语义，建立唯一写方、durable propagation、可执行的校对合同和逐值 provenance。

只有以下条件全部可复验，才可对外称为“单一公式中枢”：

1. 同式在 TB、报表、附注、底稿、推送的预览与实际写入得到相同数值和状态，并由独立权威输入/人工金标准证明会计正确；
2. 缺引用、除零、循环、参数个数不符和未知函数不会冒充 0/成功，也不会写入；
3. 全局/模板变更可靠传播，冲突有 revision 保护，失败可恢复；
4. 每个最终值可追到版本化公式、实际输入、步骤、writer、时间与人工覆盖；
5. 模板在真实 PG 双项目完成发布、订阅、升级、冲突、adopt/keep/custom、重算与回滚发版；
6. 校对与提示规则区分类别和严重度，缺数不记通过、校对类不改值、结论落库，目录与执行同源；
7. 测试以生产函数、真实 PG shape、逐值断言和真实宿主为准，而非文件、组件、Mock 或路由存在。

在此之前，对外最准确的表述是：**“平台已有统一公式治理框架和若干已运行的局部链路，但尚未完成全域统一执行、可靠传播、可执行校对与逐值溯源。”**【综合 `[A] §八~九`、`[C] §12、§17`、`[D] §六`、`[V] §0、§5`、`[M] §一、§七`】
