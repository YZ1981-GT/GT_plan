# S-cycle P0: applicable_when generation chain, orphan component wiring, sidebar routing

Implementation covers the full P0 vertical slice from `match_workpapers` 4th path through `chain_orchestrator` flag construction, `_WP_APPLICABLE_WHEN` loading with bundle parent aggregation, render-config injection, frontend `ipoProjectUtils.ts` convergence, GtWpRenderer overlay, s-checklist component wiring (12 types), and S-segment sidebar routing. The code closely follows design §1.1–§1.6 across 27 changed files.

**Watch for:** GtWpRenderer's `isWpNotApplicable` reads `renderConfig.value?.project_context?.business_category` but the render-config top-level response has no `project_context` field — `projectBiz` will always be `''`, making the overlay always show for workpapers with `applicable_when` (confirmed). The `_ONLYOFFICE_HTML_WHITELIST` addition of 12 types is a good defensive measure not in the original design but correctly prevents the render pipeline from rewriting these to `onlyoffice-sheet`.

**Verdict**: CHANGES_REQUESTED

## High-level view

The backend generation chain is clean: `match_workpapers` gets a proper 4th elif with OR semantics across dict keys, `chain_orchestrator` loads `Project.business_category` and builds biz_ flags, and `_WP_APPLICABLE_WHEN` correctly aggregates bundle parents S32–S35 from children's business_category union. The render-config endpoint injects `applicable_when` into the response at the right place.

The frontend IPO utility (`ipoProjectUtils.ts`) is well-factored with correct delegation from D4 (preserving `fraud_risk`) and F2 (keeping its three-level cascade wrapper). `useAProgramData` correctly handles both string and dict `applicable_when` by fetching project info separately.

The GtWpRenderer overlay has a data source gap: it reads `project_context.business_category` from a path that doesn't exist in the render-config response, so the overlay will fire on every applicable_when workpaper regardless of project type. This is the only blocking issue.

The s-checklist component wiring (12 types across overrides, registry, and specialized entries) follows established patterns precisely. S17-11/S17-21 correctly remain as `a-program-console`. Group B per-sheet overrides use the `{wp_code}-{tab_name}` format that matches the render-config lookup at line 796.

The S-segment sidebar routing orders long prefixes first (S20 before S17 before S16 before S15... before S1), with S16 and S11 explicitly falling back to `e1a` before S1 can catch them. Test coverage is thorough with 16 new cases.

## GtWpRenderer overlay data source gap

The `isWpNotApplicable` computed reads `(renderConfig.value as any)?.project_context?.business_category`. The render-config response (constructed at line 1057 of `wp_render_config.py`) contains `wp_id`, `wp_code`, `project_id`, `scope`, `sheets`, `applicable_when`, etc. — but no `project_context`. That field exists only inside each sheet's `html_data` (set by individual render strategies like `_b1_3_evaluation.py` or `_a177_independence_declaration.py`), and not all strategies provide it.

The fallback `|| ''` means `projectBiz` is always empty string. `isIpoProject('', cats)` returns `false` (the function's first line is `if (!businessCategory) return false`). Then `!false = true`, so the overlay always renders.

By contrast, `useAProgramData.ts` correctly solves this by loading project info from `/api/projects/{id}` and reading `projectInfo.value?.business_category`. GtWpRenderer already imports `useProjectStore` — the simplest fix is to add `business_category` to the render-config top-level response (parallel to `applicable_when`), or read from the project store / a separate API call.

## match_workpapers 4th path

The implementation exactly follows design §1.1. The `for/else` pattern correctly sets `hit = False` when no key matches (the `else` clause of a Python `for` loop runs when the loop completes without `break`). OR semantics across keys, `_KEY_FLAG_PREFIX` mapping, and fallback `f"{key}_"` prefix for unknown keys are all present.

The `_KEY_FLAG_PREFIX` dict is re-created on every call inside the loop body. For the ~60 applicable_when entries this is negligible, but if performance becomes a concern it could be module-level.

## S-segment routing ordering

S16 at position 3 and S11 at position 8 (both returning `e1a`) correctly prevent `startsWith('S1')` at position 11 from capturing them. The test file covers all critical priority cases including S11-1 → e1a (not s1a). S8 placed before S1 is safe since `'S8'.startsWith('S1')` is false, but the explicit ordering makes the intent clear.

## wp_code_overrides Group B key format

The 5 new per-sheet keys (`S1-S1-1对法律法规的考虑记录表`, `S8-审定表S8-1`, `S9-电子商务法律法规`, `S9-程序说明`, `S10-环境法规`) match the render-config lookup pattern `f"{wp_code}-{cls.sheet_name}"` at line 796 of `wp_render_config.py`. Tab names were confirmed via openpyxl per FEAT-002 findings.

## _ONLYOFFICE_HTML_WHITELIST defensive addition

The 12 new componentTypes were added to `_ONLYOFFICE_HTML_WHITELIST` in `wp_render_config.py`. This is not in the design document but is correct: without it, multi-sheet workpapers containing these components would have the S-checklist componentType silently rewritten to `onlyoffice-sheet` by the E-branch logic (line ~799), making the specialized Vue components never render.
