# 代码提交与分支管理规范

> 适用范围：本仓库为**前后端同仓**（前端 Vue3 / Vben / ant-design-vue + 后端服务代码），本规范对前后端同仓库提交与推送统一适用。
> 目标：让分支清晰、提交可追溯、Code Review 高效、发布可控。
> **治理红线：`main` 与 `dev1.0` 作为受保护集成基线，禁止直接开发、提交或推送，所有改动必须通过工作分支 + MR/PR 合入。**
>
> **当前仓库实际执行口径**：分支命名和推送还受 `.git-hooks/pre-push` 与
> `backend/scripts/check/check_git_branch_naming.py` 硬门控制。钩子当前接受
> `main`、`spec/*`、`work/YYYY-MM-DD-*`、`fix/*`、`release/v*`，不接受本文历史版本中的
> `feature/*`、`hotfix/*`。本文件以实际钩子可执行的命名为准。

---

## 一、分支模型

采用「受保护集成基线 + 短生命周期工作分支」模型。当前仓库实际使用的工作分支以 `spec/*` 为主，其他前缀必须满足 pre-push 命名检查。

| 分支 | 命名 | 说明 | 保护级别 |
| --- | --- | --- | --- |
| 生产主干 | `main` | 线上稳定代码，**禁止直接开发** | 受保护（禁止直接 push/commit） |
| 开发基线 | `dev1.0` | 团队约定的集成/提测基线；如远端存在，按受保护分支管理 | 受保护（仅通过 MR/PR 合并） |
| Spec 工作分支 | `spec/<spec-name>` | 对应 `.kiro/specs/<spec-name>/` 的 spec 实施分支 | 普通；必须通过 MR/PR 合入 |
| 单次工作分支 | `work/YYYY-MM-DD-<topic>` | 临时单次工作或验证分支 | 普通 |
| 修复分支 | `fix/<issue>` | 缺陷修复或紧急修复；当前钩子不接受 `hotfix/*` | 普通 |
| 发布分支 | `release/v<version>` | 版本发布准备（冻结功能、只修 bug） | 普通 |

> **`dev1.0` 说明**：它是团队约定的集成基线，不代表每个仓库当前都存在或可由本地直接创建。使用前先确认远端分支和保护规则；若远端实际采用其他集成基线，应以项目保护配置和 MR/PR 目标为准。当前 pre-push 钩子只对 `main` 做主干直推策略检查，`dev1.0` 的保护仍需要远端分支保护和 Code Review 流程保证。

```
main ──────●──────────────────●──────────►
            \                /  release/fix
集成基线 ─●──●──●──●──●──●──●──►
           \  /  \  /
        spec  work  fix
```

1. **工作分支从团队指定的集成基线创建**；当前团队若使用 `dev1.0`，从 `dev1.0` 创建，线上紧急修复从 `main` 创建 `fix/*`。绝不在 `main`、`dev1.0` 上直接写代码。
2. `spec/<spec-name>` 必须对应活跃或归档的 `.kiro/specs/<spec-name>/`，且 `<spec-name>` 只能使用小写字母、数字和连字符。
3. `work/YYYY-MM-DD-<topic>` 用于一次性工作或验证；`fix/<issue>` 用于缺陷修复；`release/v<version>` 用于发布候选。
4. 分支保持**短命**：功能合入后立即删除，避免长期游离分支。
5. 合并目标：`spec/*`、`work/*`、`fix/*` → 团队指定的集成基线；`release/*` → `main`，并按发布流程同步回集成基线。

## 二、分支命名规范

- 分支名必须匹配 pre-push 钩子实际接受的五类前缀：`main`、`spec/`、`work/`、`fix/`、`release/`。
- `spec/<spec-name>`：小写字母、数字、连字符组成，并且必须对应 `.kiro/specs/<spec-name>/` 的活跃或归档目录。
- `work/YYYY-MM-DD-<topic>`：日期必须为 `YYYY-MM-DD`，主题使用小写字母、数字和连字符。
- `fix/<issue>`：用于普通缺陷和紧急修复；本仓钩子**不接受** `hotfix/*`。
- `release/v<version>`：版本格式为 `release/v1.2`、`release/v1.2.3`，可带小写预发布后缀。
- 后缀语义清晰，能看出做了什么，避免 `spec/new`、`fix/bug` 这类无效命名。
- 前端/后端职责通过提交 scope 区分，不再在分支名中增加未被钩子识别的 `web-` / `server-` 前缀约定。

| 反例 | 正例 |
| --- | --- |
| `feature/test` | `spec/note-disclosure-pull-regression` |
| `hotfix/bug1` | `fix/bug1` |
| `work/topic` | `work/2026-11-02-formula-review` |
| `release/1.0.0` | `release/v1.0.0` |
| `dev2` / `main-tmp` | 禁止在 `main`、`dev1.0` 派生临时分支直接改 |

## 三、提交信息规范（Conventional Commits）

提交信息统一格式：

```
<type>(<scope>): <subject>

<body 可选>

<footer 可选>
```

- `type`：**英文小写**，便于工具解析（见下表）。
- `scope`：**可选但推荐**，用于标明模块；**前后端同仓时用端前缀区分**，如 `web-user`、`server-order`、`api-auth`。
- `subject`：简洁描述**做了什么**，不超过 50 字，结尾**不加句号**，用祈使句（“新增”而非“新增了”）。
- 中英文混排允许：type 用英文，描述可用中文。

### type 取值表

| type | 含义 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat(web-user): 新增用户列表分页` |
| `fix` | 缺陷修复 | `fix(server-order): 修复并发下单超卖` |
| `docs` | 文档变更 | `docs: 更新接口说明` |
| `style` | 代码格式（不影响逻辑） | `style: 统一缩进为 2 空格` |
| `refactor` | 重构（非新功能非修复） | `refactor(api-auth): 抽离鉴权中间件` |
| `perf` | 性能优化 | `perf(web-list): 减少重渲染次数` |
| `test` | 测试相关 | `test(order): 补充下单用例` |
| `chore` | 构建/依赖/杂项 | `chore: 升级 vite 到 5.x` |
| `build` | 构建系统或外部依赖 | `build: 调整分包策略` |
| `ci` | CI 配置 | `ci: 增加 lint 校验步骤` |
| `revert` | 回滚提交 | `revert: 撤销 feat(web-table) 改动` |

### 反例 vs 正例

| 反例 | 正例 |
| --- | --- |
| `修改了一下` | `fix(web-form): 修复必填项校验失效` |
| `update` | `feat(server-auth): 支持短信验证码登录` |
| 在 `main`/`dev1.0` 直接提交 | 先在 `spec/*`、`work/*` 或 `fix/*` 工作分支提交，再提 MR/PR 合入 |

## 四、前后端同仓特别约定

1. **目录边界清晰**：前端代码放前端目录（如 `web/` 或 `src/` 前端区），后端代码放后端目录（如 `server/`），提交尽量按端隔离，减少跨端耦合改动混在同一 commit。
2. **scope 标端**：提交信息 scope 带 `web-` / `server-` / `api-` 前缀，一眼区分改动归属（见第三节示例）。
3. **跨端改动**：若一次需求必须前后端同改，拆成“前端 commit + 后端 commit”分别标注，便于 review 与回滚；确需一起上线的在 MR 描述中注明依赖关系。
4. **共用配置**：根目录的构建/CI/依赖配置变更用 `build` / `ci` / `chore`，scope 可写 `root`。

---

## 五、提交原则

1. **原子提交**：一次提交只做一件事，方便回滚与 review。不要“顺手”把无关改动塞进同一个 commit。
2. **不提交半成品**：未通过本地 lint / 类型检查 / 单测的代码不要提交。
3. **不提交敏感信息**：密钥、token、`.env`、凭据一律忽略（已在 `.gitignore`）。
4. **不提交大文件**：构建产物、node_modules、日志不入库。
5. **先拉后提**：提交前 `git pull --rebase`，减少无意义的 merge commit。
6. **禁止 `--no-verify` 强行绕过钩子**（除非你明确知道在做什么且事后补跑）。

---

## 六、合并与 Code Review 规范

1. 合并统一走 **Merge Request（GitLab）/ Pull Request（GitHub）**，禁止直接 push 到 `main` / `dev1.0`。
2. MR 标题沿用提交规范格式；描述写明**背景、改动点、自测情况、影响范围**（跨端改动注明依赖）。
3. 至少一个 reviewer 批准（核心模块建议两人）；reviewer 需关注逻辑、边界、性能、安全与规范符合度。
4. 合并方式：`spec/*`、`work/*`、`fix/*` 通过 MR/PR 合入集成基线；`release/*` 合入 `main` 时使用发布流程保留合并节点。
5. 合并后删除源分支（仓库设置开启“delete branch after merge”）。
6. **合入 `main` 的 `release/*` 必须按发布流程同步回集成基线**，避免主干与开发基线漂移。

## 七、配套工具与当前实现

仓库当前使用 `.git-hooks/install.ps1` 安装自维护的 `pre-commit`、`pre-push` 和 `push_version.py`。
它们负责暂存区安全检查、文件行数/编码门禁、工作树完整性、分支命名、暂存树自洽和版本标签推送。
下列工具属于后续可选增强，不得在尚未接入前写成“已启用”:

- **husky**：git hooks 管理（pre-commit / commit-msg）。
- **commitlint** + `@commitlint/config-conventional`：校验提交信息格式。
- **lint-staged**：只对暂存文件跑 lint / format，提速。
- **eslint / prettier / stylelint**（前端）+ 后端对应 linter（如 golangci-lint / pylint / checkstyle 等）。

示例 `commitlint.config.js`：

```js
module.exports = {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [2, 'always', [
      'feat', 'fix', 'docs', 'style', 'refactor',
      'perf', 'test', 'chore', 'build', 'ci', 'revert',
    ]],
    'subject-full-stop': [2, 'never'],
    'subject-case': [0],
  },
};
```

`package.json` 片段（前端侧）：

```json
{
  "scripts": {
    "prepare": "husky install"
  },
  "lint-staged": {
    "*.{js,ts,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,less,scss}": ["stylelint --fix", "prettier --write"]
  }
}
```

## 八、本仓当前已启用的 Git 钩子与推送硬门

以下是仓库当前实际运行的自动检查，规范条款与它们冲突时，先修订本文或钩子，不要长期保留两套口径：

- `.git-hooks/pre-commit`：检查暂存区密钥泄漏、触碰文件的行数门禁和 `.vue` / `.ts` / `.py` 的 UTF-8 完整性；文件已安装到 `.git/hooks/` 后才会生效。
- `.git-hooks/pre-push`：要求推送前工作树完全干净，检查分支命名，并运行暂存树自洽检查。`GIT_MODE=multi` 时还会严格执行 PR/同步检查；默认 `single` 模式对部分同步检查只告警。
- `commit-msg` / `commitlint` 当前不是已安装的硬门。提交信息仍必须遵守本规范的 Conventional Commits 格式，后续接入 commitlint 时以本节 type 列表为准。
- 安装或更新钩子：

```powershell
powershell -ExecutionPolicy Bypass -File .git-hooks/install.ps1
```

### 推送版本标签硬门

推送包含远端尚不存在的新提交时，必须用 `push_version.py` 推送，不能直接用普通 `git push`：

```powershell
python .git-hooks/push_version.py push -c "主要变动一" -c "主要变动二"
```

该工具会先 fetch 远端、检查分支是否有分叉，生成递增的附注标签 `vX.Y.Z`，并在标签说明中写入“主要变动：”和自上个版本以来的提交清单，最后用 `git push --atomic` 同时推送分支和标签。先预览可使用：

```powershell
python .git-hooks/push_version.py push --dry-run -c "主要变动一"
```

分离头 worktree 推送到指定远端分支时必须显式传入分支名：

```powershell
python .git-hooks/push_version.py push --branch spec/<spec-name> -c "主要变动一"
```

不应使用 `git push --no-verify` 绕过版本、工作树和暂存树硬门；若确有紧急情况，必须补跑被跳过的检查并记录原因。

## 九、禁止事项（红线）

- ❌ **在 `main` 上直接开发、commit、push。**
- ❌ **在 `dev1.0` 上直接开发、commit、push。**
- ❌ 使用钩子不接受的 `feature/*`、`hotfix/*`、`master`、`dev2`、`tmp` 等分支名。
- ❌ `spec/<spec-name>` 不对应 `.kiro/specs/<spec-name>/` 就直接使用。
- ❌ 提交信息写 `update` / `fix` / `asdf` 等无意义内容。
- ❌ 一个 commit 塞入多模块、多需求的大杂烩。
- ❌ 把密钥、node_modules、构建产物入库。
- ❌ 用 `--no-verify` 绕过提交或推送校验。
- ❌ 推送新提交却不使用 `push_version.py` 创建递增的附注版本标签。
- ❌ 合入 `main` 的发布分支不按发布流程同步回集成基线。

## 十、快速检查清单

合并前自问：

- [ ] 我没有在 `main` / `dev1.0` 上直接提交？（改动都在 `spec/*`、`work/*` 或 `fix/*` 工作分支）
- [ ] 分支名通过 `check_git_branch_naming.py`，且 `spec/*` 对应真实 spec 目录？
- [ ] 每个 commit message 都是 `type(scope): subject` 且能看懂？
- [ ] 提交是原子的、自测通过的？
- [ ] 没有敏感信息 / 大文件入库？
- [ ] 跨端改动已拆分或注明依赖？
- [ ] MR/PR 描述写清背景、改动、自测、影响？
- [ ] 推送新提交前已用 `push_version.py` 生成递增附注标签？
- [ ] pre-commit / pre-push 已安装且没有使用 `--no-verify`？
- [ ] 已指定 reviewer，且 `main` 相关改动按流程同步回集成基线？
