# 后端冷启动、热重载与每请求固定开销 — 需求

承接 `platform-perf-hotspots` 任务 12 的后续建议（用户 2026-10-28「之后继续修复解决…立 spec 处理」）。

## 现状（2026-10-28 实测，口径见 design §1）

- 导入 `app.main` 9.9~11.6 s。其中 `APIRoute.__init__` 构造 5131 次、5.92 s（51%）：2550 条路由各构造两次（子路由装饰时一次，`include_router` 又整套重算一次依赖分析 / 参数模型）；`stale_propagation_engine` 导入时读图 0.76 s。第三方库合计约 2 s。
- 热重载：uvicorn 先让旧 worker 退出，再起新 worker 导入、启动，期间约 15 s 新请求卡在监听队列里。
- 每请求（进程内，不经网络）：8 个 `BaseHTTPMiddleware` 合计约 0.65 ms（`/api/version` 0.79 ms，去掉后 0.14 ms）；路由表线性匹配，排在第 2419 条的未读数要 0.78 ms；30 个未读数并发一批 77 ms，即每个约 2.6 ms 的事件循环时间，请求在同一个事件循环上排队。

## R1 冷启动导入

1. 导入 `app.main` 的中位耗时下降 ≥ 45%（同机、同一时段交替测量各 3 次）。
2. 路由的依赖分析、参数 / 响应模型、请求处理函数推迟到第一次用到时再算。物化后的路由与立即构造的完全等价：属性集合相同，OpenAPI 文档逐字节相同，请求结果相同。FastAPI 版本不在已验证列表里时退回立即构造，并在日志里告警。
3. 路由定义错误仍会暴露：测试会物化全部路由；运行时启动后在后台低强度逐条物化，失败写进 `/api/health` 的启动报告和错误日志。
4. 导入时的重计算（不属于路由定义、单个模块自耗时超过 100 ms 的）改成第一次使用时计算。

## R2 热重载不中断

1. 检测到改动后，旧 worker 继续服务；新 worker 启动完成（能接请求）后才让旧 worker 退出。重载期间每 0.5 s 轮询 `/api/version`，不出现连接失败，也不出现超过 3 s 的响应。
2. 新 worker 起不来（导入或启动报错）时，旧 worker 继续服务，控制台告警；`/api/health` 显示最近一次重载的结果与原因摘要。下一次改动再重试。
3. 只能有一个进程做的事（14 个后台 worker；启动事件重放、AI 对话中断恢复、ACNR 快照 GC、失效 outbox 分发），在新 worker 里等旧 worker 退出后才开始。首次启动、不带 `--reload` 运行时，行为与现在相同。
4. 旧 worker 退出时，先给 SSE 连接发 `server_draining` 并关闭（客户端重连到新 worker），再优雅关闭；超过时限（默认 30 s）强制结束。
5. Ctrl+C 或关闭窗口时，新旧 worker 都退出，不残留进程。
6. 开关：`GT_NEVER_PRIMARY=1` 时上述「只能一个进程做的事」永不执行，供另起实例做测量，不和主实例抢后台任务。`GT_OVERLAP_RELOAD=0` 时退回 uvicorn 原来的重载方式。

## R3 每请求固定开销

1. 8 个 `BaseHTTPMiddleware` 改成纯 ASGI 中间件，行为不变：状态码、响应头、响应体、审计日志写入、request_id 上下文、限流 429、请求体上限 413、慢请求日志。`/api/version` 进程内单次 ≤ 0.25 ms。
2. 路由匹配按路径的字面前缀建索引，匹配结果与线性扫描完全相同（含 405、尾斜杠重定向、404、Mount）。路由表任何位置的路由匹配耗时 ≤ 0.05 ms。路由表在运行中被改动后索引自动重建。
3. 30 个未读数并发一批的耗时下降 ≥ 30%。
4. 不改成多 worker 进程（原因见 design §5）。

## 验收

- 每项改动有判据测试，并做磁盘变异确认判据会红。
- 相关测试在干净检出下失败集合不增加。
- 前后对照用同一口径测量，结果写回 tasks.md。
