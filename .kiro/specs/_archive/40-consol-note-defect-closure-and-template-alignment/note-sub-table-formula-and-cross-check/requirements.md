# 附注子表公式与跨表勾稽 — 需求文档

## 背景

当前附注公式管理三层机制（种子层 / formula_push 层 / 前端同步层）只覆盖各科目的**主表**（第一张表的期末/期初 = 报表行审定数）。子表（坏账分类表、账龄表、变动表、单项计提明细等）**在三层中全部为空**——没有公式种子、没有推送规则、部分科目甚至没有前端同步路径。

以应收账款 E5 为代表：11 张子表（五-5-1 到 五-5-11），三层全空，数据完全靠人工填入。但这些子表之间存在严格的勾稽关系（如账龄合计 = 坏账分类合计），当前无任何自动校验。

## 当前覆盖现状（2026-10-09 实测）

| 层 | 机制 | 覆盖 |
|---|------|------|
| 种子层 `plan_seed` | 主表合计→报表行 + 行级科目码 | soe 51/292 五-表、listed 39/291 五-表 |
| formula_push note 阶段 | 79 条规则，推主表期末/期初 | E1/D1-7/F1-4/G1-14/H1-10/I1-6/J1-2/K1-13/L1-7/M/N |
| 前端 buildXSyncPayload | 各披露 Tab 的保存后同步 | 有披露 Tab 的底稿 |
| **子表** | **零覆盖** | **E5 等科目的全部子表** |

## 子表公式的三类需求

### R1. 表内合计勾稽
每张子表的合计行 = 数据行之和。engine 的 `_push_note_total` 已实现此逻辑，但只在有 note 推送规则的表上执行。

**需求**：扩展合计重算到所有有合计行的子表，不依赖 formula_push 规则的存在。

### R2. 跨子表校验
同一科目的子表之间存在严格勾稽关系。以应收账款为例：

| 校验 | 来源表 | 来源行/列 | 目标表 | 目标行/列 | 关系 |
|------|--------|----------|--------|----------|------|
| F4-8 | 五-5-1 账龄 | 合计.账面余额 | 五-5-2 坏账分类 | 合计.账面余额 | = |
| F4-9 | 五-5-1 账龄 | 合计.坏账准备 | 五-5-2 坏账分类 | 合计.坏账准备 | = |
| F4-4 | 五-5-3 单项明细 | 合计 | 五-5-2 坏账分类 | 按单项计提行 | = |
| F4-5 | 五-5-4~8 组合明细 | 各合计 | 五-5-2 坏账分类 | 按组合计提行 | = |
| F4-3a | 五-5-2 坏账分类 | 各行.账面余额−坏账准备 | 五-5-2 同行 | 账面价值 | = |

这类关系目前只在单体模板的 `guidance` 字段中以中文描述，没有结构化声明。

**需求**：在合并模板 JSON 中增加 `check_rules` 声明，并提供后端校验 + 前端展示。

### R3. 子表取数公式
子表的数据来自**底稿披露表**——底稿中每个科目的审定表/披露表已包含全部子表（如 E5 底稿含账龄表、坏账分类表、单项计提表等），通过 `wp_disclosure_sync_service.sync_from_workpaper` 的 `sub_table_data` 浅合并机制同步到附注。

**现状**：
- 有前端 Tab 的底稿（如 E1）：前端保存后 `buildXSyncPayload` 构建子表载荷 → `syncToDisclosureNotes` → 后端 `sync_from_workpaper` 写入附注
- formula_push 的 note 规则也调用 `sync_from_workpaper`（或直接定位子表写入）
- **问题不在于数据没有同步路径，而在于**：① 部分科目（如 E5）没有 note 规则，formula_push 引擎不会主动推子表 ② 子表间的勾稽关系没有结构化声明和自动校验

**需求**：
- 在 `formula_push_rules.json` 中给缺失科目（E5 等）增加子表级 note 规则，使引擎能自动推送子表数据到附注
- 确保子表数据通过既有 `sync_from_workpaper` 路径落库，不另建写入方

### R4. E5 应收账款作为 canary
E5 是最复杂的科目（11 张子表、3 级表头、跨表勾稽最多），优先做完 E5 可以验证机制。

**需求**：
- E5 的全部 11 张子表都有表内合计
- E5 的跨表勾稽至少覆盖 F4-3a/F4-4/F4-5/F4-8/F4-9
- E5 底稿披露表中的子表数据能通过 formula_push 的 note 规则自动推送到附注（走既有 sync_from_workpaper 路径）

### R5. 勾稽声明格式
合并模板 JSON 中子表之间的勾稽用结构化格式声明：

```json
{
  "check_rules": [
    {
      "check_id": "F4-8",
      "source": {"section_id": "五-5-1", "row": "合计", "col": "账面余额"},
      "target": {"section_id": "五-5-2", "row": "合计", "col": "账面余额"},
      "relation": "equal",
      "description": "账龄表合计账面余额 = 坏账分类表合计账面余额"
    }
  ]
}
```

### R6. 不改已有机制
- 不改 formula_push engine 的写入逻辑（只加规则）
- 不改 plan_seed 的主表种子逻辑（只扩展子表支持）
- 不改前端 useDisclosureAutoSync 机制（只加新的 Tab 接入）
- 校验结果只读展示，不自动覆盖

## 排除项
- 不做全科目子表公式（本 spec 只做 E5 canary + 机制基础）
- 不改合并计算引擎（consol_calc_basis）
- 不处理合并差额表级的子表（合并附注差额由 `_refresh_notes` 处理）
