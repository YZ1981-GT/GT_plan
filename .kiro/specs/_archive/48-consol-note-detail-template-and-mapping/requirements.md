# 合并附注明细模板与多企业行映射规则 — 需求

日期：2026-10-13。来源：用户提出的合并附注披露明细转换规则需求。

## 背景

合并附注每张科目明细表（如管理费用、应收账款账龄等）的二级明细行需要由用户根据合并企业实际情况自定义。当前平台从子公司单体附注汇总时，仅靠行标签模糊匹配（`fuzzy_merge_same_label`，阈值 0.85）自动聚合，没有用户可审核、可版本化、可复用的转换规则。当下属企业的明细行名称发生变化时，系统无感知，金额可能静默归入错误目标行或丢失。

本 spec 建立：可复用的合并附注明细模板 → 多企业批量行映射规则 → 来源变更自动失效与重新确认的完整机制。

## 边界

1. 本 spec 的**目标章节范围**是合并附注中包含二级明细行的科目表（如管理费用、销售费用、财务费用、应收账款前五名、存货分类等），不改变合并专用 7 章节（合并范围/商誉/少数股东等）的生成逻辑。
2. **"按公式填入"**（`fill_by_formula`）走合并报表/TB 公式取数的路径不变，与本 spec 的"从下属企业附注刷新明细"是两个独立动作。
3. 复用现有 `consol_note_data` 持久化层（JSONB rows），不另建渲染表；映射结果最终写入 `consol_note_data.data.rows`。
4. 复用现有合并锁定（`check_consol_lock`）、`manual_cells`、`cell_state=locked`、`locked_cells` 保护机制。
5. 复用现有企业树（`consol_tree_service.build_tree` + `data_leaves`）获取下属企业清单。
6. 不改单体附注 `disclosure_notes` 的写入方；只读取其 `table_data.rows`。
7. 不处理"一条来源行拆分到多个目标行"（需金额分摊规则，风险高，留后续）。
8. 隔离测试使用 SQLite + 合成数据；真实 PG 写路径须另行授权。

## R1 合并附注明细模板

### R1.1 模板建议

1. 系统扫描当前合并范围内所有数据叶子企业的单体附注，提取指定章节的明细行标签。
2. 按标签出现频率、金额占比和模糊相似度（复用 `fuzzy_merge_same_label`）生成建议模板行列表。
3. 建议结果仅作为参考展示，不得未经用户确认写入任何持久化数据。

### R1.2 模板结构

1. 每个目标明细行必须有不可变的 `target_row_id`（UUID），不以显示名称或行号作为身份。
2. 每行包含：`target_row_id`、`canonical_name`（规范名称）、`aliases`（别名列表）、`sort_order`、`row_type`（data / total / subtotal）。
3. 模板按 `(template_type, section_id)` 维度组织，`template_type` 为 `soe` 或 `listed`。

### R1.3 版本与共享

1. 模板采用不可变版本；修改时创建新版本，旧版本保留可回滚。
2. 版本号递增（`v1`、`v2`……），每个版本记录创建人、创建时间和变更说明。
3. 模板可见范围分三级：个人草稿 → 当前项目 → 事务所共享。
4. 项目绑定的是一个**确定版本**；其他成员在同一项目内看到的是同一份版本。
5. 项目内切换版本需要二次确认，并提示影响的章节数和已有映射规则数。
6. 跨项目引用时复制为项目本地版本；源版本后续变化不影响已引用的项目。

### R1.4 模板编辑

1. 新增行、删除行、修改行名、调整排序均通过模板编辑器操作。
2. 删除已被映射规则引用的目标行时，必须提示受影响的规则数和企业数，并要求用户选择替代目标行或确认删除。
3. 合并附注表格第一列（行名）的直接编辑不再改变模板身份；行名仅作显示，身份由 `target_row_id` 承载。

## R2 多企业行映射规则

### R2.1 来源结构指纹

1. 读取每个数据叶子企业对应章节的 `disclosure_notes.table_data.rows`，提取每行的标签（`label` / `rows[i][0]`）、行类型和稳定行键（如有 `row_id` / `item_id`）。
2. 对提取结果计算结构指纹（`source_structure_hash`），指纹排除金额值，包含：来源 `section_id`、行名列表、行类型列表、稳定行键列表（无稳定键时用"名称+重复序号"生成伪键）。
3. 相同指纹的多个企业归为一组，一次维护映射后批量绑定。

### R2.2 映射操作

1. 每条映射记录：`source_label`（来源原始行名）→ `target_row_id`（目标模板行 UUID）+ `mapping_action`。
2. `mapping_action` 枚举：
   - `map`：映射到已有目标行；
   - `map_merge`：多个来源行汇总到同一目标行（金额求和）；
   - `create`：新增为合并模板明细行（自动在模板中追加）；
   - `ignore`：忽略，不参与合并（必须填写 `ignore_reason`）。
3. 多个来源行可以映射到同一个目标行（N:1），金额按 `simple_sum` 求和。
4. 禁止一条来源行映射到多个目标行（1:N 拆分），本 spec 不实现。

### R2.3 批量确认

1. 用户可以在一个弹窗中查看所有待映射的来源行，按"来源结构分组"展示，不逐企业重复。
2. 同一组内的映射确认一次后，该组内所有企业自动绑定该版本规则。
3. 用户可展开组查看各企业金额明细和来源行内容。
4. 用户可单独排除某家企业不适用当前组的规则。
5. 确认时系统自动建议映射（基于别名列表和模糊匹配），用户可接受、修改或拒绝每条建议。

### R2.4 规则持久化

1. 映射规则按 `(project_id, section_id, template_version_id, source_structure_hash)` 唯一约束。
2. 规则包含版本号；编辑规则时创建新版本，不覆盖旧版本。
3. 规则记录确认人（`confirmed_by`）、确认时间（`confirmed_at`）和变更说明。
4. 删除规则为停用（`is_active = false`），不物理删除。

## R3 来源变更识别与重新确认

### R3.1 变更检测

1. 每次刷新前，系统重新读取各企业来源章节的当前结构，计算新指纹。
2. 与绑定记录中保存的 `bound_source_hash` 比较。
3. 指纹不一致时，该企业的绑定进入 `stale` 状态，后续刷新不得使用该规则。

### R3.2 触发重新确认的变更类型

| 变更类型 | 是否重新确认 |
|---|---|
| 金额变化 | 否 |
| 行顺序变化（有稳定行键） | 否 |
| 新增明细行 | 是 |
| 删除明细行 | 是 |
| 明细行名称变化 | 是 |
| 来源章节或模板变化 | 是 |
| 合并目标模板版本变化 | 是 |

### R3.3 变更提示

1. `stale` 的企业在刷新预览中明确标出，提示变更内容（哪些行新增/删除/改名）。
2. 系统预选基于别名和历史规则的建议映射，但不得自动确认。
3. 用户必须逐条确认或批量确认后，绑定才恢复为 `confirmed`。

## R4 刷新流程

### R4.1 三阶段

1. **预览**（`preview`）：读取来源数据和当前规则，生成预览结果但不写数据。返回：已匹配行及金额、待确认行、`stale` 企业、建议映射。
2. **确认映射**（`confirm_mapping`）：用户在弹窗中完成映射后提交。后端校验 `template_version_id` 和 `source_structure_hash` 未变化，否则返回 `409 Conflict` 要求重新预览。
3. **应用**（`apply`）：按已确认规则将转换后的金额写入 `consol_note_data.data.rows`。

### R4.2 并发安全

1. `confirm_mapping` 和 `apply` 均在 `check_consol_lock` 保护下执行。
2. `apply` 携带 `preview_token`（预览时生成的一次性令牌），后端校验令牌有效且来源数据未变化。
3. 过期令牌（来源数据已变化）返回 `409`，前端提示"来源数据已更新，请重新预览"。

### R4.3 阻断规则

1. 存在未处理行（未映射 + 非 `ignore`）时，该章节的刷新被阻断，不生成缺企业金额的"半张表"。
2. 存在 `stale` 绑定的企业时，该企业的数据不参与本次汇总，但不阻断其他企业。
3. 已确认且来源未变化的企业，其金额直接参与汇总。

### R4.4 手工保护

1. `manual_cells` 标记的单元格在 apply 时保留原值，不被刷新覆盖。
2. `cell_state=locked` 的整节跳过，返回 `skipped_locked`。
3. `locked_cells` 中的坐标不被覆盖。

## R5 规则管理与防误操作

### R5.1 规则中心

1. 提供独立的"转换规则"管理入口（合并附注工具栏或设置页）。
2. 展示当前项目所有章节的规则状态：已确认 / `stale` / 无规则。
3. 支持按章节筛选和按企业筛选。

### R5.2 二次编辑

1. 编辑已确认规则时生成新版本草稿，显示新旧差异。
2. 显示受影响的企业数和章节数。
3. 用户确认后发布新版本；发布后旧版本转为历史记录。
4. 新版本在下一次刷新时才生效，不自动重算已保存的合并附注数据。

### R5.3 二次确认操作

以下操作需弹出确认对话框：
1. 修改已使用的映射目标行。
2. 删除模板明细行。
3. 批量切换企业使用的规则。
4. 覆盖手工填写金额。
5. 切换项目绑定的模板版本。
6. 停用映射规则。

### R5.4 审计追溯

1. 每次 `apply` 保存来源级穿透：哪家企业 → 哪条来源行 → 映射到哪个目标行 → 贡献多少金额。
2. 穿透数据与现有 `consolidation_breakdown` 格式兼容，支持在附注差额弹窗中展示。
3. 规则版本历史可查询。

## R6 勘误

1. **ADR-017 勘误**：`fuzzy_merge_same_label` 仅用于建议映射的候选排序，不得作为未经确认的权威映射依据。合并附注的行级汇总必须经过本 spec 定义的"人工确认 → 规则持久化 → 版本绑定"流程。
2. 现有 `consol_note_aggregation_service.aggregate_section` 的模糊合并路径保留为"无规则时的降级建议"，但其输出不得直接写入 `consol_note_data`。
