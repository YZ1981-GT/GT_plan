# 需求文档：公式治理全覆盖收口（formula-governance-coverage-closure）

> 来源：2026-10-22 公式管理全面评估，用户答复「按建议来」。七条建议逐条落地。
> 现状核验见 design §1（每条带文件与行号）。计数都是 2026-10-22 现算快照，**禁止写进判据**，实施时重算。

## 背景

公式治理内核（四层有效定义 / 三方比对同步 / 待确认 / 模板订阅）已建成且六域接入，但：

1. 真库可治理层几乎空跑：`formula_setting` 0 行、`formula_template` 0 行、`formula_publish` 0 行；
2. 真正驱动底稿 → 附注贯通的 420 条公式推送规则写死在 `formula_push_rules.json`，不能全局设置、不能按项目适配；
3. 校对规则散在十余套引擎里，公式管理中心只看得到其中一套；
4. 公式调试、底稿用户公式、公式导入、报表公式审核共 7 个端点只校验登录，可跨项目读写；
5. 表间审核的 AUX / PREV 取不到数时代入 0；
6. 底稿可编辑公式只支持 10 个取数函数中的 3 个；
7. 509 行提示面板等 5 个组件写好了从未挂载。

## 术语

- **推送规则**：`formula_push_rules.json` 中一条「目标地址 + 来源公式 + 写入策略 + 触发事件」声明。
- **push 域**：本 spec 新增的第七个公式域，公式位 = 推送规则 `rule_id`。
- **严格取数**：取不到数时报「无法取数」并判不通过，禁止代入 0 后继续比较。

## R1 越权修复

- R1.1 WHEN 调用 `POST /api/formula/debug` THE 系统 SHALL 对请求体里的 `project_id` 校验项目 readonly 权限；非成员 403，且不查询该项目任何数据。
- R1.2 WHEN 调用 `/api/workpapers/{wp_id}/user-formulas` 的读 / 写 / 恢复预设三个端点 THE 系统 SHALL 按底稿所属项目校验权限（读 readonly，写与恢复 edit）。
- R1.3 WHEN 调用 `POST /api/workpapers/{wp_id}/validate-formula` THE 系统 SHALL 按底稿所属项目校验 readonly；请求体 `project_id` 若给定须与底稿所属项目一致（不一致 403），预览取数一律用底稿所属项目。
- R1.4 WHEN 调用 `POST /api/formula-management/import-export/import-data` 且 `persist=true` THE 系统 SHALL 与「新增自定义预设」同一口径：只允许可写预设的角色；管理员直接写数据库预设，其余角色提交为全局候选待审核；**不得再改写仓库里的 seed 文件**。
- R1.5 WHEN 导入请求带 `project_id` THE 系统 SHALL 校验该项目 readonly。
- R1.6 WHEN 调用 `GET /api/reports/{project_id}/{year}/consistency-check` THE 系统 SHALL 校验项目 readonly。
- R1.7 THE 系统 SHALL 有守卫覆盖「项目在请求体 / 查询参数 / 对象反查」三类端点（现有守卫只看路径里的 `{project_id}`），冻结基线只许变小，本 spec 修过的端点逐个钉死。
- R1.8 WHEN 权限收紧影响前端按钮 THE 前端 SHALL 同步门控（不能显示一个点了必 403 的按钮）。

## R2 推送规则纳入治理内核

- R2.1 THE 系统 SHALL 新增 `push` 公式域：系统预设层 = `formula_push_rules.json`（文件不改、不迁移），全局层 / 本项目层 / 模板层存 `formula_setting`。
- R2.2 可改的只有两件事：①公式来源规则的来源公式；②启用 / 停用。目标地址、写入策略、触发事件、四表与派生来源不可改。
- R2.3 WHEN 写入任一层的推送规则定义 THE 系统 SHALL 用与规则清单加载同一套校验（禁用列名、`TB()` 须写列名、函数白名单、试算）；规则不存在、非公式来源却改公式，一律拒绝并给中文原因。
- R2.4 WHEN 推送引擎运行 THE 引擎 SHALL 读本项目有效规则；本项目停用的规则不推送；本项目改写的公式按改写后的公式推送。
- R2.5 IF 某层改写在运行时校验不通过（如 binding 变更）THEN 引擎 SHALL 跳过该规则、在运行结果里写明原因，**不得**回退系统预设去覆盖用户有意改掉的值。
- R2.6 WHEN 在任一层停用一条系统值 / 派生值规则（`policy ∈ system / derived`）THE 系统 SHALL 拒绝并说明：这类目标是推送独占键，前后端保存都会剔除它，停用后既无人推送也无人能填；这类规则只能改写公式。可编辑值规则（`editable`）与附注规则可以停用。
- R2.7 WHEN 推送规则的有效定义变化（全局发布、项目适配、模板订阅 / 发版 / 退订、待确认处理）THE 系统 SHALL 在提交后对受影响项目的受影响底稿重新推送；运行记录的触发来源标为「公式规则变更」。
- R2.8 THE 公式推送面板 SHALL 显示每条规则的层级（系统预设 / 全局 / 模板 / 本项目 / 暂缓采用），并提供「改写公式」「本项目停用」「启用」「恢复上游」；全局设置页、发布预览、待确认弹窗、公式模板 SHALL 无需专门改动即可处理 push 域。

## R3 校对规则统一目录

- R3.1 THE 系统 SHALL 提供只读目录接口，列出平台全部校对 / 提示规则来源：每个来源给出名称、规则数、执行位置、是否可在公式管理中编辑，以及逐条规则（编号、名称、表达式或说明、严重程度、适用范围）。
- R3.2 目录 SHALL 只读现有规则源，不新增存储、不改各执行器。
- R3.3 THE 全局公式设置页 SHALL 新增「校对规则目录」页签；公式管理中心的勾稽 / 合理性分类 SHALL 有入口跳到该页签。
- R3.4 目录 SHALL 有守卫：每个已知规则文件都被登记为来源，新增规则文件未登记即失败。

## R4 零挂载组件处置

- R4.1 对 5 个从未被挂载的组件逐个查来历与功能重叠：有独立价值的接入页面，与现有组件重复的删除。
- R4.2 接入的组件 SHALL 用真实接口数据（禁止接入后显示空壳）。
- R4.3 处置后 SHALL 有守卫：`components/formula/` 下的 Vue 组件都至少被一处生产代码引用。

## R5 真库全链路走查

- R5.1 在【测试】项目上走通：全局发布 → 预览 → 冲突 → 待确认弹窗 → 项目确认；保存为模板 → 订阅 → 模板发新版 → 待确认；推送规则本项目改写 / 停用 → 重新推送。
- R5.2 用浏览器实测关键界面（全局设置页、待确认弹窗、公式推送面板、校对规则目录）。
- R5.3 写入型验收只用【测试】项目；结束后按「写过哪些表」逐项清理并对账，保留的回归数据写明。

## R6 底稿可编辑公式补齐函数

- R6.1 底稿可编辑公式 SHALL 支持 ROW / SUM_ROW / REPORT / NOTE / PREV / AUX / ADJ（现只支持 TB / SUM_TB / WP）。
- R6.2 求值 SHALL 走统一预载层 + L1 内核；ADJ 用底稿口径（不排除底稿来源分录）。
- R6.3 取不到数 SHALL 写进错误清单，禁止静默 0（无上年试算表、无辅助核算、报表未生成、附注无该项）。
- R6.4 函数支持矩阵、其 golden、前端矩阵 SHALL 同步更新并保持对拍。
- R6.5 统一预载层 SHALL 补齐 AUX 取数（现恒为空）与报表行取数（现须调用方自带）；四表查询走 `get_active_filter`。

## R7 回归与交付

- R7.1 表间审核 AUX / PREV 在严格模式下取不到数 SHALL 判「无法取数」不通过；AUX 查询走 `get_active_filter`；修掉重复的异常分支。
- R7.2 `formula_settings` 全套与本 spec 涉及模块的既有测试 SHALL 全绿；预存失败须在干净检出上复现并登记。
- R7.3 交付 SHALL 在干净 worktree 上验证要提交的那棵树；推送到特性分支并建 PR，合并 main 由用户拍板。
