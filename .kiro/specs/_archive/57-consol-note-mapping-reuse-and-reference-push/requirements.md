# 合并附注映射规则复用与标准科目参考下推

## 背景与动机

### 现状

合并附注的明细对应机制已完整实现（spec `consol-note-detail-template-and-mapping`，已归档）：

- **来源扫描**：`scan_all_entities` 读取各子企业单体附注 `disclosure_notes.table_data.rows`
- **结构分组**：`group_entities_by_structure` 按 `source_structure_hash`（SHA-256）将结构相同的子企业归组
- **五级匹配**：`suggest_template_rows` 做精确→别名→模糊→历史→手动 五级建议
- **用户确认**：`confirm_mapping` 带版本冲突检测（409）、来源结构变化检测、批量绑定
- **stale 检测**：`detect_stale_bindings` 在子企业附注结构变化后自动标 stale

### 痛点

1. **每年重复劳动**：同一集团每年审计项目都要从零做映射确认，而集团下属企业的附注行结构年度间变化很小
2. **跨项目无复用**：映射规则按 `project_id` 存储，A 项目确认过的映射 B 项目看不到
3. **集团无法统一口径**：集团审计组希望统一"应收账款明细该有哪几行、对应哪些科目"，但没有下发参考的通道
4. **子企业改数无感知**：子企业修改附注金额后，合并组不知道、不知道该不该刷新
5. **出具前无确认闸门**：没有机制确保所有子企业的附注数据都已定稿

### 核心矛盾与裁决

**集团不能直接推送附注行结构给子企业**——子企业附注的行结构由底稿→公式推送引擎→单体附注这条链路决定，推结构会断底稿取数链路。

**裁决**：集团推送的是**映射规则模板**和**标准科目参考**，不是附注行结构。子企业的底稿取数链路完全不变，变的只是"我的行怎么归到集团的行"这层映射关系。

## 用户故事

### US-1：映射规则提升为模板（集团审计组）

> 作为集团审计组，我希望将本年确认过的映射规则提升为"规则模板"，这样下一年或同集团其他项目可以直接复用，不需要从零确认。

**验收标准**：
- AC-1.1：已确认的映射规则（`ConsolNoteMappingRule`，status=active）可以被提升为规则模板
- AC-1.2：规则模板不绑定 `project_id`，存储在独立的模板表中
- AC-1.3：规则模板按 `section_id + template_type + source_structure_hash` 索引，支持按章节查找
- AC-1.4：规则模板记录来源项目和确认人，可追溯
- AC-1.5：提升时校验映射完整性（所有来源行都已映射，无 `match_type=manual` 且 `target=null`）

### US-2：新项目自动预填映射（集团审计组）

> 作为集团审计组，我希望新合并项目预览某章节时，系统自动从规则模板库和上年项目查找匹配规则，高置信度的直接预填，只让我处理少数变化的行。

**验收标准**：
- AC-2.1：`preview_detail_refresh` 返回的 `suggestions` 增加 `match_type=rule_template`（规则模板库匹配）和 `match_type=previous_year`（上年同集团项目匹配）两种来源
- AC-2.2：匹配优先级：规则模板库（confidence=0.92）> 上年项目历史（confidence=0.88）> 现有五级匹配
- AC-2.3：匹配依据是 `source_structure_hash` 精确匹配（结构完全一致）+ `source_label` 模糊匹配（结构有变化但大部分行相同）
- AC-2.4：预填结果在前端弹窗中用不同颜色标识来源（规则模板=蓝色、上年=灰色、本次新匹配=绿色、需手动=红色）
- AC-2.5：用户可以一键确认全部预填建议，也可以逐行修改后确认

### US-3：标准科目映射参考（集团审计组）

> 作为集团审计组，我希望在合并明细模板的目标行上标注推荐的科目码，子企业审计组在公式管理页面能看到"集团推荐"，参考着设置科目对应关系。

**验收标准**：
- AC-3.1：合并明细模板版本的 rows JSONB 每行新增可选字段 `recommended_account_codes: string[]`
- AC-3.2：模板编辑器支持为每行添加/修改推荐科目码
- AC-3.3：子企业的公式管理页面（附注章节）展示集团推荐的科目码（只读参考，不强制）
- AC-3.4：推荐科目码与实际使用的科目码不一致时，展示"与集团推荐不一致"提示（warning 级别，不阻断）

### US-4：子企业值变化实时通知（合并审计组）

> 作为合并审计组，我希望子企业修改附注金额后，合并附注页面能实时提示"N 家子企业数据已更新"，我决定何时刷新。

**验收标准**：
- AC-4.1：子企业附注保存时（`NOTE_SECTION_SAVED` 事件），计算值指纹（仅数值列的 hash）
- AC-4.2：值指纹变化时，通过 EventBus 发 `CONSOL_NOTE_VALUE_CHANGED` 事件
- AC-4.3：合并项目侧接收事件，标 `ConsolNoteData.is_stale=True`
- AC-4.4：合并附注编辑器展示黄色横幅："N 家子企业的数据已更新，点击刷新"
- AC-4.5：用户点击刷新触发 `fill_by_formula`，不自动刷新（保护 `manual_cells`）
- AC-4.6：横幅展示具体变化的子企业名称列表（hover 展开）

### US-5：值确认与签发闸门（合并审计组）

> 作为合并审计组，我希望出具审计报告前，系统检查所有映射章节的所有子企业数据都已确认定稿，未确认的阻止签发。

**验收标准**：
- AC-5.1：子企业审计组可以标记"附注章节已完成"（章节级确认）
- AC-5.2：确认时记录值指纹，子企业确认后又改数→自动降级为"已过期"
- AC-5.3：合并附注编辑器展示各企业的确认状态（✅已确认 / ⚠️已过期 / ⬜未确认）
- AC-5.4：签发前闸门检查所有映射章节：全部企业已确认且未过期→放行；否则列出问题清单
- AC-5.5：闸门集成到现有签发清单（`deliverable_readiness_check`）

### US-6：结构锁（集团控制骨架）

> 作为集团审计组，我希望确认映射后锁定子企业的附注行结构（不能加行/删行/改行名），但不锁金额，防止子企业改结构导致映射失效。

**验收标准**：
- AC-6.1：合并组确认映射后，可以对指定章节启用结构锁
- AC-6.2：结构锁生效后，子企业对已锁定章节的行操作（新增行/删除行/改行名）被拦截，返回提示"该章节结构已被集团锁定"
- AC-6.3：金额修改不受影响
- AC-6.4：结构锁可由合并组解除（需 review 级权限）
- AC-6.5：子企业侧展示锁定标记（🔒图标 + tooltip）

## 非功能需求

### NFR-1：性能

- 规则模板库查询响应时间 < 200ms（模板数 < 1000）
- 预填匹配（含规则模板+上年历史）总响应时间 < 500ms（子企业数 < 50）
- 值变化事件传播延迟 < 2s（EventBus 进程内）

### NFR-2：数据完整性

- 规则模板不可变（与 `ConsolNoteDetailTemplateVersion` 一致，追加新版本不改旧版本）
- 确认闸门 fail-closed（检查失败=阻断签发，不降级为 warning）
- 结构锁与 `ConsolNoteData.cell_state=locked` 不冲突（结构锁管行增删，cell_state 管单元格编辑）

### NFR-3：兼容性

- 子企业底稿→公式推送→单体附注链路零改动
- 现有五级匹配逻辑保持不变，新增来源插入到第四级之前
- 不新增子企业侧的必做操作（推荐科目码为参考，确认状态为可选）

## 约束与排除

### 约束

- C-1：映射规则模板按 `source_structure_hash` 精确匹配为主——结构完全一致时直接复用，结构有变化时降级为逐行模糊匹配
- C-2：标准科目参考只作推荐，不强制——子企业可以使用与推荐不同的科目码
- C-3：值变化通知仅限同一 PG 实例内的项目（跨实例需要消息队列，不在本 spec 范围）
- C-4：迁移使用 V200/R200（当前最高 V199）

### 排除

- E-1：不做附注行结构的下推（裁决理由见"核心矛盾与裁决"）
- E-2：不做跨事务所/跨实例的模板共享
- E-3：不做映射规则的自动合并（两个项目的规则有冲突时由用户手动选择）
- E-4：不改公式推送引擎（`formula_push`）的任何逻辑
- E-5：不做 consol-note-three-level-drilldown 的穿透功能（该 spec 独立）

## 术语表

| 术语 | 定义 |
|------|------|
| 映射规则模板 | 从已确认的项目级映射规则提升而来的、不绑定 project_id 的可复用规则 |
| 标准科目参考 | 合并明细模板目标行上标注的推荐科目码，供子企业参考 |
| 结构锁 | 合并组对子企业附注章节行结构的锁定（禁增删行，不禁改值） |
| 值指纹 | 附注表格数据中仅数值列的 SHA-256 哈希，用于检测金额变化 |
| 值确认 | 子企业/合并组对某章节当前数据的确认动作，记录确认时的值指纹 |
| source_structure_hash | 已有概念——附注行标签+行类型的 SHA-256，用于检测行结构变化 |
