## R1　共享库迁移执行（裁定②）

**R1.1** 执行前现扫 `schema_version` 与 `list_pending()`，执行集合 = 磁盘版本集合 − 已登记版本集合，不引用
本文档记录的数字。

**R1.2** 执行必须经 `MigrationRunner.run_pending()`（与应用启动同一路径），执行前备份 `schema_version` 全表。

**R1.3** 执行后逐项验证：目标列 / 表存在；已应用行的 checksum 与磁盘一致；`schema_migration_failures` 无残留；
`list_pending()` 为空。

**R1.4** 本批迁移不止附注链路。归属、DDL 概要、风险逐个登记（design §2.1），用户按清单放行（2026-11-03 已放行
方案甲）。

**R1.5** 已发布的迁移文件**不得改动**（checksum 是已应用行的身份）。执行失败时修执行器，不修迁移文件。

**R1.6** 迁移执行器分句必须与 PostgreSQL 词法一致：文件开头的 UTF-8 BOM 不发给数据库；字符串字面量
（`'...'`、`''`、`E'\''`）与引号标识符（`"..."`）里的分号不分句。须有用例钉住，且变异（去掉任一规则）必红。

## R2　HEAD 回归修复（裁定③）

**R2.0** 回归的修复方式是**按文件三方恢复被覆盖的改动**：基线 = 覆盖提交的父提交，「他方」= 覆盖提交，
「我方」= 当前 HEAD；覆盖之后别人在 HEAD 上的改动一律保留。不得整文件取旧版。恢复清单、冲突裁决与「恢复链
之外的丢失」须逐条登记（design §3.0、§3.8、§3.9）。

**R2.1 比例 / 损失率预设公式**：带「比例(%)」「预期信用损失率(%)」列的附注表重新获得预设公式；分子格为空不出值、
不写 0（`requires`），**执行时**同样先查 `requires`；单体预设与合并汇总后派生比例共用 `note_formula_ratios`。

**R2.2 推送提交后附注表内公式**：每次推送提交后，写入过的附注章节**恰好执行一次**附注公式。执行点在
`run_and_commit` 的提交边界（R20 收口，ADR-NPR-08），事件触发、推送页立即推送、采纳公式值、公式配置变更
传播四个入口**不再各自调用**；附注刷新链路传 `skip_note_followup=True`，回填之后自己最后执行。失败只记日志、
不回滚已提交的推送。推送拥有格保护只认生效规则、只认规则自己的字段；用户公式可以覆盖推送拥有格（R20.3）。

**R2.3 合并附注公式种子**：先定位根因再决定改实现还是改基线（铁律㉓）。若是数据有意变化，每个增减的单元格
都要逐条解释，基线注释写明口径变化与日期；禁止只改基线数字。真正分不出净额 / 毛额（循环引用等）的报表行
恒不种。

**R2.4 SQLite 测试基座**：`create_all` 前导入全部模型子模块（pkgutil 走包），`attachment_versions.blob_id →
asset_blobs.id` 类外键不再悬空；同时 `app.models` 包本身要注册资产模型（生产启动也靠它）。

**R2.5 阻碍本轮验证面的 HEAD 缺陷（R5.3 的例外，逐条说明）**：
- 单体报表生成在 HEAD 上必失败（S5 的运行记录写入方与 V246 共享表 `report_generation_run` 撞表：
  状态词表与 `calc_version` 类型都不一致）⇒ 写入方按共享表口径写；对外状态口径不变（`partial` / `running`
  由读时换算）。
- 推送用例的测试环境缺调整分录财务处理表（`adjustment_treatment_events` / `adjustment_client_bookings`）。
- 公式管理弹窗以打开态挂载（异步宿主模块晚到）时打开流程不执行：HEAD 去掉了 `immediate`；恢复的原写法把
  `immediate` 监听注册在 `<script setup>` 中段，首轮同步执行读到未初始化的 ref（暂时性死区）⇒ 同样什么都不加载。
- 后端全量回归会删掉跑它的那个 worktree 的 git index：`scripts/check/candidate_tree_identity.py` 的安全校验写在
  `try` 里，校验不过（路径就是真实 index）时 `finally` 照样清理 ⇒ 删的正是要保护的真实 index；它自己的变异用例
  每次都走到这条路径。index 被删后全部文件变成「已暂存删除」，此时只 `git add` 部分路径再提交，提交树就只剩这几个
  路径。须修复并加「拒绝后真实 index 逐字节不变」断言。

## R3　单体附注表格权威源确认与门禁修真（裁定①）

**R3.1** 固化：单体附注每张表的列结构、表名**以底稿模板 xlsx 的披露 sheet 为准**；Word 权威章 / 节 / 标题 /
顺序 / 归属与合并附注骨架。不按 Word 回退单体表结构。

**R3.2** 修 Word 同步门禁假绿：`sync_note_templates_from_word.py --check` 下各 phase 的漂移必须真实计入判定。
必配两条反向断言：注入一处不一致 ⇒ exit 2 并点名；不注入任何改动 ⇒ exit 0（铁律㉗：永红门禁等于没有门禁）。

**R3.3** `check_note_template_word_tree.py` 白名单从「沉默登记」升级为可解释声明：每条带差异类别与可伪证的理由；
`todo` 类只许减少；保留「白名单无失效条目」检测。应收账款族优先。

**R3.4** 补「表名」判据：已配对成功的表，模板表名与底稿表名归一后一致，或落白名单（带类别与理由）。

## R4　详细披露 builder 后端化（裁定④）

**R4.1** 目标：审定数（过完调整分录）变化后，无需任何人打开附注页或底稿披露 Tab，详细披露表即可自动重算并
写入附注。

**R4.2** 必须正面处理与 `disclosure-payload-authority-source`「载荷权威源留前端、否决后端重建」的冲突：选定一条
**不产生第二套算法**的路线（ADR-NPR-03：在 Node 侧执行既有 TS builder）。

**R4.3** 规模按期 1 实施时的现扫值规划，不按旧数字排期。

**R4.4** 单一算法源是硬要求；同一张披露表不得「前端算一份、后端算一份」只靠人工比对。

**R4.5** 后端化不得削弱四层人工保护（整章 `_manual_override`、正文 `is_local_override`、格级 `_cell_modes`
manual / locked、首次同步保护）与推送 ownership 重放。

**R4.6** 分期交付。期 1 必须让「审定后无人开页也能更新」成立（可以只覆盖少数码），每期独立验证、独立回滚。

## R5　通用约束

**R5.1** 不改变合并附注的数据来源：合并只从单体附注拉数。血缘统一为「底稿披露表 → 单体附注 → 合并附注」。

**R5.2** 共享库写操作先经用户放行；验收写入只用【测试】项目或回滚事务。

**R5.3** 不顺带修 design §9 登记的其他缺口；只在它们阻碍本轮四项时触及并显式说明（R2.5）。

**R5.4** 每项标完成必须有：真实代码 + 测试通过 + 至少一条磁盘变异打红（且红在本判据自己的用例上，不是红在
基线本来就红的用例上）+ 生产调用方 / 挂载证据。回归修复另需「由红转绿」的前后对比。

**R5.5** 回归口径：候选树与**当前远端最新头**两棵干净 worktree 逐测试节点比对，candidate-only red = 0；前端
全量 `vue-tsc` 按（文件, 错误码, 信息）计数比对，added = 0；vitest 的未处理错误（Unhandled Errors）不得新增。
