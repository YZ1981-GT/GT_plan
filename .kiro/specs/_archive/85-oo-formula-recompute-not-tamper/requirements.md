# 需求：OnlyOffice 重算公式格不再当成篡改

> 承接 `oo-return-to-form-dead-end-and-save-speed` design §9.10 的待拍板项。用户 2026-10-25：「在 D2-2 的在线编辑里改金额，保存时必定报冲突。原因是期末余额、期末未审、期末审定这三个公式格会被 OnlyOffice 重新计算，后端把这种重算当成了用户篡改公式格。改文字则一切正常。修它要动合并的核心规则，另立 spec 来做，注意其他科目也都会涉及这个问题」。

## 背景

- 三方合并对受保护字段（公式字段、落在公式遮罩里的格、自动取数格）的规则是：OO 一侧的值与打开时不同（超出 R10 的按分容差）⇒ 一律记受保护冲突、保留服务器值（AC 6.6 / Property 24）。OO 打开文档就会重算公式，所以只要改了某个公式的输入，这个公式格就一定「被改」，整次保存进入冲突。
- 真库现有受保护冲突 351 条（D2 333 条 / 5 次保存，D4 18 条 / 9 次保存），全部是「打开时值 = 服务器值、OO 一侧不同」这一种形态。
- 判断「是重算还是篡改」所需的公式文本，提取时已经读到（`formula_inventory`），但适配器只把值交给合并，公式证据在半路丢掉了。
- 即使冲突裁决后应用成功，store 镜像也跳过全部受保护字段：D2 的 store 里存着期末余额 / 期末未审 / 期末审定，D2-1 审定表按 store 里的期末未审 SUMIF 并发布到试算表，OO 改了输入后这三列在 store 里一直是旧值。

## 术语

- **重算候选**：受保护字段，保护策略是公式字段或公式遮罩格；打开时（base）与 OO 一侧（incoming）都有值，且两值超出 R10 容差。
- **公式签名**：单元格公式文本中「引用本行的地址」换成 `{r}`、其余逐字保留后的字符串；在行增删后仍可比较。
- **输入一致**：合并结果中，除重算候选外的每个字段都与 OO 一侧读到的值相同，且没有任何冲突或被搁置的行 / 字段。

## R1 合并规则：重算不是篡改

1. 重算候选的 base 与 incoming 都带公式签名且相同、并且输入一致时，判「采纳重算」：合并结果取 OO 一侧的值，不产生冲突，不要求客户端重载。
2. 重算候选的公式签名相同但输入不一致（服务器一侧有 OO 一侧没有的改动，或本次合并另有冲突 / 搁置）时，记受保护冲突、保留服务器值，原因写明「OO 按自己一侧的输入重算过，合并结果的输入与之不同」。
3. 以下情形仍是受保护冲突（保留服务器值），原因分别写明：公式被换成数值；公式被改写；原本是数值的受保护格被写入公式；受保护的数值格被改了值。
4. 没有公式证据（Word 底稿、未提供证据的适配器、转置表等）时行为与现在逐字相同。
5. 自动取数格仍精确比较；可编辑字段的规则、R10 容差规则不变；公式文本变了而值没变仍不报冲突（与现在相同）。
6. OO 新增行（三方中只有 incoming 有这一行）的公式字段：签名与 base 里同一列的公式之一相同且输入一致时判「采纳重算」，合并值仍取 OO 一侧（与现在相同），只是允许进入 store；否则保持现状。
7. 新规则只会把现在的冲突变成采纳，不会把现在的采纳变成冲突。

## R2 公式证据

1. Excel 提取对每个读到公式的受管格产出公式签名：本行引用（含 `$` 锁定、单格与区间端点）换成 `{r}`；跨表引用、引用别的行、结构化引用、名称、字符串字面量逐字保留。分词只调用 `excel_row_shift` 现有的唯一改写入口（只读使用，不改它）。
2. 证据覆盖适配器的全部 binding（主表与兄弟表），随 projection 一起交给合并；不进 projection 摘要、不参与 projection 相等比较。
3. 已发布形态缓存（P9）与 incoming 复用（P8）命中时，证据与重新提取得到的相同。

## R3 store 与下游一致

1. 判「采纳重算」的公式字段，其值进入 store 镜像；store 里本来就存这个字段的 provider 才会写，按自身规则过滤公式字段的 provider 不受影响。
2. D2 在 OO 里改金额后，store 中期末余额 / 期末未审 / 期末审定为新值，D2-1 审定表与「发布到试算表」读到的期末未审随之更新。
3. 模板骨架行判据不把公式格的值算作用户内容（与它的文档描述一致，不再依赖「公式字段受保护」这一巧合）。
4. 发布出去的 content version 与 store 视图分开：视图只影响 store 镜像。

## R4 前端公式与权威模板对齐（期末余额族）

1. D1-2、D1-3、D2-2、D3-2、D5-2、D6-2、D7-2 七张表的表单把「期末余额 / 期末未审」按「期初审定 ± 本期发生」计算，权威模板是「期初未审 ± 本期发生」；改为与模板一致（F 循环已按「对齐致同源模板」处理过同类问题，先例 F1-2 裁决 F1-H3）。D1-7 备查簿核对的「明细账(D1-2)」行按 D1-2 口径重建，随之同改。不对齐时，有期初调整的行会在表单保存与 OO 保存之间来回变值。全仓扫「期初审定作滚动起点」后逐个对照模板，同一问题还有 D2-3、G2-3、G5-3、K1-3 四张坏账准备明细表的期末未审（期末账面）与 G2-2 的期末余额，连同读同一口径的两处跨表取数（G2-3 → G2-1 / 附注、G5-3 → G5-1 / 上市附注）一并改。
2. D5-2 的期末审定，模板取期末余额列（O = J + M + N，不含被审计单位重分类 K），表单取期末未审（L + M + N）；同属公式格被 OO 重算后来回变值，一并按模板改（F1-2 的 X = O + V + W 同此）。
3. 真库现状如实登记：七张表共 2760 行，期初调整全部为 0（D3 / D5 / D6 的行没有金额，D1 / D7 没有行），改动不改变任何已存数字；新增的五张表真库没有存数（对应 store 键 0 条）。
4. 其余口径不一致（贴现天数 360 / 365、差额方向、D6-3 等）属业务口径，本 spec 不改，逐条登记待拍板。

## R5 验收

1. 修订既有判据须在测试里写明原判据与改判理由；新增判据配隔离副本里的磁盘变异，变异必须打红。
2. 真实历史冲突重放：真库每次留下受保护冲突的保存，用当时的 base 与 OO 文件在新规则下重放（只读），逐条给出新旧冲突数与剩余冲突的原因。
3. 浏览器实测（新建【测试】项目）：D2-2 在线编辑改金额保存后 0 冲突，表单与 D2-1 显示新值；在公式格里敲数字仍报冲突；结束后经平台清理。
4. 回归：相关后端测试文件改前改后逐条对比、前端相关单测、golden digest、行数门；新增失败为 0。
