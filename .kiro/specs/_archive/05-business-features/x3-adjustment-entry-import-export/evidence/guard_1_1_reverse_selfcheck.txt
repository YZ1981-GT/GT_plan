[2] 物理变异清单（backend/data/adjustment_ie_contract.json）——「改一列 / 改一机制必打红」
--------------------------------------------------------------------------------
做法：read_bytes 取原始字节 + md5；把 M4-3 迁入 sheets（形如 design §Key_Ledger 条目的
per_field_plus_data 探针值）；只跑三个节点；finally 写回原始字节并比对 md5。
开跑前检查清单 mtime 新鲜度（<120s 即中止，防与并发会话对撞）。

三个节点：
  A registered = TestLedgerRegistersSixteenX3::test_sheet_is_registered_in_sheets_section[M4-3]
  B fields     = TestLedgerEntryDeclaresTripleAndMechanism::test_entry_declares_triple_and_mechanism[M4-3]
  C gs9        = TestStorageFieldDerivedFromMechanism::test_storage_field_matches_mechanism[M4-3]

清单 md5（变异前）= 5fe43fc5b84fca16ea7724eaa2d4b311  size=61029

变体      mechanism              storage_field  收集数  A       B       C            判读
--------  ---------------------  -------------  ------  ------  ------  -----------  ------------------
CONTROL   adjustment_savebatch   remark         3       PASSED  PASSED  PASSED       三条全绿 ⇒ 断言非恒红
MUT-SF    adjustment_savebatch   conclusion     3       PASSED  PASSED  FAILED       RED（消息=机制↔列不一致）
MUT-MECH  formdata_setfield      remark         3       PASSED  PASSED  FAILED       RED（消息=机制↔列不一致）

清单 md5（还原后）= 5fe43fc5b84fca16ea7724eaa2d4b311  一致=True

结论：反向自检通过。CONTROL 排除了 ANCHOR-MISS / WRONG-TEST（三条并非恒红）；两个变异
各自只打红「机制↔列」那一条、未连带打红 A/B ⇒ 判据定位准确、非空转。

[3] GS1 反假绿：「X3_SHEET_SPECS 从清单装载」的判据能区分三种实现
--------------------------------------------------------------------------------
做法：合成三个模块文件（临时目录，零生产代码改动），把守卫的 _MODULE_PATH 指向它们，
用替身清单（把 M4-3 的 mechanism/storage_field 成对翻到 formdata_setfield/conclusion）
重新 exec，看 X3_SHEET_SPECS 是否跟着变；同时跑剥注释后的字面量扫描。

合成实现               清单读取次数  storage_field  装载判据  字面量判据  预期符合
---------------------  ------------  -------------  --------  ----------  --------
GOOD（从清单装载）     1             'conclusion'   PASS      PASS        ✓
HARDCODED（写死 dict） 0             'remark'       RED       RED（M4-3） ✓
LOADS_BUT_OVERRIDES    1             'remark'       RED       RED（M4-3） ✓
  （源码里确有 json.load，值却被硬编码覆盖 = grep 式守卫必假绿的那类）

结论：两条判据（真实装载行为 + 剥注释后字面量扫描）均能区分，且第三种「装载了但不采用」
也被抓住 —— 这是 grep 「有没有 json.load」式守卫抓不到的那一类。

[4] 判据边界（防下一轮高估覆盖面）
--------------------------------------------------------------------------------
本文件的 mechanism 取清单登记值 ⇒ 只抓「清单内机制与列自相矛盾」。

两处一起错）要靠任务 1.9 的前端源码机制探针，两侧合起来才是 design §GS9 的完整判据。
