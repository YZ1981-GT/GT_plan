二、helper 的 4 处真缺陷（本轮修，逐条给理由）
--------------------------------------------------------------------------------
H1 findCalls 不识别可选调用 `callee?.(…)`
   M 族 11 张的复核入口实测写法是 `openReviewDialog?.('M1-3-adjustment', '调整分录')`
   （L2 是无 `?.` 的 `openReviewDialog(…)`）⇒ 修前只有 5 张抓到复核键，M 族 10 张的
   复核键排除集恒空 ⇒ R2.4「排除复核键」对这 10 张整条空转。修后 11 张全部抓到。
H2 collectWriteSites 只解析 saveBatch 调用实参
   L6-3 / M1-3 / M2-3 的写入载荷在调用点之外构造（`const items = entries.value.map(...)`
   里才是 `{ itemId: …, data: { remark: … } }`，调用处是 `saveBatch(items)`）⇒ 修前这
   三张取不到写入列 ⇒ 机制判不出 ⇒ 被误标 pending_manual（与裁决 1 冲突）。改为按
   **结构**扫 `{ itemId: …, data: … }` 元素字面量（两个键都在才算，避免把
   `useAdjustmentCentralSync({ …, itemId })` 的选项对象当写入载荷）。
H3 「机制歧义」判过宽，把 N1-3 误标 pending_manual
   N1TabAdjustment 内既 `formData.setField('3','entries', …)`（机制①三步链）又
   `formData.debouncedSave('N1-3-entries', { conclusion: … })`（同一 formData 门面的
   直呼形态），键与列**逐字相同** ⇒ 是同一存储目标的两种调用写法，不是歧义。改为
   「键与列都相同 ⇒ 取机制①并双链留痕；只有真分叉才判歧义」。
H4 形态④的键被同名非数据键误剔（最贵的一条 —— 正是 E12 那个坑本体）
   收尾处 `entryKeys.filter(k => !review.has(k) && !csync.has(k))` 无条件执行，把 N5-3
   由三步链拼出的真数据键 `N5-3-entries` 一并剔掉（tab 内同名字面量属中央同步键、
   同名纯属巧合，E12 → E17 / G11）⇒ 修前 N5-3 判「键不可确证」，正是 E12 的错结论。
   改为排除只作用于**字面量扫描**得来的键（机制②），形态④的键来源已证、不按名字剔。
未改动的部分：四形态提取器骨架、注释剥离器、括号配对/跳参数列表、机制→列的
   「读机制实现源码载荷键」思路、SourceBundle 注入面、清单读取与 legacy 锚点。

三、E14 修法（不是把常量 'remark' 换成 'conclusion'）
--------------------------------------------------------------------------------
旧：expect(entry.storage_field).toBe('remark')            ← 守卫把错值锁成基线
新：前端源码 --实测--> 机制 --实测该机制实现的载荷对象字面量--> 应有列 == 清单登记列
    · 机制① use{X}FormData.setField → saveField(itemId, { conclusion })  ⇒ conclusion
    · 机制② use{X}Adjustment 的 saveBatch / debouncedSave(itemId,{remark}) ⇒ remark
    · 判据内不出现任何列名常量；14 张既有 aligned sheet 改判后仍 14/14 绿
      （逐张实测出唯一写入列 remark，依据链落到 emit('save') / debouncedSave /
       saveField / saveBatch / allResponses.set 五种真实写入形态之一）
非退化自检：两条机制必须各推出**不同**的列且都有实例（塌成同一列即红）；
           机制分布钉死 ①=[N1-3,N2-3,N3-3,N5-3] / ②=12 张。
E14 回归锚点：旧常量判据对机制①的 4 张全判违规（4/4），机制判据 0 违规；
             旧判据「碰对了机制②的 12 张」正是它长期被误认为正确的原因。
后端分工（design §GS9 完整判据 = 两侧之和，已写进 helper 与 spec 的注释）：
  后端 test_x3_key_ledger.py 的 mechanism 取**清单登记值** ⇒ 只抓「清单内自相矛盾」；
  「机制是否与前端源码一致」后端读不到 .vue ⇒ 由本前端探针承担。
