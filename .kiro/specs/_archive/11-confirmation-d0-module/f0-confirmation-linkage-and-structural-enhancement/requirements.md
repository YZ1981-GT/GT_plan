# Requirements Document

## Introduction

F0 存货循环函证（预付账款/应付票据/应付账款/采购）是 7 个函证循环中**结构最完整但联动最弱**的一个。11 张可见 sheet 已全部映射到正确的 componentType（无隐藏 sheet 无 skip 问题），F0-5/F0-6 替代程序有专属前端组件+后端导入导出 —— **组件缺失不是瓶颈，「取数联动」才是**。

### 立项依据（只读实证）

**源模板**（`backend/wp_templates/F/F0 存货循环函证.xlsx`，openpyxl 逐格读取 11 sheet）

- F0-1 函证结果汇总表：上区 20 行 × 33 列两级表头（发函纪要6 + 发函信息5 + 收到回函7 + 回函金额确认区）+ 下区四块（函证情况矩阵 7 指标 × 4 品种 / 样本选择 6 段 / 审计说明 5 段 / 审计结论）
- F0-4b 函证差异检查表：ABCDEFGHI 九段调节（D=A+B−C / H=E+F−G / I=H−D），含凭证明细区各 2 行+`…`（动态）
- F0-5 预付及采购替代程序：四区块（期后收货/期末余额证据/本期付款/本期采购入库），每块含凭证列 + 合计行
- F0-6 应付及采购替代程序：四区块（余额支持证据/期后付款/本期采购入库/本期付款），结构对称 F0-5
- F0-7 邮件传真回函可靠性验证：7+7=14 列，含「被函证者身份确认」「邮箱可靠性验证」「致电确认」等子列
- F0-8 函证程序舞弊风险评价表：19 条迹象 + 汇总到 B50

**平台现状实证**

- `wp_code_overrides.json` F0 条目：10 条，8 个 componentType（hub/program/summary/entity-verify/followup/diff-reconcile/diff-checklist/alternative-f05/alternative-f06/reliability/fraud-risk）
- `cycleConfirmationMeta.F0`：summaryCode=F0-1 / diffCode=F0-4 / diffChecklistCode=F0-4b / altPrimaryCode=F0-5 / altSecondaryCode=F0-6 / reliabilityCode=F0-7 / fraudCode=F0-8 —— **完整齐全**
- `_f0_import_export.py`：F0-5/F0-6 四区块导入导出完整
- **缺失联动**：F0-1 的 7 个统计指标全是手工录入 0；F0-5/F0-6 的供应商名称+余额手工填写；F0-4b 差异公式无实时计算；F0-8→B50 推送是 TODO stub

**参照 E0 的改进模式**

- E0 `importE0ListsToSummary`：从 4 张发函清单自动聚合到 E0-1 矩阵（per-list `amountKeys` / 三元去重 / 品种分流）
- E0 `confirmation-send-list-e03`：从 E1-3 自动取数（开户银行/账号/余额），专属 16 列结构化字段
- E0 `confirmation-wealth-list`：看板指标 + 审计说明 + 结论 + 导入导出

F0 的「取数」源头是 **`tb_aux_balance` 的往来维度**（按供应商归集预付/应付余额）+ **F1/F3/F4 审定表**（四品种期末审定额），应做同等联动。

## Requirements

### Requirement 1: F0-1 函证情况矩阵自动聚合（P0）

**User Story:** 作为审计助理，我在 F0-1 编制完上区函证明细后，「一、函证情况」矩阵应自动从上区 grid 和 F0-5/F0-6 合计行聚合出各指标值，无需手工填 0。

#### Acceptance Criteria

- 1.1 「抽取样本的发函金额」= 上区 grid F 列（发函金额）按品种（E 列 `账户/交易`）自动求和
  —— 源模板 `R31 = SUMIF(E8:E27, E29, F8:F27)`
- 1.2 「回函确认金额」= 上区 grid **U 列（可确认金额）** 按品种求和，**不叠加「相符」过滤**
  —— 源模板 `R33 = SUMIF(E8:E27, E29, U8:U27)`。
  🔴 **2026-08-03 更正**（原写「S 列中 N 列=『相符』的行求和」）：平台
  `useConfirmationData.computeConfirmedAmount` 已按相符→amount / 不符→reply_amount /
  未回函→amount 或 alt_confirmed 派生出 U 列，业务规则本就内含在里面，
  再叠一层相符过滤是双重口径（E0 的 `e0SummaryMatrix` 同样直接取 `confirmed_amount`）
- 1.3 「替代测试确认金额」= 上区 grid **Y 列（替代后可确认金额）** 按品种求和
  —— 源模板 `R36 = SUMIF(E8:E27, E29, Y8:Y27)`。
  🔴 **2026-08-03 更正**（原写「F0-5 合计 + F0-6 合计按品种归属」）：替代确认金额本就逐行记在上区 Y 列，
  源模板从不按替代程序底稿合计反推品种归属。F0-5/F0-6 四区块合计改作**勾稽信号**
  （上区 Y 列合计 ?= 两表凭证金额合计，不符即提示「Y 列漏填 / 替代程序底稿漏编」），
  不参与矩阵取值 —— 见 design.md 的 `checkAltConsistency`
- 1.4 百分比指标（发函占账面/回函占发函/回函占账面/替代+回函占账面）自动派生
  —— 源模板 `R32/R34/R35` 用 `IF(ISERROR(...),0,...)`，本实现改为**分母缺失或为 0 时返回 null 渲染「-」**
  （显示 0 会让「未取到账面数」与「比例真为 0」不可区分）；
  `R37 = (R36+R33)/R30` 忠实实现，另对「U 与 Y 相等」的行给出双算风险提示而不改公式
- 1.5 「本期（期末）账面金额」从 F1/F3/F4 审定表自动取（走 `fetchWorkpaperHtmlRows` 或 render-config 的 `tb_amount`）
- 1.6 矩阵值只读、自动更新（用户改上区 grid 或 F0-5/F0-6 保存后刷新）
- 1.7 手工录入优先模式：若用户曾手工修改某格，标记 `_manual` 不再被自动值覆盖

### Requirement 2: F0-5/F0-6 供应商+余额自动带入（P0）

**User Story:** 作为审计助理，我打开替代程序底稿（F0-5/F0-6）时，供应商名称和期末余额应从 F0-1 上区的未回函供应商清单自动带入，无需手工抄录。

#### Acceptance Criteria

- 2.1 F0-5/F0-6 顶部「供应商名称」从 F0-1 上区 grid 中 `是否收到回函=否` 的行的 D 列（被询证单位名称）取值
- 2.2 「期末余额」(E12) 从 F0-1 上区 grid 的 F 列（发函金额）取对应供应商的值
- 2.3 若辅助余额表（`tb_aux_balance` 往来维度）有该供应商更精确的余额，优先使用
- 2.4 带入后仍可手工修改（手工优先）
- 2.5 供应商选择器支持从 F0-1 未回函清单中下拉选取

### Requirement 3: F0-4b 差异检查表公式实时计算（P1）

**User Story:** 作为审计助理，我在 F0-4b 录入各段金额后，调节后余额和差异应自动计算并标红非零差异。

#### Acceptance Criteria

- 3.1 D = A + B − C（调节后被询证方余额）实时派生
- 3.2 H = E + F − G（调节后本公司余额）实时派生
- 3.3 I = H − D（差异）实时派生，非零时红色高亮
- 3.4 B/C/F/G 各段的凭证明细区支持动态增删行，金额列自动求和到段合计
- 3.5 差异非零时在底部「审计说明」区自动提示需要进一步调查或调整

### Requirement 4: F0-8 舞弊迹象汇总推送 B50（P1）

**User Story:** 作为审计助理，我勾选了存在的舞弊迹象后，可一键把所有「是」的迹象推送到 B50 风险底稿。

#### Acceptance Criteria

- 4.1 「是否存在」列改为三态下拉（是/否/不适用）
- 4.2 选「是」时自动展开「应对措施」录入区域
- 4.3 底部「汇总」行提供「推送到B50」按钮，把所有标「是」的迹象打包推送
- 4.4 推送走 EventBus（`fraud-risk:push-to-b50`），载荷含 wp_code + 迹象序号列表 + 金额
- 4.5 推送成功后该行「索引号」列自动填写 B50 索引

### Requirement 5: F0-1 样本选择段结构化（P2）

**User Story:** 作为审计助理，「二、样本选择」段应改为结构化录入（下拉+输入框），而非整段占位文字手工替换。

#### Acceptance Criteria

- 5.1 「测试总体」自动显示四品种各自的账面余额 + 供应商个数（从审定表 + 辅助余额取）
- 5.2 「特定样本」提供结构化输入：大额门槛 / 关联方标记 / 异常标记 → 自动生成文案
- 5.3 「确定的抽样样本量」提供输入框，自动拼接「共XX个供应商」
- 5.4 「抽样方法」做成四选一下拉（随机/系统/货币单元/随意）
- 5.5 「抽样过程」做成结构化模板，用户只填工具名+比例+底稿索引
- 5.6 生成的结果仍可全文编辑（结构化优先、文本兜底）

### Requirement 6: F0-7 可靠性验证结构化（P2）

**User Story:** 作为审计助理，F0-7 的可靠性验证子列应改为结构化判断，而非纯文本填写。

#### Acceptance Criteria

- 6.1 「被函证者身份确认」改为是/否下拉 + 确认方式多选（名片/网站核对/系统查询/合同信息核对）
- 6.2 「回函邮箱」列自动检测 @ 后缀：公司域名绿色 / 私人邮箱（qq/163/gmail/hotmail等）红色告警
- 6.3 「致电确认」改为结构化：日期 + 对方姓名 + 部门 + 确认内容摘要
- 6.4 「回函可靠性结论」根据上述结构化判断自动推导（全通过→可靠 / 有红色→需进一步确认）
- 6.5 审计说明区保留自由文本兜底

### Requirement 7: F0-4 差异原因枚举 + 联动 A13（P2）

**User Story:** 作为审计助理，函证差异的原因应从常见枚举中选取，超重要性水平的差异应能一键推到 A13 错报底稿。

#### Acceptance Criteria

- 7.1 「差异原因」列改为下拉枚举 + 自由文本（枚举：在途款项/未达账项/退货退款/跨期记账/尾差/其他）
- 7.2 差异金额绝对值超重要性水平时自动标红 + 提示「建议推送错报」
- 7.3 提供「推送到A13」按钮（per 行），走 `a13:push-misstatement` EventBus
- 7.4 推送载荷含：科目(预付/应付票据/应付账款) + 金额 + 差异原因 + 索引号 + source_wp_code=F0

### Requirement 8: F0-3 跟函核对点结构化 + 工号字段（P3）

**User Story:** 作为审计助理，跟函记录的三个核对点应改为 checkbox 可勾选，经办人工号应有专属输入框。

#### Acceptance Criteria

- 8.1 R23~R25 三个核对点改为是/否 checkbox（是否了解流程/确认身份权限/正常流程处理）
- 8.2 话术中 `工号为[XX]（如有）` 改为专属 `el-input` 字段
- 8.3 checkbox 全部勾「是」时自动标绿「核对通过」
- 8.4 签名区保留手写签名逻辑（或电子签名 placeholder）

### Requirement 9: 守卫与 CI（贯穿）

**User Story:** 作为平台维护者，上述改进必须有守卫防回退。

#### Acceptance Criteria

- 9.1 后端守卫：F0-1 矩阵聚合纯函数测试 + F0-5/F0-6 联动取值测试
- 9.2 前端守卫：差异公式派生测试（PBT） + B50 推送载荷契约 + 可靠性自动推导测试
- 9.3 CI job `f0-confirmation-linkage` 覆盖上述守卫
- 9.4 源码级守卫：F0-1 矩阵值禁手工赋值（除 `_manual` 标记路径）
