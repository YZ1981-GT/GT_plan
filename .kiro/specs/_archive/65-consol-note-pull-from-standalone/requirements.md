# 合并附注从单体附注拉取数据

## 背景

当前合并附注的数据来源是通过公式引擎从**试算表审定数**（CalcBasis → node_measures → TB()/SUM_TB()）计算得出。这意味着合并附注绕开了各子企业已编制的单体附注，直接从试算表重算——导致单体附注中审计人员已确认的披露表数据、手工调整、表格结构（含合并单元格表头）等信息全部丢失。

用户要求：**合并附注必须从各子企业的单体附注拉取数据**，而非从试算表审定数直接计算。

## 现状问题

1. **数据源错误**：合并附注 `fill_by_formula()` 通过 `note_breakdown()` → `node_measures()` → `BasisResolver` 走 TB() 公式求值，数据来自各叶子节点的 `leaf_amounts`（试算表），不是单体附注
2. **章节映射缺失**：合并附注 section_id（如 `五-1-1`）与单体附注 note_section（如 `八、1`）之间没有显式映射表，仅通过中文科目名（`parent_section` ↔ `section_title`）语义关联
3. **表格结构不一致**：单体附注 `table_data` 使用 `sub_table_data`（dict rows）或 `_tables`（二维数组），合并附注 `consol_note_data.data` 使用 `headers` + `rows`（二维数组），两者行结构不同
4. **国企/上市模板差异**：单体附注按 `source_template`（soe/listed）使用不同的章节编号（国企 `八、N` / 上市 `五、N`），合并附注模板也有 SOE/Listed 之分，需要正确映射
5. **公式管理无法配置此路径**：现有公式 DSL 只有 `TB()`/`SUM_TB()`/`REPORT()`/`ROW()` 函数，没有读取单体附注的函数

## 需求

### R1：数据来源变更——从单体附注拉取

合并附注的 "🔄 重新汇总" 和 "ƒx 按公式填入" 操作，数据来源**必须**是各子企业项目下的 `disclosure_notes` 表，而不是试算表审定数。

#### R1.1 按企业树遍历各子企业的单体附注

- 通过 `TreeNode.project_id`（数据叶子指向子企业项目）跨项目查询 `disclosure_notes`
- 按 `node_key` 标识每个子企业的贡献
- 差额节点（kind=elim）的调整/抵销分录仍从 `elim_totals` 取（这部分不在单体附注中）

#### R1.2 章节映射

- 建立合并附注 `section_id` → 单体附注 `note_section` 的显式映射
- 映射依据：合并模板的 `parent_section`（中文科目名）匹配单体模板的 `section_title` / `account_name`
- 国企/上市各自映射（国企合并 `五-N-*` ↔ 国企单体 `八、N`；上市合并 `五-N-*` ↔ 上市单体 `五、N`）
- 映射关系持久化为 JSON 配置文件或数据库表，支持运行时自定义

#### R1.3 行匹配

- 合并模板的每一行（通过行标签如"库存现金""银行存款"）在单体附注的对应表中按标签匹配
- 匹配策略：精确匹配 → 去后缀 → 包含匹配（与现有 `find_row()` 三级策略一致）
- 多个子企业的同名行数值**相加**得到个别数汇总

#### R1.4 表格结构对齐

- 单体附注的 `sub_table_data` 或 `_tables` 数据需要转换为合并附注的 `headers` + `rows` 二维数组格式
- 合并单元格表头（`multi_header` / `_column_groups`）按合并模板为准
- 列对齐：通过列标签名（如"期末余额""期初余额"）匹配，不按位置

### R2：五度量恒等式保持

合并附注仍需展示四列（个别数汇总 / 调整 / 抵销 / 合并数），P2 恒等式 `individual + adjustment + elimination = consolidated` 必须成立。

- **个别数汇总**：从各子企业单体附注的对应行、对应列取数相加
- **调整**：从差额节点的调整分录计算（保持现有 `elim_measures()` 逻辑）
- **抵销**：从差额节点的抵销分录计算（保持现有逻辑）
- **合并数** = 个别数 + 调整 + 抵销

### R3：国企/上市模板适配

- 国企项目：合并附注用 `consol_note_sections_soe.json`，单体附注用 `note_template_soe.json`（章节号 `八、N`）
- 上市项目：合并附注用 `consol_note_sections_listed.json`，单体附注用 `note_template_listed.json`（章节号 `五、N`）
- 同一集团内各子企业的模板类型**可能不同**（如国企集团含上市子公司），需要按各自的模板类型查附注，然后统一映射到合并模板

### R4：前端交互

#### R4.1 现有按钮复用

- "🔄 重新汇总" 按钮（`handleReaggregate`）改为从单体附注拉取
- "ƒx 按公式填入" 按钮保留，对于有公式配置的单元格仍走公式引擎（TB/REPORT 路径），与从单体附注拉取的数据互补
- "📊 查看差额" 面板仍显示个别数/调整/抵销/合并数四列

#### R4.2 用户确认弹窗

- 重新汇总前预览：显示将要汇总的子企业列表、各子企业附注数据状态（已同步/未编制/过期）
- 汇总后展示结果：已填入的单元格数、保留手工的单元格数、取不到数的单元格数及原因

#### R4.3 stale 联动

- 子企业单体附注被修改时，合并附注对应章节标记 `is_stale = True`
- 前端显示过期提醒，引导用户重新汇总

### R5：公式管理融合

- 对于**有明确公式配置**的单元格（`consol_note_formula` 表中有记录），仍走公式引擎路径
- 对于**没有公式配置但模板行有对应单体附注行**的单元格，走「从单体附注拉取」路径
- 两条路径互补：公式优先，无公式时走单体拉取
- 公式管理面板中新增"来源"列，标明每个单元格是"公式计算"还是"单体汇总"

### R6：降级与容错

- 子企业项目不存在（`TreeNode.project_id = None`，如差额节点、汇总节点）→ 跳过，不报错
- 子企业附注未生成（对应章节 `disclosure_notes` 不存在）→ 跳过该子企业该章节，汇总结果中列出
- 子企业附注表格结构与合并模板不匹配（列名不同、行名不同）→ 列出不匹配的行/列，只填能匹配到的
- 单体附注数据为空（sub_table_data 无数据）→ 该子企业该章节贡献为 0

## 验收标准

### AC1：功能正确性

- [ ] 合并附注 "重新汇总" 后，各章节数值等于各子企业单体附注对应章节对应行对应列数值之和
- [ ] 五度量恒等式在每个单元格成立：`individual + adjustment + elimination = consolidated`
- [ ] 国企项目：合并附注 `五-1-1` 的"库存现金"行期末余额 = 各子企业 `八、1` 章节"库存现金"行期末余额之和
- [ ] 上市项目：合并附注 `五-1-1` 的"库存现金"行期末余额 = 各子企业 `五、1` 章节"库存现金"行期末余额之和

### AC2：章节映射

- [ ] 映射配置文件覆盖 SOE 和 Listed 两套模板的全部带表格章节
- [ ] 映射文件可被运行时自定义覆盖

### AC3：表格结构

- [ ] 合并单元格表头（multi_header / _column_groups）正确保持，与合并模板一致
- [ ] 合计行 = 合计行之前各数据行之和（`backfill_total_rows` 逻辑保持）

### AC4：前端交互

- [ ] "重新汇总" 操作有预览和结果弹窗
- [ ] stale 状态正确联动：单体附注修改 → 合并附注标 stale → 前端显示过期提醒

### AC5：容错

- [ ] 子企业附注未生成时不报错，汇总结果说明哪些子企业缺失
- [ ] 行/列不匹配时部分填入，不整体失败

### AC6：回归安全

- [ ] 现有合并附注公式引擎（TB/REPORT 路径）不受破坏
- [ ] 现有 280 条合并附注测试全绿
