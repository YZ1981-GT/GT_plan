# 抽凭总体完整性核对接入科目余额表 + 预览内就地放行 — 需求

## 背景（2026-10-21 用户报告：抽凭预览「确认填充」点不了）

重药控股安徽有限公司_2025（0ec33ac9）D2 应收账款抽凭：总体 37129 笔 / 3,490,246,865.45，
抽 30 笔，「确认填充」恒 disabled，tooltip 为「未执行总体完整性核对：无独立账面来源且未手工录入
账面金额…（请先关闭本预览，在下方对应区域补齐后再点操作栏的「继续填充」）」。

现状实证（代码 + 真库）：

| # | 事实 | 证据 |
|---|------|------|
| F1 | 资产/负债/权益类科目（1~4 开头）后端**从不**提供独立账面 | `voucher_sampling._resolve_independent_book_amount` 首句即对非 5/6 开头科目返回 `(None, None)`；测试 `test_asset_account_no_reconcile` 钉死该行为 |
| F2 | 损益类科目即使有独立账面也**恒判不符** | 比对的是「序时账 GREATEST(\|借\|,\|贷\|) 合计」与「试算表审定数绝对值」：安徽 6001 为 1,909,277,055.78 vs 894,804,876.83，差 113%（前者含月末结转本年利润的借方与红字冲销绝对值，后者是净额且含审计调整） |
| F3 | 完整性核对不可用 / 不符 ⇒ 阻断回填（sampling-evaluation R5.1/5.2，用户 2026-08-05 授权「阻断 + 理由放行」） | `useVoucherSampling.conclusionBlockedReason` → 引擎 `confirmBlockedReason` → 预览按钮 disabled |
| F4 | 解除方式藏在预览弹窗背后 | 理由输入框只在引擎主界面「总体完整性校验」卡片里，预览带遮罩；R5.5 明文要求「不得把提示指向被弹窗遮挡的区域」 |
| F5 | 平台已有独立且同口径的数据源：科目余额表 `tb_balance` 本期借/贷方发生额 | 安徽 1122：序时账带符号借方 1,004,440,483.35 / 贷方 907,753,272.70，与余额表 1122 行**逐分相等**；全库 8 个项目 × 8 个常用科目对账，绝大多数逐分相等，少数真实不符（和平物流 6001 序时账借方 0 vs 余额表 2.28 亿） |
| F6 | 预置理由「已与科目余额表核对一致…」恰是系统本可自动完成的核对，却要求审计师一键声明 | `GtVoucherSamplingEngine.RECONCILE_PRESETS` |

F1 + F2 + F3 叠加 ⇒ 平台上几乎**每一次**抽凭都被完整性门禁拦下，只能手填理由放行 —— 门禁退化为恒亮的噪声，
放行理由也就失去证据意义。

## 需求

### R1 自动核对改用科目余额表发生额（所有科目类别）

1. WHEN 执行抽凭 THEN 后端 SHALL 以科目余额表（与序时账分别导入）的本期借方、贷方发生额作为独立账面，资产/负债/权益/成本/损益各类科目一律适用。
2. WHEN 汇总余额表 THEN SHALL 只取所选科目范围内的**最高层行**（没有上级行也在范围内的行），不得父子行重复相加。
3. WHEN 汇总序时账 THEN SHALL 取所选科目、该年度、当前激活数据集的**全部分录**（带符号的借方、贷方合计），不受抽样筛选（期间、方向、金额区间、摘要、凭证类型、已抽排除）影响 —— 核对对象是抽样框的数据来源是否完整，筛选属于总体界定。
4. WHEN 比对 THEN SHALL 借、贷两个方向分别比对，任一方向差异超出「可容忍差异比例 × 该方向账面绝对值」即判不符。
5. 不得再以试算表审定数作为核对来源（含审计调整、且无发生额列）。

### R2 取不到时如实说明，手工录入口径明确

1. WHEN 余额表在所选科目范围内无行 / 未指定科目 / 取数失败 THEN 响应 SHALL 给出中文原因，界面在「未执行总体完整性核对」提示中展示该原因。
2. 取数失败 SHALL 不阻断抽样，且不得让同一请求后续查询因事务中止而失败（只读查询放保存点）。
3. WHEN 审计师手工录入账面金额 THEN SHALL 与序时账借+贷发生额合计比对，界面标明录入口径为「借+贷发生额合计」；手工值优先于自动取数（沿用 voucher-sampling-hardening Req2.4）。

### R3 预览弹窗内就地放行（补齐 sampling-evaluation R5.5）

1. WHEN 完整性核对未通过 THEN 预览弹窗 SHALL 在底部展示原因与「放行说明」输入框，填写不少于 10 字后「确认填充」即可用，无需关闭预览。
2. 预览内输入与主界面卡片 SHALL 是同一份状态（同一 ref），任一处填写另一处同步。
3. WHEN 阻断来源是完整性核对 THEN 按钮 tooltip SHALL 指向本窗口下方，不再要求「先关闭本预览」；其余门控（未检查样本处置 / 偏差性质 / 结论确认）提示保持不变。
4. WHEN 余额表已取到但核对不符 THEN SHALL 不提供「已与科目余额表核对一致」类一键预置理由（与系统证据矛盾）；仅在未执行核对时提供预置理由。

### R4 不改变的裁决

1. sampling-evaluation R5.1~R5.6（不可用 / 不符即阻断、≥10 字理由放行并留痕、核对通过零要求）保持不变。
2. R3（未检查样本处置）、R4（偏差性质）门控作用于「确认填充」的范围不在本 spec 内改动（见 design §6 待裁决）。

### R5 验证

1. 后端：SQLite 真实 ORM 行覆盖最高层行选取、科目前缀、数据集过滤、年度窗口、各类不可用原因、取数失败降级；端点契约覆盖新字段。
2. 真库：对安徽 1122 等科目逐值对账（与独立 SQL 结果一致）。
3. 前端：核对纯函数（逐方向判定、负数账面、手工口径）、composable 映射、门控来源、预览弹窗就地放行。
4. 浏览器：复现用户场景，核对显示一致、按钮可用；构造不符场景验证预览内填写说明即可解除。
