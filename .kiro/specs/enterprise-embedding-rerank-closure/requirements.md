# 企业向量 / 重排模型接入与知识库向量检索修通 — 需求

> 用户 2026-11-04：「LLM 模型中的向量化模型有 qwen3-reranker-4b、wemm-embedding-4b，也在致同的服务器，
> 参照之前的模型配置，key 也跟 qwen3.8 的 27B 一样，你继续修复下」。
> 现状实证与裁决见 design.md；本文件只写验收口径。

## R1 企业预设

1. `wemm-embedding-4b`（向量）与 `qwen3-reranker-4b`（重排）登记为致同企业预设，端点
   `https://ai.gt-china.com.cn:10010/v1`（与 qwen3.8 同一网关），预设只许录入 / 清除 Key 与调整信任策略，
   目的地、模型名、类型锁定，不可删除。
2. 迁移种子只写公开配置，不写任何 Key；已存在同名同类型行时不重复插入。

## R2 重排模型类型

1. 新增模型类型 `rerank`：PG 枚举、ORM、provider 支持（OpenAI 兼容 / 自定义）、配置页 tab 与类型选项。
2. 启用约束与对话一致：本机、服务器各最多一条启用（唯一索引 + 应用层兜底）。
3. 「测试连接」与启用验证真发一次 `/rerank`；调用路由面板出现「重排模型」一行并能检测可用性。
4. 没有启用的重排模型时不回落 `.env`（重排是可选增强，未配置 = 不重排）。

## R3 向量与重排调用

1. 企业向量预设请求带 `dimensions=1024`；返回维度与声明不符按配置错误报出（不静默写库）。
2. 向量与重排只发给「允许处理客户数据」的候选；没有符合政策的候选按不可用处理。
3. 启用企业向量预设后，原指向本机 8100（无 `/embeddings`）的向量行被自动停用（向量仍只一条）。

## R4 知识库索引写入可用

1. 文本向量列能容纳真实维度的向量（原 `VARCHAR(5000)` 连 1024 维都写不下）。
2. 分块 upsert 的冲突目标有唯一索引承接（原先 `ON CONFLICT` 在 PG 上必然报错）。
3. 公共文档的全局哨兵分区（全零 UUID，不是真实项目）可以入索引（原先被 `projects` 外键挡住）。
4. pgvector 扩展可用时建 `embedding_vec vector(1024)` + HNSW，只写 1024 维向量；扩展不可用时整段跳过，
   写入与检索退回文本列，二者都不得让调用方会话 aborted。

## R5 向量模型签名

1. 每个分块记录生成它的向量模型签名（模型名 @ 维度）。
2. 检索只与同签名的分块比较相似度；不同模型的向量绝不混比。
3. 存在其他签名的分块时：普通检索为业务数据补词法兜底；严格检索零命中时报「索引需按当前向量模型重建」。

## R6 重排接入检索

1. 启用重排时，`semantic_search` 各层召回放大（top_k×3，上限 50），权限过滤之后按重排分数排序再截断。
2. 结果保留原召回分（`recall_score`）并带 `rerank_score`；重排未启用或失败时保持原排序（记日志，不报错）。
3. 严格检索（DSH `kb_search`）同样重排，重排失败不改变其「向量不可用才报错」的语义。

## R7 落地与验证

1. 共享库执行本次迁移前核对待执行集合只含本次文件。
2. 两条预设的 Key 由用户在模型配置页「录入 Key」手动填写（与 qwen3.8 同一个 Key），保存与启用都写模型配置
   变更审计。（原「复制密文」口径作废：用户 2026-11-04「密文不需要复制，支持用户在前端手动输入即可」。）
3. 浏览器实测模型配置页与调用路由面板；端到端：建【测试】知识文档 → 入索引（带签名与向量列）→
   语义检索命中且重排 → DSH 严格检索命中；测试数据清理并对账。

# 第二批：范围外问题收口（用户 2026-11-04「把你所有发现的问题和建议逐一修复，按你建议来」）

## R8 审计链分叉确认与执行

1. 分叉确认工具能一次确认一条链上的多个死端：在同一事务、同一把链锁内，前置校验「未确认链尾 = 主链尾 ∪ 点名的死端」，
   不符即拒绝并列出实际链尾；写入后该链恰好剩一个未确认链尾（确认条目），否则整体回滚。
2. 死端侧枝有多条记录时，同时确认侧枝根，扫描、健康端点与链校验不再把它报成分叉；确认条目按 v2 哈希写入，
   位于 v2 链段时校验不报内容不符。
3. 只读演示输出每条被阻断链的链尾、建议主链尾（通到最新记录的那一支）、各侧枝（根、条数、时间范围、动作）与可直接执行的命令。
4. 共享库执行：先在一次性库按共享库链数据演练，再在共享库留演示记录后执行；执行后所有链未确认链尾恰为 1、
   健康端点未确认分叉为 0，被阻断期间进入隔离区的合法审计条目随重放写入。

## R9 审计队列不被坏条目卡住、测试不写共享 Redis

1. 写库前逐条校验（与写链内核同一套：用户 id、年度、时间、载荷）；不合法的条目进死信列表并记原因，
   同链其余合法条目照常写入，不再整组滞留隔离区。
2. 健康端点报告死信条目数；有死信时 degraded（审计记录未写入必须可见）。
3. 测试进程里的审计日志只许推进 fakeredis，不得推进开发环境共享 Redis（共享后端的 worker 会把测试条目写进
   共享库审计链或永久滞留隔离区）。
4. 共享 Redis 里已滞留的测试条目备份后清理。

## R10 审计链写入被拒时的接口提示

1. 审计链分叉 / 绕过写入被拒时，接口返回 503 与中文原因（本次操作未保存、需管理员处理审计链），不再是笼统的 500。

## R11 模型配置页提示与校验

1. 「不可用仍启用」的提示按模型类型与部署位置如实说明：向量（本机 / 企业预设各自的恢复条件，期间改用词法召回）、
   重排（没有兜底时期间不重排，检索照常）。
2. 已启用的企业预设重新保存时连不上，与启用同口径：保存并提示，而不是 400。
3. 未勾选「清除凭证」不算连接变更。
4. 没有录入 Key 的企业预设不能启用（提示先录入 Key）。
5. `routers/ai_models.py` 降到行数门以内（请求体与字段规范化原样移到服务层模块，行为不变）。

## R12 DSH 向量探针与实际向量路由同口径

1. `/capabilities` 健康字段与启动自检都按平台实际向量路由判定（库里启用行，没有则 `.env` 兜底；只认允许客户数据的候选），
   端点按 DSH 受信口径（`validate_dsh_upstream`）校验；不发请求。
2. 路由读不到 / 被政策挡住报 `semantic_unavailable`，端点不受信报 `local_only_violation`，并写明模型名与部署位置。

# 第三批：第二批推送后复核发现（2026-11-04）

## R14 schema 漂移检测不误报、不静默

1. pgvector 列在 `information_schema` 里是 `USER-DEFINED`：只把 `public.vector` 归一成 `VECTOR` 与 ORM 比较；
   其他 `USER-DEFINED`（业务枚举、自建 domain、`halfvec` 等）照旧按原值比较，不被隐藏。
2. 整次扫描超时 / 抛错、或健康端点读不出漂移快照时，记一条 critical 的 `scan_failure`（只带异常类型，不带可能含
   连接串的异常正文），健康端点 degraded；不再返回空列表让健康端点报 healthy。
3. 漂移快照写库失败只记日志，扫描结果照常返回给启动日志，不抛错。

## R15 审计链健康缓存只存已知结果

1. 分叉扫描失败或 Redis 不可达时该项为未知（null），这次结果不进 300 秒缓存；三项都读到的已知结果照旧缓存。
2. 只测迁移 / 漂移的既有健康用例显式声明审计链干净（mock 会话跑不了分叉扫描，扫描失败按未知处理）。
