# 三码入口一致与改上级并发保护 — 需求

来源：`docs/proposals/consolidation-three-code-tree-and-formula-chain-review-2026-11-10.md` §3.2~§3.3、§4、§5.3、§10 P1-1 / P1-2 / P1-5；按 HEAD `39777a020` 现读收窄（现状与取舍见 `design.md`）。

「三码」= 企业代码、上级企业代码、最终控制方代码（统一社会信用代码，USCC）。「写入口」= 单建项目、向导保存基本信息、Excel 批量建项 / 更新集团关系、合并总览拖拽改上级、建项授权登记。

## R1 三码规范化单一来源

1. 后端提供唯一的规范化函数：Unicode NFKC → 去首尾空白 → 转大写；结果为空串时返回 None。全角数字 / 字母、首尾空格、小写字母都按此转换后再做 USCC 校验。
2. 全部写入口先规范化再校验，入库写规范化后的值。现状是单建先转大写再校验，`create_project` 去空白后校验却写入原值，向导保存不转大写；改造后同一输入在各入口得到同一结果（同为通过或同为拒绝，入库值相同）。
3. 建项授权的代码比较（`project_creation_grant_service.normalize_company_code`）改为调用同一函数，授权判断与入库值同口径。
4. 前端提供同名同规则的规范化函数，向导三个代码输入框在失焦时写回规范化值，校验对规范化值进行。前后端用同一份测试向量文件 `backend/tests/fixtures/uscc_test_vectors.json` 验证规范化与校验结果逐条一致。
5. 中间带空格、含 USCC 字符集以外字符的输入不做猜测修复，照常拒绝。
6. 只读取方（树构建、森林、比较函数中的 `strip()`）不改：存储值已规范化，共享库现查 0 行不规范（design §1.4）。

## R2 校验与报错口径统一

1. 三码校验失败的 422 detail 统一为字符串 `"{字段}：{原因}"`，字段为「企业代码」「上级企业代码」「最终控制方代码」。企业代码报错现不带字段名，批量导入现为 `"{字段}格式错误：{原因}"`，均改为统一格式。
2. 向导保存基本信息遇 pydantic 校验失败时，已知字段以中文名列出（三码、客户名称、项目简称、审计年度等），未登记字段保留原名；不再出现英文长度错误原文。带首尾空格的 18 位代码先规范化再判长度，不因空格被拒。
3. 向导保存基本信息时，若企业代码、审计年度或报表口径与库内项目不同：企业代码须通过 USCC 校验，且按 `check_uniqueness` 判唯一，冲突返回 409（现状不校验，靠数据库唯一索引报 500）。
4. 授权类 409 的 dict detail（含 `error_code`）保持不变。
5. 向导保存基本信息时企业代码有变化（按 R1 规范化后比较），须对**新**企业代码通过建项授权：admin / partner 照建项口径直通；manager 须持有该代码的有效授权，并在年度锁之后重验；其他角色不能修改企业代码。被拒返回 403，detail 沿用授权服务的 dict 形态，message 改为「修改企业代码需要该代码的建项授权：{原因}」。上级 / 控制方代码变化不要求授权（与批量「更新集团关系」、拖拽改上级同口径）。（用户 2026-11-11 拍板）
6. 向导保存（`PUT /api/projects/{id}/wizard/{step}`）与确认（`POST …/wizard/confirm`）现只校验登录、服务层不判项目权限，任何登录用户都能改任意项目的基本信息与三码；改为要求本项目 edit 级权限（admin 直通），R2.5 的授权判断以此为前提。前端收到授权 403 或 R6 的 409 时保留表单并提示原因。

## R3 Excel 批量模板与读取

1. 模板「数据」sheet 的企业代码、上级企业代码、最终控制方代码三列，数据区设为文本格式（`@`），示例行写成文本值。
2. 读取时这三列的单元格若为数字类型（int / float），该行报错「{字段}：单元格被 Excel 识别为数字，请将该列设为文本后重新输入（读到 {原值}）」，不再把 `9.11100002e+17` 之类的字符串送去 USCC 校验。
3. 这三列若是公式且没有缓存值，该行报错「{字段}：公式没有计算结果，请在 Excel 中重新计算保存或粘贴为值」，不再按「未填」静默丢弃上级 / 控制方关系；有缓存值的公式照常使用缓存值。
4. 错误明细文件回写的代码单元格为本系统读到的原值，按文本格式写出，用户能看到被 Excel 改坏的样子。
5. 导出「更新集团关系」行必须带 `entity_group_fields_hash` 基线；删除只在缺基线时使用、且永远对不上的旧 `group_fields_hash`，缺基线视为程序错误直接抛出。

## R4 拖拽改上级的并发保护

1. `PATCH /api/projects/{project_id}/parent-code` 请求体新增必填字段 `expected_parent_company_code`（字符串或 null，null 表示调用方看到的是「无上级」）。缺字段返回 428，detail「请刷新企业树后重试（缺少改前上级）」。
2. 服务端在拿到年度拓扑锁之后，比较项目当前上级代码与期望值（两侧都经 R1 规范化），不一致返回 409，detail 为 `{"error_code": "PARENT_CODE_CONFLICT", "message": …, "current_parent_company_code": …}`，不写任何字段。
3. 合并总览拖拽请求带上节点当时的上级代码；收到 409 时提示「企业树已被他人调整，已刷新为最新结构」并重新加载森林，不重试。
4. 拒绝让客户端计算 `entity_group_fields_hash`：森林接口不返回该 hash 所需的口径与关系字段（design §2.3）。

## R5 合并差额表端点的跨项目越权

1. `POST /api/consolidation/worksheet/recalc`、`POST …/worksheet/pivot`、`POST …/worksheet/pivot/templates` 按查询参数 `project_id` 鉴权、却按请求体 `project_id` 执行。两者不一致时返回 422，detail「请求体项目与校验项目不一致」，不执行。
2. 新增 AST 守卫：路由函数既有 `project_id` 参数、又读取其他参数的 `.project_id` 时，函数内必须有两者的比较；现算违规 3 处全在本条修复，基线为 0，只许保持 0。

## R6 企业代码修改的影响检查

1. 向导修改企业代码前，服务端按**旧**代码、同一审计年度查引用：同企业另一口径项目；以旧代码为上级或最终控制方的其他项目；合并附注节点数据、附注明细映射绑定、差额表、股权变动事件中以旧代码为节点身份的记录（清单与判据见 design §2.6）。
2. 有任何引用时返回 409，detail `{"error_code": "COMPANY_CODE_IN_USE", "message": …, "impacts": [{"kind", "label", "count"}]}`，不写任何字段；没有引用时照常保存。
3. 不提供「确认后照改」：平台还没有节点身份迁移能力，照改会让下级脱挂、合并附注与映射挂在旧身份上。代码更正迁移另立 spec（design §6）。
4. 向导前端收到该 409 时弹窗列出影响项，说明不能直接修改的原因与处理方式，不重试。
5. 守卫：枚举 ORM 元数据中名为 `node_key` / `entity_node_key` / `node_company_code` 的列，每一列须在影响清单里或登记为豁免（附理由，如树版本快照、报表运行记录属历史留痕）；新增此类列未登记即打红。

## R7 重复项目与关系冲突弹窗提示

1. 保持诊断制、不阻断计算与推送（2026-10-27「计算门只校年度」裁决不变）；把 `duplicate_project` 与 `relation_conflict` 从可关闭的横幅提升为弹窗提示。（用户 2026-11-11 拍板）
2. 企业树诊断为这两类带上涉及的项目 id（`project_ids`）。
3. 进入合并工作台、企业树加载出这两类诊断时弹窗一次：逐条列出诊断文字与「企业树按哪一方取值」，每个涉及项目给「去修改」入口（打开该项目的基本信息）；「我知道了」后同一会话内同一组诊断不再弹，诊断内容变化后再弹。
4. 三个手工推送入口（合并工作台、合并推送面板、合并试算表）推送前现取企业树诊断，存在这两类时弹确认框「仍要推送 / 取消」；取诊断失败不拦推送，并在提示里说明未能检查。公式变更后的自动推送不弹。
5. 批量导入预校验对这两类已是阻断（`batch_project_plan.py:536-541`），不改。
