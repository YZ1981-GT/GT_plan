# 旧制度损益科目自动映射到新准则 6xxx — 设计

## 1 现状 grep 确认

- 匹配入口：`mapping_service.auto_suggest` → `_match_single`（优先级：坏账二级 → 全码 → 前 4 位 → 一级 → 名称精确 → 名称基础 → 模糊）。
  `auto_match` 只为**未映射**的客户科目写入，已有映射不改。
- `mapping_service.py` 现 1014 行，超 800 且未登记白名单 ⇒ 对照表放新模块，`mapping_service` 只加接线，登记白名单。
- `report_config` 四套标准的利润表公式 0 行引用 5xxx（现扫）⇒ 把损益映射到标准 5xxx 对报表永远是死路。

## 2 方案

新模块 `app/services/legacy_pl_crosswalk.py`（纯函数，无 DB）：

- `PL_CROSSWALKS = {"enterprise_system_2001": {...}, "small_enterprise_2013": {...}}`：一级码 → 新准则码。
- `detect_legacy_pl_crosswalk(client_codes) -> (system, crosswalk) | None`：按 R2 判定。
- `crosswalk_target(code, crosswalk) -> str | None`：取编码归一后的前 4 位查表（`1001.0` / `5101.01` / `510101` 均可）。

`auto_suggest` 对整张客户科目表判定一次，结果传给 `_match_single`；`_match_single` 在坏账二级之后、全码匹配之前查对照表，
命中且目标码在标准科目表里 ⇒ 返回 `match_method="legacy_pl_crosswalk"`、置信度 0.99（落 `auto_exact`）。

### 判定为什么只看编码、为什么要「≥ 2 且严格多于」

- 名称不可信（真库整体错位）。
- 新准则账套也有 5001 生产成本 / 5101 制造费用 ⇒ 单个 5xxx 码不能定体系；只有成本类的新准则账套最多各命中 1 个
  （5001 → 小企业、5101 不是特征码），不满足 ≥ 2，不会误套。有 6xxx 损益码的直接排除。

## 3 存量修复

一次性脚本 `backend/scripts/fix/_fix_legacy_pl_mappings.py`（用完即删）：对指定项目复用同一判定与对照表，列出
「现映射 ≠ 对照表结果」的行；`manual` 不改只列出；`--apply` 时先把涉及的 `account_mapping` 与该项目全部 `trial_balance` 行
写入 `backend/backups/`，再改映射、`full_recalc`、提交。脚本不经事件总线 ⇒ 已生成的审定报表不会自动标待更新，需手工重新生成。

集成（5101→6001、5501→6601、目标码缺失回退原逻辑、新准则账套不受影响）。

## 5 实施中发现：合计行排在明细之前时恒为 0（已修）

映射修好后营业收入 38,599,110.27，但「一、营业总收入」「二、营业总成本」仍是 0。根因与映射无关：
报表引擎按 `row_number` 单遍求值，行值写进 `row_cache` 供后续 `ROW()` 读取；国企模板（standalone / consolidated
各 2 行：IS-001、IS-007）的合计行排在被引用的明细之前 ⇒ 读到空缓存静默得 0。上市模板无此形态。
已生成的审定报表里这两行同样是 0（两个项目都是）。

修法：新模块 `app/services/report_row_order.py` 的 `evaluation_order(configs)`：被 `ROW` / `SUM_ROW` 引用的同表行先算，
无前向引用时与按行号排序完全相同，循环引用按原顺序（不报错）；`SUM_ROW` 区间口径与求值内核一致（行次字符串落在 [起, 止]）。
`report_engine` 四处求值循环（全量生成 / 未审 / 过期行重算 / 增量重算）改用它；全量与未审两处的输出用
`_in_row_number_order` 恢复行号顺序（前端与导出按列表顺序展示）。测试 `backend/tests/test_report_row_order.py`。
