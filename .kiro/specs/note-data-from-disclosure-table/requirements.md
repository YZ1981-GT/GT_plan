# 附注数据统一从披露表获取 — 需求文档

## 背景

当前平台附注模块有两条数据管道：

1. **前端同步（管道 A）**：审计师编辑底稿披露表 → 前端 69 个 `buildXSyncPayload` 把披露表全部行（含动态行）打包 → POST `sync-from-workpaper` → 整表写入 `disclosure_notes.table_data`。**行完全动态，能正确处理浮动区域**。

2. **公式推送（管道 B）**：TB 更新/调整审批 → `formula_push.engine` 从**试算表直接取审定数** → 按标签匹配附注已有行 → 写值不建行。80 条附注域规则全部是 `derivation` 类型，79 条只推 `end_amount + prior_amount` 两个字段。

**核心问题**：管道 B 绕过了披露表，直接从 TB 取数写附注。这与正确的数据流不一致：

```
四表(TB) → 调整分录(AJE/RJE) → 审定数 → 底稿披露表 → 附注
                                          ↑ 唯一权威源
```

披露表是审计师审定后的产物，包含按准则要求的分类结构、动态行、国企/上市不同样式。附注必须从披露表获取数据，不能绕过它。

## 需求

### R1：数据流统一 — 附注从披露表获取，不直接取 TB

- R1.1：附注的所有数值数据必须来源于底稿披露表（`working_paper` + `wp_entries`），不得直接从 `trial_balance` 取数
- R1.2：公式管理中的预设公式的 source 定义为「从哪个底稿的哪个子表、哪行、哪列取值」，不再是 `TB('科目号','列名')` 表达式
- R1.3：当披露表数据更新时（底稿保存事件 `WORKPAPER_SAVED`），自动触发附注刷新

### R2：动态行处理 — 附注行结构跟随披露表

- R2.1：附注子表的行由披露表的实际行决定（如应收账款按账龄有几行就有几行，组合有几个就建几张子表）
- R2.2：公式推送引擎需具备「按披露表行列表动态建/更新附注行」的能力，不再限于 `"公式推送不新建行"`
- R2.3：删行：当披露表删除了某行时，附注对应行应标记为空值或移除（不能残留旧数据）
- R2.4：合计行由引擎自动按数据行求和，不单独推送

### R3：公式管理配置 — 预设公式对齐披露表

- R3.1：80 条现有附注域规则需修订为从披露表取数的形式
- R3.2：规则的 `source` 改为引用底稿披露表的 `sub_table_data` 结构，按子表名 + 列 key 定位
- R3.3：国企/上市的差异通过 `table_by_template`（不同子表名）和 `fields_by_template`（不同列）处理
- R3.4：公式管理面板展示「数据来源：披露表 → 附注」的映射关系

### R4：刷新性能 — 避免打开底稿才能同步

- R4.1：`WORKPAPER_SAVED` 事件触发时，后端直接读取披露表已保存的 `sub_table_data`，不依赖前端 payload builder
- R4.2：刷新操作应在 2 秒内完成单个科目的附注更新（含读取披露表 + 写入附注）
- R4.3：批量刷新（全部科目一次性）应在 10 秒内完成
- R4.4：手动「刷新附注」按钮可一键从所有关联披露表重新拉取数据

### R5：管道 A/B 协同 — 不冲突

- R5.1：管道 A（前端同步）和管道 B（公式推送/刷新）写入的数据源相同（都是披露表），值必须一致
- R5.2：管道 A 推送的行结构（动态行）是管道 B 写值的基础——先有行结构，再有值
- R5.3：当管道 A 尚未同步过（用户从未打开过披露表）时，管道 B 应能独立从后端读取披露表数据并建立附注行结构
- R5.4：两条管道对同一单元格的写入不应产生覆盖冲突（都读同一数据源，值相同）

### R6：合并附注的联动

- R6.1：合并附注的子公司维度数据同样从各子公司的披露表获取
- R6.2：合并层面的抵销/汇总仍走 consolidation engine，但子公司个别数来源于子公司披露表
- R6.3：集团统一附注模板（行结构）暂不在本 spec 范围，后续另立 spec

## 约束

- C1：不改变 `disclosure_notes.table_data` 的 JSONB 存储结构（`sub_table_data` / `_sub_table_columns` / `_tables` 三种格式兼容）
- C2：前端 69 个 `buildXSyncPayload` 继续作为管道 A 的前端同步路径，不删除
- C3：公式推送引擎的基本架构（规则 → 匹配 → 写入 → 状态记录）保留，只改数据来源
- C4：单体附注和合并附注的模板 JSON（本次已补全 `multi_header`）保持为渲染模板的权威源
- C5：用户手工编辑的单元格（`_cell_modes: manual/locked`）和整节人工覆盖（`_manual_override`）的优先级不变
