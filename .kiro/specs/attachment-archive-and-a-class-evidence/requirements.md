## 需求 1　归档包按数据库清单构建

1.1 归档时按数据库生成项目清单，打成一个包：未删除底稿的文件（必须是本项目自己的文件；指向模板库的、路径为空的视为「未生成文件」，只收数据快照）、每张底稿的数据快照（`parsed_data` + 核对表填写）、现行版本附件（未被新版本取代）、已确认 / 已签字 / 已归档的交付件、归档章节（各章节生成器的产物）。
1.2 清单里任何一项读不到（文件不存在、路径越界、类型不符、Paperless 取不到、章节生成器报错）⇒ 打包失败，任务失败，失败原因逐项列出（底稿编码 / 附件名 / 交付件名 / 章节名 + 原因）；章节生成器返回空 = 不适用，清单记「跳过」。
1.3 包内 `manifest.json` 逐项记录类别、来源 id、包内路径、字节数、sha256；任务 `manifest_hash` = `manifest.json` 的 sha256；完整性记录登记包文件路径与 sha256，`verify_package(任务 id)` 能复核。
1.4 包存平台存储；任务成功后提供下载（项目成员只读及以上），向导「下载归档包」可用。

## 需求 2　归档失败即失败，成功才锁定

2.1 打包、云端推送、项目锁定任一步失败 ⇒ 任务失败并记录失败步骤与原因；只有通知失败不影响结果。
2.2 云端推送上传的是归档包本身，上传失败抛错（不再上传 `storage/projects` 目录、不再吞异常）。
2.3 全部步骤成功 ⇒ 项目状态改为「已归档」、写归档时间与保留期，项目内未删除底稿状态改为「已归档」；之后项目内编辑一律被锁（现有锁定判据）。
2.4 每步进度（`section_progress`）真实落库；重试从第一个未成功的步骤继续。
2.5 删除不再有调用方的旧实现（`WpStorageService.archive_project`、`ProjectArchiveService`）。
2.6 门禁与归档向导「下一步」同一口径（就绪检查通过、完整性自检无阻断项），服务端每次现算，不以客户端带来的评估结果放行（走查补）。
2.7 解除归档是锁定的逆操作：底稿恢复归档前状态（归档期间被改过的不动）、清归档时间与保留期；解除后再归档重新执行；归档横幅的「解除归档」可用（填原因、输入项目名称确认）（走查补）。

## 需求 3　旧端点下线与归档路由鉴权

3.1 删除需求表所列 3 个旧归档端点；守卫断言它们不再注册。
3.2 归档任务查询：项目成员只读及以上；重试：归档管理权限 + 二次密码确认（与启动同级）；任务不属于该项目 ⇒ 404。

## 需求 4　二次密码确认真正可用

4.1 密码错误不返回 401（改为 403 + 错误码与剩余次数），前端不再因此刷新令牌、登出或重复计数；锁定仍返回 423 与解锁时间。
4.2 前端提供编程式确认：弹出现有「安全验证」对话框，确认后返回一次性令牌，取消返回空；密码错误 / 锁定在对话框内提示，不弹全局错误。
4.3 启动归档、重试归档、签字（`PartnerSignDecision`、`PartnerDashboard` 经 `signDocument`）都先确认再带 `X-Confirmation-Token` 发请求；取消即不发请求。`SignatureBlock` 的签字载荷与后端签字接口不兼容，不在本 spec（design §14-1，待拍板）。
4.4 向导取任务 id 读接口真实字段 `id`，轮询、重试、下载都用它。

## 需求 5　归档完整性检查补 5 类

5.1 新增类别：证据缺口（证据声明未满足，提示）、未回函（函证底稿的未回函笔数，提示）、OCR 未确认（附件识别结果未人工确认，提示）、文件缺失（底稿 / 附件 / 交付件被引用但读不到，阻断）、孤儿文件（附件存储目录下本项目没有任何附件行引用的文件，提示）。
5.2 文件缺失与打包用同一份清单判定（同一实现），检查通过的项目打包时不会再因缺件失败（除非期间文件被删）。
5.3 所有类别在界面显示中文名称；失败步骤显示中文名称。

## 需求 6　QC-17 按证据声明判定

6.1 QC-17 改为：底稿有证据声明且有未满足的类型 ⇒ 出结论，列出缺哪几类（与附件抽屉「应收集证据」同一判定，含函证逐笔拆分）；无声明的底稿不出结论。
6.2 严重程度保持阻断（规则本意是证据充分性；改为提示属于行为变更，不在本 spec）。

## 需求 7　A 类签字件

7.1 新增证据类型「签字件」（`signed`），后端附件类型登记、证据入口类型、前端证据类型选项三处一致（守卫互相钉住）。
7.2 声明键支持精确匹配写法 `=编码`（只匹配该编码本身，不被 `编码-x` / `编码字母` 继承）；精确键优先于前缀键。
7.3 声明签字件：A16 管理层声明书（精确）、A10 与治理层沟通（精确）、A10-1、A9-1、A9-2、A8-1、A17-6 总结会会议纪要、A17-7（含 A17-7A）独立性声明书、A18-1、A18-2；不声明 A1-11（平台自有签发流转表单）与 A16-1~7（由 A16 承接）。
7.4 入口复用附件抽屉「上传此类证据」与工具栏「关联附件」，不新建页面。

## 需求 8　A30 电子底稿归档检查表可用

8.1 解析 `A30 电子底稿归档检查表.xlsx`：每个底稿编码一行（编码去空格，如 `A 1-11` → `A1-11`），名称带 `*` 的为必备项，按循环字母分节（A 完成阶段 … N 税费）；重复编码第二次出现加后缀区分；遇页脚（「项目合伙人：」/「填表说明」）停止。
8.2 「按项目底稿建议」：项目里有该编码的未删除底稿 ⇒ 建议「是」，否则「否」；只填空项，已填的不改；与建议不一致的已填项列出提示，不覆盖。
8.3 只读时不能填写与应用建议。
8.4 「是 / 否 / 不适用」能保存；「本章节批量标记」的选项与结论选项一致；章节适用性首次确认即落库，只读时不弹（走查补）。

## 需求 9　回收站彻底删除同步删物理文件

9.1 单条、批量、清空回收站三种彻底删除附件：提交成功后删除本地物理文件，前提是文件在附件存储根目录内，且没有其他附件行（含已删除的）引用同一路径；Paperless 文档不删。
9.2 删除文件失败只记日志与返回提示，不回滚已提交的删除。

## 非目标

- 归档改后台异步执行（仍在请求内同步执行，前端放宽超时）；
- QC-17 降级为提示、规则严重程度可配置；
- 抽凭证据绑定（Spec D）、合同检查（Spec F）、证据治理收尾（Spec G）；
- 真实项目缺失底稿文件的修复（完整性检查如实列出，由用户重新生成）。
