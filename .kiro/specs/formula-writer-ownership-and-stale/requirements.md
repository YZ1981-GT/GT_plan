# 需求文档：S3　写入方归属与过期状态机

> **本 spec 由 `formula-hub-integrity-closure` 按需求 17.5 创建（design §8.1 的 S3 交接）。**
> 本版根据当前代码树复核结果重整。原设计基线与当前 HEAD 不同，所有数量、调用点和文件清单以任务 0 的现算产物为准，禁止把现算快照当成永久分母。
>
> 本轮先收口三件套与实施契约，不执行附注权威源 D1 拍板，不直接修改生产代码。生产实现必须在三件套通过复核后进行。

## 1. 负责范围

### R1：附注写入方登记与唯一写方矩阵

R1 分两阶段交付：

- **R1a，立即可做：写入方登记表冻结。** 登记所有会写 `DisclosureNote` 的后端入口，以及前端 `*SyncPayload` builder 的对应入口。登记内容至少包括稳定 `writer_id`、入口模块与函数、触发方式、作用域、标准类型、写入字段、是否尊重 `_cell_modes`、事务边界和当前实现状态。
- **R1b，依赖 D1：唯一写方强制。** 按「章节 × 规范字段」矩阵指定唯一自动写入方。矩阵必须明确 `template_type`、章节、表/字段键、writer_id、manual/locked 行为和未知矩阵项行为。手工保存是否绕过自动写方必须与 locked 的语义分开定义。

R1 不接受只登记函数名但无法定位实际写入的实现。ORM 赋值、SQLAlchemy `update().values(...)`、原生 SQL、JSONB 原地修改、`flag_modified` 和统一写入门面均属于写入路径。

### R2：附注过期状态机

仅管理 `disclosure_notes.is_stale` 与 `disclosure_notes.stale_source`，不扩展到没有来源列的 `consol_note_data` 和底稿预填状态。

- 所有新产生的附注过期标记必须同时写入稳定的 `stale_source` 编码；历史已有 `stale_source IS NULL` 的 227 行不回填，界面显示「过期（来源未记录）」。
- 标记和清除必须经统一的 `stale_state` 写入口；入口只使用调用方当前事务，不自行创建会话、提交或吞掉事务错误。
- 清除过期必须清除 `stale_source`；本次失败诊断只存在于结果和结构化日志中，不得残留为下一轮会误读的 stale 状态；值没有变化但本章节计算成功时，仍必须清除过期。
- 计算失败或部分失败时必须保留过期状态，并返回可定位的失败章节和中文原因；失败原因不得依赖下一次 `table_data` 重建仍然存在。
- 前端附注状态接口和页面必须显示来源中文名称、未知来源兜底和未记录来源状态。

所有重算入口必须返回可区分的结果集合：

```text
requested_sections    请求处理的章节
changed_sections      金额或表格值发生变化的章节
recomputed_sections   计算成功的章节，值不变也包含在内
failed_sections       计算失败或部分失败的章节
cleared_sections      实际清除 stale 的章节
errors                章节级中文错误
```

`cleared_sections` 只能来自完整计算成功的章节，不能仅根据「有值变化」或「函数未抛异常」推断。

### R3：试算平衡表手工值读回

- 试算平衡表持久化读取必须以合并工作底稿端点返回的 `content.rows` 为准；不得恢复到旧的 `saved.data.rows` 读取方式。
- 必须保留并读回手工未审数、重分类借/贷、`formula_detached` 及相应手工标记，零值不能因真假值判断丢失。
- 保存使用服务端返回的版本号和 CAS 语义；非 2xx 不得显示成功。
- 页面刷新后必须逐行读回并核对手工值和断开公式标记。本 spec 不强制每次保存后额外 GET；若实现需要即时服务器反读，应另行增加明确的性能与一致性验收。
- 如果当前代码已经满足以上行为，任务只做核验和回归，不重复建设另一套持久化链路。

### R4：前端写请求按状态码判成功

- 前端所有经 AST 判定为 `POST`、`PUT`、`PATCH`、`DELETE` 的写请求，不得用「`status < 600`」等宽放行把 4xx/5xx 当作正常返回。
- 业务确实需要接受非 2xx 的调用必须逐状态码列举，并在调用处处理该状态；GET 请求的合法兼容逻辑不纳入写请求违规。
- 精确分母由任务 0 的 TypeScript AST 探针生成，requirements 不再写死“14 处”。探针必须解析 `api`、`http`、`httpApi` 等导入别名和包装客户端。
- 写入失败必须进入统一错误处理，不得显示成功 toast、清除 dirty 状态或推进本地版本。

## 2. 依赖与先后

- R2、R3、R4 和 R1a 不依赖附注权威源拍板，可以先实施。
- R1b 依赖 D1：附注权威源仍需在「留前端」与「经公式管理自动推」之间按章节交接并形成可执行决议。未拍板前只冻结登记表，不拦截生产写入。
- 已完成的 `formula-settings-durable-outbox`（S4）是 R2 的必接入方。S3 落地时必须把 S4 的附注过期标记改调统一入口，不能保留第二套 `DisclosureNote.is_stale` 写法。
- `formula-hub-integrity-closure` 已交付部分不回填重写；仅为接入统一状态机、补当前树的调用方和测试所需的最小改动除外。

## 3. 触发条件

- 当前任务启动时先执行任务 0 的现状重算；
- stale 误报、漏报、来源缺失或值不变重算后仍显示过期；
- 试算平衡表手工值刷新后丢失；
- 任一前端写请求因宽放行而把失败提示成成功；
- D1 拍板后启动 R1b 唯一写方强制。

## 4. 验收边界

- 新产生的 `disclosure_notes.is_stale = true` 行，经过真实写入路径后 `stale_source` 非空率必须为 100%；存量无来源行单独统计，不得混入该分母。
- 值不变的真实重算路径必须清 stale，并返回 `recomputed_sections` 与 `cleared_sections`；计算失败的章节必须仍为 stale。
- S4 outbox 的同事务语义必须验证：定义事务回滚时，附注 stale 标记不得单独提交；投递失败只影响重试状态，不伪造成功清 stale。
- 前端浏览器验收必须覆盖试算表刷新读回、附注来源展示和写请求失败提示。

## 5. 不属于本 spec

- 不执行 D1 权威源拍板本身；
- 不回填历史 227 行 `stale_source`；
- 不为 `consol_note_data` 或底稿预填新增来源列；
- 不重建已经存在的试算表 CAS/持久化模块；
- 不修改 `formula-hub-integrity-closure` 的历史档案内容；
- 不把前端 `validateStatus` 的 GET 兼容逻辑一并删除；
- 决策项 X1~X5（共享库迁移与推送、存量归属行升级、真实项目重算、门禁切 enforce、D1~D15 默认值）仍由用户或母 spec 决定。
