# Phase 0 Task 0.7 — Property 1 裁决报告

> tasks 0.7 原文：「**先验 P1**（净额拆分 ≡ 现有 `aje_dr - aje_cr`），
> 若不等价则本任务停下来报告差异，**不得擅自改口径**。」
>
> 本文件即该报告。可执行形态见 `backend/tests/test_adj_caliber_property1.py`（7 passed）。

## 结论：P1 不成立

等价性边界**恰好是科目方向**，与金额大小、借贷方向无关：

| 科目方向 | 现有口径 `dr − cr` | 归一口径 `net` | 等价 |
|---|---|---|---|
| 借方正常（资产/费用） | `+(dr−cr)` | `+(dr−cr)` | ✅ |
| 贷方正常（负债/权益/收入） | `+(dr−cr)` | `−(dr−cr)` | ❌ **符号相反** |

差额恒为 `2 × |原始净额|`。实测样例：

| 科目 | 类别 | 分录 | 现有口径 | 归一口径 | 差额 |
|---|---|---|---|---|---|
| `1001` 库存现金 | 资产 | 借 500 | `+500` | `+500` | 0 |
| `1001` 库存现金 | 资产 | 贷 120 | `−120` | `−120` | 0 |
| `2202` 应付账款 | 负债 | 贷 800 | `−800` | `+800` | 1600 |
| `2202` 应付账款 | 负债 | 借 300 | `+300` | `−300` | 600 |
| `6001` 主营业务收入 | 收入 | 贷 10000 | `−10000` | `+10000` | 20000 |

## 哪个口径正确：归一口径

三条独立依据，均来自平台既有约定而非本轮判断：

1. **v2 存储约定**：`trial_balance.unadjusted_amount` 按 `category_natural_positive`
   存**自然正数**（收入类贷方余额存为正数）。调整额要与它相加，就必须同为自然方向。

2. **同文件参照实现的注释**（`trial_balance_service.py` L405-416，`recalc_adjustments`）：
   > v2 约定（category_natural_positive）：调整净额 SUM(debit)-SUM(credit) 是"借正贷负"，
   > 但 unadjusted_amount 已按科目自然方向存正数（Task 3.1）。**对贷方正常类（负债/权益/
   > 收入），一笔贷记增加应使审定数增大，若直接相加"借正贷负"净额会方向反掉**

   并据此实现 `row.aje_adjustment = sign * vals["aje"]`。

3. **业务语义**：应付账款贷记 800 = 负债增加 800 ⇒ 审定数应比未审数**大** 800。

⇒ `get_summary_with_adjustments` 用的 `audited = unadj + aje_dr − aje_cr`
**正是上述注释警告的那个未修形态**。它是 `recalc_adjustments` 的孪生体，
但 `adj-formula-repair-and-approval-gate-wiring` 只修了后者。

## 🔴 新增缺陷 B4

原 spec 记录了 B1（无 status 过滤）/ B2（无 origin 过滤）/ B3（查主表遗留列）。
本次 P1 验证新发现第四个：

| 编号 | 缺陷 | 后果 |
|---|---|---|
| **B4** | `audited = unadj + aje_dr − aje_cr` 用**未归一**净额 | 贷方正常类科目（负债/权益/**收入**）的审定数**方向反掉** |

**B4 独立于 B1~B3**：即便把 status/origin/明细表三处全修好，只要审定数仍用
原始 `dr − cr`，贷方类科目的审定数依然是错的。

### B4 直接解释了截图现象

截图：`IS-001 一、营业收入` 审计调整**贷方** 10,000、审定数 **−10,000**。

- `unadj + dr − cr = 0 + 0 − 10000 = −10000` ← 与截图逐字吻合
- 修正后应为 `0 + 10000 = +10000`（收入增加）

（注：该行的科目归属本身也错 —— 那笔 10,000 的科目是 `1122` 应收账款，
属 B3 的科目错配。B3 与 B4 在此叠加。）

## 对实现的裁决

**采纳「显示列用原始借贷、审定数用归一净额」**（即 ADR-ADJ-005 的双口径并存）：

```
aje_dr 列 ← adj_net_batch()[code]["aje_dr"]    # 原始借方，恒非负，与凭证逐字一致
aje_cr 列 ← adj_net_batch()[code]["aje_cr"]    # 原始贷方，恒非负
audited  ← unadj + aje_net + rje_net           # 归一净额，方向正确
```

### 已知副作用：视觉上「列加起来 ≠ 审定数」

对贷方类科目，审计师会看到 `未审数 + 借方 − 贷方 ≠ 审定数`。这是**归一口径的必然结果**，
不是新引入的错误（`trial_balance` 的 `aje_adjustment` 持久化列早已是归一值，
底稿审定表一直如此展示）。

⚠️ **此副作用需要产品侧决定如何呈现**，可选：
- (a) 保持现状，在列头加 tooltip 说明"审定数按科目自然方向计算"
- (b) 增设「调整净额」列（折叠调整列时已有此形态，见 `tbSumCollapseAdj`）
- (c) 贷方类科目的借贷列按归一后符号显示（会与凭证不一致，**不推荐**）

本 Phase 0 **只修正确性，不改 UI 呈现**；(a)/(b) 留给 Phase 3 决策。
前端现已有 `tbSumCollapseAdj`（折叠调整列 → 单列净额）开关，
折叠态下该副作用天然不可见。

## 对 spec 的勘误

`design.md` §五 Property 表原文：

| P1 | 净额拆借贷 ≡ 现有 `aje_dr - aje_cr` | 对同一批分录，两种算法结果逐行相等 | 方案 D 的前提假设，设计阶段无法凭空断言 |

⇒ 应改为「**P1 已验证为不成立**；等价性边界 = 科目方向；裁决采纳归一口径并
新增缺陷 B4」。设计阶段把它列为"必验项"而非"已知真"是正确的 —— 若当时直接假定
等价并据此实现，会把 B4 固化进新代码。
