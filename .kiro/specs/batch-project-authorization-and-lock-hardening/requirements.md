# 需求：批量建项授权与拓扑锁加固

## 范围与裁定

承接 `batch-project-import-and-consol-tree-closure` 复盘。当前平台没有客户主数据或公司级授权，单项目创建仅校验登录，批量 apply 仍可用成功/冲突探测任意 USCC；年度项目行锁不能锁空年度，也未覆盖其他集团关系写入口；status 锁等待无上限；浏览器竞态仅有临时桩测。

本 spec 采用以下产品裁定：

- admin、partner 保留全局建项能力；partner 仍不能管理系统授权。
- manager 只能为获得**精确 USCC 建项授权**的企业创建项目；不支持前缀、模糊或集团通配。
- 授权仅由 admin 管理；存量 manager 从本人 active edit 项目的合法 USCC 幂等回填。
- auditor、qc、eqcr、readonly 不得创建单项目或批量项目。
- 经理首次承接新客户时，必须先由 admin 授权；这是消除存在性 oracle 的必要流程变化。

## R1 公司建项授权

1. 新增授权表，记录 grantee、精确 company_code、有效期、版本、grant/revoke 操作者、原因和软删除状态；活动授权 `(grantee_user_id, company_code)` 唯一。
2. 授权目标必须是未删除、已启用的 manager；USCC 必须通过平台统一校验。
3. admin-only API 支持列表、批量授予和撤销；授权与撤销必须审计，重复授予幂等。
4. manager 的普通新建行必须授权 company、parent、ultimate 中每个非空代码；自动根代码同样须授权。update 行仍以项目 edit 为准，不因建项授权获得已有项目权限。
5. 未授权必须在任何全库项目、唯一性或企业树查询之前统一 403；公开响应只包含调用方提交的代码，不暴露库存是否存在。
6. 持久计划保存授权 ID/version/有效期摘要；apply 先锁并重验授权，撤销、过期或换版本统一 `BATCH_PLAN_STALE`，零业务写。
7. 单项目 `POST /api/projects` 与 batch validate/apply/legacy import 共用同一授权服务；manager 创建后同事务写本人 manager/edit 成员，不能信任请求体伪造的 manager/signing partner。

## R2 防枚举与审计

1. batch validate、legacy import 和单项目创建按 actor 使用 Redis 固定窗口限流；默认 30 次/分钟，可配置，超限返回 429、稳定错误码和 `Retry-After`。
2. Redis 不可用时限流 fail-open，但公司授权门仍 fail-closed；不得降级成全局可创建。
3. 授权拒绝只记录代码集合 SHA-256、数量、入口和 actor，不把原始 USCC 写入普通日志。

## R3 状态锁有界等待

1. status 保留锁定读；PostgreSQL 等待计划行锁最多 1500ms，超时只映射 SQLSTATE `55P03` 为 503 `BATCH_PLAN_STATUS_BUSY`，响应带 `Retry-After: 1`。
2. lock timeout 必须置于 SAVEPOINT 内并回滚保存点；不得 fallback 普通 SELECT、`SKIP LOCKED` 或把计划标 failed。
3. 前端收到 busy 保留 sessionStorage 计划并有限重试；后续能读 applied/failed 终态。

## R4 集团拓扑锁

1. 新增 PostgreSQL 事务级年度 advisory lock，按年度升序获取；SQLite 测试环境 no-op。
2. 锁必须在第一次集团拓扑读取和关系字段写入前取得，覆盖 batch apply、拖拽改上级、显式关系更新、建项/删除/恢复/改年度或口径后重算等生产入口；静态守卫冻结调用范围。
3. 暂不按 ultimate/group 细化。集团边界由可变关系字段推导，跨组移动与整年度 `sync_group_links` 使简单分组锁不安全。
4. 真 PG 测试证明空年度也互斥、不同年度可并行、反向改上级最终不会双提交成环。
5. 20 个不同集团同年度基准记录 wait p50/p95/max 与临界区并发；只量化年度串行代价，不以放宽正确性换速度。

## R5 管理界面与正式浏览器回归

1. 用户管理页增加“经理建项授权”卡片：经理筛选、精确 USCC、有效期、原因、授权人、状态；授予和撤销均二次确认，所有文本中文。
2. 新增专用 Playwright synthetic 配置，workers=1、retries=0、阻断未知 API/WebSocket，不运行全局 seed、不写真库。
3. 正式 E2E 覆盖模板下载、延迟 status 与新文件竞态、failed stale 换新键、500 节点 DOM<50/滚到末项/Long Task=0、390px 无横向溢出，并带 Long Task 忙等自检。
4. 后端覆盖 SQLite/PG、真实 TestClient 鉴权、迁移正反向、授权撤销竞态、限流与审计；前端覆盖 API 与管理 UI。写入验收只使用【测试】数据并精确清理。

## R6 人员档案绑定登录账号（用户 2026-10-31 裁定）

1. 用户管理页提供“人员档案”列与绑定 / 解除绑定入口，仅 admin 可用；后端提供列表、绑定、解除绑定接口。
2. 一个启用账号最多绑定一个未删除人员档案，一个人员档案最多绑定一个账号；目标账号须已启用、未删除，人员档案须未删除且未离职。重复绑定同一对幂等；任一方已有其他绑定返回 409，须先解除原绑定。
3. 绑定时，该人员在未删除项目上的有效委派立即生效：为缺失的项目成员行按委派角色映射补建，已有成员行不改；受影响项目递增可见性策略版本。
4. 解除绑定须带当前人员档案 ID 做并发校验；人员仍在未删除项目的团队中时返回 409 并列出项目，不改任何数据。
5. 绑定 / 解除绑定写审计，只记录人员档案、账号与项目数量。
6. 既有 `GET /api/staff/me/staff-id` 的按名称自动关联须遵守同一规则：只关联唯一、未绑定、未离职且没有有效委派的同名人员档案；同名档案不唯一或已有委派时返回 409 提示联系管理员，不得把已绑定他人的档案改绑到当前账号；完全无同名档案时保持自动创建。
7. 绑定不得让同一账号在同一项目既是独立复核（EQCR）又担任其他角色（含无档案经理建项时写入的成员行），冲突时 409 并列出项目。
8. 绑定 / 解除绑定与保存项目团队并发时互相等待，结果与先后提交顺序一致：不漏建成员行，解除后不残留按该档案写入的成员行；人员作为程序行执行人 / 复核人的项目同样递增可见性策略版本。

## R7 经理没有人员档案时的建项兼容（用户 2026-10-31 裁定）

1. 经理没有绑定人员档案时，单建、批量执行、旧版导入、连续审计和自动创建的合并根照常创建，创建者只写项目成员（经理、编辑权限），不写团队委派记录；`manager_id` 仍为本人。
2. 绑定了多个人员档案属于数据异常，继续拒绝（403）。
3. 有唯一人员档案时行为不变：写团队委派并由委派同步项目成员。
4. 建项被拒（如授权已撤销）时，建项向导与「创建下年」显示后端给出的原因，向导保留已填内容、可直接重试（6.2 实测发现：原先只提示「权限不足」，且整页被错误边界替换）。

## R8 创建者可见本项目底稿（用户 2026-10-31 裁定）

1. 项目创建者（`Project.created_by`）按主管待遇看到本项目全部循环的底稿，无论其是否有人员档案或委派。
2. 创建者后来被移出团队（成员行删除）时不再按创建者放行（仍按普通成员规则）。

## R9 删除项目按项目授权（用户 2026-10-31 裁定）

1. 软删除单个 / 批量项目改用项目级 `edit` 权限（admin 跳过、其余须是本项目的 edit 级成员），不再只按系统角色放行。
2. 前端删除按钮对无权限的用户不可见或禁用。

## R10 建项向导新建分支恢复（用户 2026-10-31 裁定）

1. 新项目创建成功后依次显示：建项引导（showGuide `project_create`）、公式模板订阅提示、合并项目的「配置合并范围」弹窗。
2. 引导取消或「稍后设置」后正常进入项目列表或合并模块。
3. 新项目仍应通过 `confirmProject` 进入 planning 状态。

## R11 创建者不给本人发委派通知（用户 2026-10-31 裁定）

1. 单建经理有人员档案时改走与批量相同的 `initialize_project_managers`（创建者不给本人发通知）。
2. 新项目无缓存，不需要递增策略版本或发 SSE。

## R12 回收站永久删除不吞失败（用户 2026-10-31 裁定）

1. `_cascade_delete_project` 的逐表删除失败不再被 `except: pass` 吞掉：在同一连接、同一事务里按 FK 拓扑排序删除，任一步失败回滚并向调用方报错。
2. 永久删除的前端显示具体失败原因（不只是「已永久删除」）。
