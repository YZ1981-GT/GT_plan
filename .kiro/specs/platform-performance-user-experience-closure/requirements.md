# 平台性能与用户体验闭环 — 需求

来源：用户 2026-10-29 在本机、运行环境、数据库与前后端只读体检后决定「按建议来」，实施顺序固定为：遗留容器治理与稳定运行模式 → 辅助明细索引和 COUNT → 表膨胀维护 → Ledger 窗口化 → 请求及保存协调器 → 正式前端构建。

本 spec 以 `platform-perf-hotspots`、`backend-startup-and-request-overhead`、`runtime-performance-and-reload-hardening-followup` 的最终磁盘形态为前置，不重复实现 render-config 压缩、lazy route、路由索引、纯 ASGI 中间件、overlap reload、SSE replay、GC 空闲门、首页请求收敛和项目列表单飞。

## R1 安全基线与交付边界

1. 当前分支落后远端且主工作树有并发改动；实施只能改本 spec 明确登记的文件块，不得 stash、clean、reset 或整树覆盖他人工作。
2. 新模块与调用方必须同一候选树存在；迁移号以实施时全工作树最高版本顺延，V/R 成对。
3. 现有三份性能 spec 的未提交成果必须作为依赖整体验证，不能只提交引用方或早期阶段版本。
4. 所有运行指标使用 `127.0.0.1`；无真实证据不得声称通过 6000 并发。

## R2 遗留容器治理与稳定运行模式

1. PostgreSQL MCP 的 stdio 容器必须由单一 wrapper 启动，带工作区、会话、宿主 PID 与开始时间标签；正常退出和异常中断都只清理自己的容器。
2. janitor 只能自动清理由本 wrapper 标记且宿主已失效的容器；历史无标签容器必须先 dry-run，再按本次用户授权清理，不得波及业务容器或活跃 MCP。
3. `.kiro`、`.cursor` 和 MCP 冒烟入口必须复用同一 wrapper，数据库 URI 仍只通过环境变量传递，不写日志。
4. 增加 `GT_RUNTIME_MODE=dev|stable`。dev 保持后端 overlap reload 与前端 HMR；stable 关闭后端 reload，并运行固定的前端构建快照，源码变化不能触发页面重挂载。
5. 默认模式保持 dev；旧 `GT_BACKEND_NO_RELOAD=1` 继续兼容。非法模式 fail-closed，启动器明确打印模式与重启要求。

## R3 辅助明细索引与 COUNT

1. 以和平药房科目 1002 等真实只读样本保存 COUNT、首页和 `EXPLAIN (ANALYZE, BUFFERS)` 基线。
2. 为 `tb_aux_ledger` 建与 active dataset、项目、年度、科目前缀和稳定排序一致的索引；大表必须并发创建并验证 `indisvalid/indisready`，不能在启动事务里长时间锁写。
3. 前缀筛选必须验证当前排序规则下确实使用索引；必要时使用 `text_pattern_ops`，不能只看“索引存在”。
4. SQL 分页首次返回精确 total；后续同一查询翻页不得重复 COUNT。复用凭证必须与用户、作用域、查询定义和数据集绑定，篡改或过期时重新计数而不是信任客户端数字。
5. 辅助明细首页冷缓存不超过 5 秒，热缓存 p95 目标不超过 2 秒；若索引仍未达标，任务保持未完成并保留执行计划。

## R4 表膨胀维护

1. 维护前记录 `checklist_responses` 精确行数、主键集合摘要、表/索引大小和约束；生成可恢复备份。
2. 本地共享库在维护窗口执行受控表重写与 ANALYZE；执行前确认无长事务，执行后逐项核对行数、摘要、约束、应用健康与大小。
3. 正式工具必须先 dry-run，默认不执行；生产建议与本地做法分开，明确 ACCESS EXCLUSIVE 锁风险和 `pg_repack` 替代方案。
4. 不得依据短观察窗口的 `idx_scan=0` 自动删除索引。

## R5 Ledger 服务端窗口化

1. 互动查账不得再循环下载最多 20 万行；普通序时账和辅助明细一次最多返回 500 条业务行，并提供不透明、绑定查询与数据集的 keyset cursor。
2. 统一账序为日期、凭证号、行 id；普通与辅助明细、运行余额、月小计和导出使用同一顺序。
3. 运行余额按完整账序计算，不因显示筛选改变；日期范围期初必须包含 `date_from` 之前发生额。金额在服务端保持 Decimal 语义。
4. 首窗口返回精确 total、范围期初、筛选合计和下一游标；后续窗口不重复 COUNT。数据集切换时旧游标不得静默混入新数据。
5. 主穿透、顶部序时账、辅助明细与辅助穿透共用一个前端窗口 composable，带请求代际、取消和有界 LRU；凭证第三层深链保持可用。
6. 达到边界必须明确显示，不允许以截断数据冒充完整结果；完整导出改走服务端，不依赖浏览器当前窗口。

## R6 请求与保存协调器

1. 参数化 GET 使用规范化查询键共享同一在途 Promise；键包含 URL、参数、响应类型与身份纪元，参数顺序不同但语义相同必须合并。
2. 单个订阅者取消不得取消其他订阅者；项目/年度切换的晚到响应不得覆盖新状态。
3. 每个底稿/附注文档的保存必须串行；每次编辑递增 epoch。保存期间继续编辑时，旧回执不得清除新 dirty，必须自动合并一次后续保存。
4. `onSave=false`、版本冲突和网络失败都不得记为保存成功；失败后保留 dirty，自动保存不得无限并发重试。
5. 先接入 Univer 与附注写入链；现有 CAS、版本号、项目鉴权和离开确认保持不变。

## R7 正式前端构建

1. `build` 只负责确定性 Vite 生产产物；全量 typecheck 与单测由独立命令负责，CI 不重复执行 typecheck。
2. 生成 Vite manifest；Univer、Office 预览和公式管理等重功能必须保持异步，不得进入入口递归依赖。
3. 包体预算读取实际 manifest 与 gzip 大小，首次成功构建建立棘轮；不得用抬高 warning limit 隐藏超限。
4. 提供本地 built-dist smoke：主页、SPA 深链、动态 chunk、`/api/health` 与 `/wopi` 代理均可用。
5. Nginx 静态托管必须包含 history fallback、哈希资源长缓存、HTML/SW 不缓存及 SSE 代理；开发 Vite 不能作为生产入口。
6. README 必须如实说明当前打包能力；在资源路径与 frozen smoke 未完成前，不把不存在的 `build_exe.py` 描述为已交付。

## R8 验收

1. 后端、前端、数据库、构建和浏览器实测都须在明确候选树执行；与干净基线逐节点区分预存失败。
2. 核心页面不得出现新增 console error、可见 canceled 提示、未保存数据丢失或序时账金额差异。
3. 记录健康接口、查询 p50/p95、首窗口行数、浏览器长任务、构建 chunk 和数据库尺寸前后值。
4. 容器清理、索引创建和表维护均保留可审计清单；任何无法验证的外部依赖如实保持未完成。
