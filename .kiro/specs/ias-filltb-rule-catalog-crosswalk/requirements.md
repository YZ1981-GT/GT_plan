# IAS / FillTbTool 规则目录与编码候选对照（0）：需求

## 概述
本 spec 把当前平台静态规则、IAS 可见源码和 FillTbTool 最小必要审阅事实整理为离线规则目录及编码候选对照，供人工审阅；未来接入以当前平台为目标。
本轮交付为 0、A 两份 spec 与两本 Excel；Excel 已生成并通过现有自检，平台产品未实施。实际基线为 HEAD `9684955683720068cf3aad82dfc5502a0194e73c`，分支 `sj-dev1.0`；spec 仅文档交付，无提交或推送。文档完成、离线产物完成、映射批准和运行接入分别记账。

## 范围
- 0 仅为离线目录；不产出 runtime alias 包，不承诺 API、UI 或数据库表，不另造 IAS FS_CELL 执行器或万能映射库。
- A=`.kiro/specs/ias-filltb-import-compatibility/`，负责未来导入兼容；参考 0 已核实目录，在现有 identifier/adapter 规则载体内独立实现经确认的语义。本轮 Excel 不直接加载，外部未确认不启用。
- 外部语义采纳按“目录审阅 → 语义确认 → A 独立实现及验收”推进，不阻断 A 基于现有规则的其他开发；目录转换/发布及后续报表、重分类、结转专题须独立批准，本轮不实施 A。
- 平台和 IAS 事实只来自本次磁盘快照，未查库；静态种子不等于项目运行时有效定义，数量不作为永久验收阈值。
- FillTbTool 为商业闭源：只保留行为描述与精选事实，不复制模板、JSON、二进制或完整商业词库，不从字符串线索重建字典。
- IAS 数据采集工具（用友审计数据采集工具系）同样只保留行为与字段事实；对比结论见 `docs/reviews/ias-filltb-fusion/IAS数据采集工具对比分析.md`。

## 需求与验收标准

### R1 规则分类与命名空间
作为审阅人，我希望不同用途的同名字段不被当成同一种规则。
1. **R1.1** 当收录规则时，目录应分开导入别名、表识别、导入校验、标准科目、报表行、底稿附注、推送规则、公式 TB 列词表，并记录来源系统。导入校验收录平台 `validation_rules_catalog.VALIDATION_RULES_CATALOG` 与外部字段依赖/主键/平衡规则，两者按规则码与语义对照。
2. **R1.2** 当读取原规则时，应保留适用条件及扩展字段；推送的 formula、derivation、four_table_leaves 不得压成同一种科目映射。
3. **R1.3** 当展示平台现状时，应区分静态定义、代码引用与运行时有效定义；不得把公式 COLUMN_ALIASES 当上传列别名，亦不得声称 recognition JSON 有实际不存在的顶层 column_aliases。

### R2 稳定身份与来源
作为审阅人，我希望每个条目都能回到本次看到的材料，而非漂移行号。
1. **R2.1** 每条规则及关系应具有稳定 ID、source_id、原生键、JSON Pointer 或符号及内容 hash；ID 不以数组下标、显示名称或内容 hash 单独定义。
2. **R2.2** 每个 source_id 应关联快照路径、原来源路径/hash、快照 hash、来源 commit 和许可用途；未取得 commit 时留空并给原因，不把工作树内容冒称提交内容。
3. **R2.3** 当实际账套、部署模型或关系数据缺失时，编码应留空且说明缺失原因；已有源码证据仍应保留，不得笼统断言 IAS 规则全部缺失。

### R3 证据、映射、接入三维分离
作为审阅人，我希望“看见了规则”不被误报成“已批准且已生效”。
1. **R3.1** source_evidence 应独立取源码/静态表/字符串线索/缺数据；mapping_state 独立取未建立/候选/冲突/已确认；integration_state 独立取未实施/平台已有/待验收，三者不得互相推导。
2. **R3.2** 映射进入已确认必须记录审阅人、决定时间、适用范围和被审内容 hash；本轮外部对照只为候选或冲突待审，Excel 生成不得自动确认。
3. **R3.3** 平台已有只说明有可定位的现存定义或接线；已确认不等于已接入，待验收须有另行实施证据，未查库不得声称项目生效。

### R4 编码、维度与关系
作为审阅人，我希望同码异义、合法一对多和内部差异不会被自动清洗掉。
1. **R4.1** 编码应按文本逐值保留前导零、标点和大小写；检索归一键不得覆盖原码/原名，空码不补造，Excel 不得将编码转数值。
2. **R4.2** 国企单体、国企合并、上市单体、上市合并四口径应独立保留；未知不等于全部适用，报表类型、期间、余额/发生额及借贷语义不得混用。
3. **R4.3** 应允许一对多/多对一并保留关系类型、条件和证据；冲突与孤儿单列，report seed 中不在标准 chart 的编码仅为本次差集，不自动判错或删除。
4. **R4.4** 候选不得默认参与导入；不得以同码、同名、前缀或字符串相似直接批准映射，存在冲突时不得取首项或相互覆盖。

### R5 外部证据与合法授权
作为审阅人，我希望借鉴可证的行为，同时看到未取得材料和许可限制。
1. **R5.1** IAS 应列出 DSService.getDisclosureApiData 的 DataModel 依赖、四个指定 SQL 过程和 base.reportItems 模型 001 的字段语义；仅记录源码可证行为。
2. **R5.2** 实际 CW_KMB、完整报表关系及部署 DataModel 未取得时保持缺数据；autoCarryForward 的 BillID=@Data_ID 仅列疑点、未实测，不照搬或执行。
3. **R5.3** FillTbTool 应精选货币资金、坏账、权益、损益、现金流及 1523/1524 冲突条目；cmp_F 的 1-A 等列位不得作科目码，提取字符串只作 C 级线索。
4. **R5.4** 材料可见不等于获得转换或发布授权；只在许可允许范围内保存快照和最小事实，超出本轮审阅的使用必须另批。
5. **R5.5** IAS 数据采集工具应作为独立来源（`ias_collector`）登记：Excel 采集加载项的四张标准表名、按表分组的列同义词、必选列、字段依赖、主键组合、方向与符号约定，SAP 两张表模板的中文字段与 S/H 方向、科目级次规则；只记录行为与字段事实，不复制宏代码与模板文件。
6. **R5.6** 采集工具的财务软件直连、备份还原、SAP RFC、定时采集只登记为“现场工具能力、平台不接入”；`DumpModel.mdb` 有访问密码未打开，其中各软件的采集表与字段标“缺数据”，不得破解；密码破解、口令读取、数据恢复组件只在风险清单出现，不进入任何规则条目。

### R6 版本与确定性重生成
作为维护人，我希望重复生成不会制造假变更或沿用过期审批。
1. **R6.1** 同一来源快照、schema 版本及审阅决定应生成相同排序和逻辑内容；内容未变沿用更新时间，不用当前时间或随机值制造差异。
2. **R6.2** 内容或适用范围变化应更新版本/hash并重新待审，保留旧决定的历史；仅位置变化不重分配稳定 ID，来源删除转孤儿/退役而不静默消失。
3. **R6.3** 数量、差集和 source.kind 分布应按本次材料现算并写明口径，以最终报告为准；重生成只对账来源，不采用固定总数作为验收阈值。

### R7 本轮离线交付与验收
作为审阅人，我希望拿到可筛选、可追溯的真实文件，而非未来交付承诺。
1. **R7.1** 本轮离线交付应包含 `docs/reviews/ias-filltb-fusion/规则目录_审阅稿.xlsx`、`编码对照表_审阅稿.xlsx`、`source_manifest.json`、`README.md`；规格文档不能代替真实文件。
2. **R7.2** 工作簿应覆盖平台/IAS/FillTbTool 分区、差异融合、来源、字段字典、冲突与待确认；关键字段中文说明，编码原串和状态可筛选，公式表达式按文本展示不执行。工作表与条目数量以最终验证报告为准。
3. **R7.3** 产物须读回核对工作表、编码、ID、来源引用、三维状态与来源摘要；最终内容验证完成并留证据后才勾选离线任务，运行接入任务保持未做。

### R8 阶段交接与交付状态
作为负责人，我希望审阅工作不扩大为未经授权的产品改造。
1. **R8.1** 目录审阅通过仅允许形成确认记录；未来目录转换/发布、报表映射、重分类和结转须分别明确批准及验收，不归 A 的实施范围。
2. **R8.2** 0 与 A 的边界已统一：0 只交离线目录；A 参考已核实目录，在现有 identifier/adapter 规则载体内独立实现经确认的语义。本轮 Excel 不直接加载，外部未确认不启用，不依赖 0 的 runtime alias 包。
3. **R8.3** 本轮交付状态应区分已完成的规格与离线生成、待完成的最终离线验收及未实施的平台产品，不因文档或 Excel 完成勾选产品实施任务。
