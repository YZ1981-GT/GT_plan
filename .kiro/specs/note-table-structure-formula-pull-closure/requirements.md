# 附注表格结构、预设公式与合并拉数收口 — 需求

## 背景

承接 `note-disclosure-formula-and-consolidation-chain-closure`（15/16）、`note-chain-followup-optimizations`（归档 101）、
`note-pull-residual-governance-closure`。三道模板门禁（Word 树、模板↔底稿、四版同步）现为绿，78 个底稿披露 provider 已全部离屏。
本轮按用户 2026-10-31 要求（单体按底稿披露表、国企对国企 / 上市对上市；合并按 Word；表头合并单元格、标题行、序号、预设公式、
公式管理；刷新自动从审定后的披露表取数；合并从单体拉数）重新现读代码与数据，只修现存缺陷，不重做已交付能力。

现读证据（D2 应收账款为主样本，四版 Word 与两版种子逐表比对，见 design §1）：

## R1 合计构成判定（单体 / 合并 / 前端同一判定）

1. 冒号结尾的分段标题行（「资产：」「负债：」「组合：」「主营业务：」「合营企业：」等，非「其中：」、非减项 / 加项、非合计）不是明细，
   不进合计构成；只有标题行的小计报「没有可合计的明细行」。
2. 账龄表的嵌套小计（「1年以内 / 其中：0-X个月 / X-Y个月 / 1年以内小计： / 1至2年 … / 小计 / 减：坏账准备 / 合计」）可判定：
   「1年以内小计」= 本组「其中」之前的明细（无「其中」时 = 本组明细）；「小计」= 分项小计 + 其后明细；「合计」= 小计 ± 减项 / 加项。
   与底稿源模板（R12 = R8、小计不含细分行）同口径。
3. 纵向变动表（首个明细是期初类、合计行是期末类，如「上年年末余额 / 本期计提 / 本期收回或转回 / 本期核销 / … / 期末余额」）
   的期末行不生成自动合计（原先把转回 / 核销当加项），回原因「期末 = 期初 + 本期增加 − 本期减少，属审核勾稽」。
4. 「账龄」「期末账龄」列是说明列，不当金额列（不加总、不取数、不生成公式）。
5. 前端 `noteTotalTerms.ts` 与后端 `note_total_terms.py` 同步修改，golden 重新生成且 `--check` 通过。

## R2 比例与损失率预设公式

1. 单体附注每张表按当前结构现算：账面余额组下的「比例(%)」= 本行金额 ÷ 本表合计行金额 × 100；「预期信用损失率 / 计提比例 /
   损失率」= 同期间坏账（减值）准备 ÷ 账面余额 × 100。分子格为空不算、不写 0；分母为 0 不写；认不准（同期间多列、无合计行）不生成并回原因。
2. 分母不在本表的占比（前五名「占应收账款合计的比例」）不生成，回原因。
3. 底稿投影表上比例预设只补空格，与底稿值不一致保留底稿值并回报（与现有 ADR-2 同口径）。
4. 合并附注拉数与子树汇总后：合计只加金额列（比例列不加总）；比例、损失率按同一判定从本表金额派生。

## R3 单体附注读时增强

1. 期间层（`_display_layout`）只挂到自身没有期间层的表；存量旧结构表（列上已有期末 / 期初分组）不再被套第二层期间。
2. 表名等于首列表头（旧数据「泄漏名」）不再单独作为同一张表的依据；按位置回填模板结构须首列一致且列数相同。

## R4 推送后自动运算与溯源

1. 试算表更新、底稿保存、公式配置变更、推送页手动推送、采纳公式值写入附注后，对写入的章节自动执行附注公式（合计、账面价值、
   比例等跟着审定数更新），不需要再点刷新或「应用自动运算」。刷新链路本身已在最后执行公式，不重复。
2. 存储表上公式推送拥有的格（推送状态 auto 且当前值等于推送值）不被预设公式改写；用户公式照常覆盖。
3. 单元格来源诊断的公式推送步骤写明规则的取数口径（如「期末 = TB('1122','期末余额')」）。

## R5 公式管理（附注节点）

1. 附注章节节点先列可执行公式（预设 / 全局 / 本项目，按目标单元格），文字版校验预设单列为「审核要点（不执行）」，不再与可执行公式混排。
2. 列出本章节没有生成预设公式的原因（表 · 行 · 原因），便于判断是结构问题还是需手工设公式。

## R6 合并附注拉数

1. 行名比较键去掉【…】编制提示（「按组合计提坏账准备【注意：…】」≡「按组合计提坏账准备」），映射、分组、行对应同口径。
2. 账龄区间归并：来源区间完全落在合并模板某一区间内（「3至4年 / 4至5年 / 5年以上」→「3年以上」）按该行建议并可自动确认；
   明细模板不再把这类来源行另建新行。
3. 来源独有的明细行插在来源表里它前一个已有行之后，不统一堆到合计行之前。
4. 行名别名：「上年年末余额」≡「期初余额」、「上年年末余额在本期」≡「期初余额在本期」。
5. 单体账龄表「小计 / 减：坏账准备 / 合计」折叠成合并账龄表合计行的账面余额 / 坏账准备两列；判得准的合计行该列明细全空时用来源合计。
6. 选中的单体表一列金额都对不上（转置表、口径不同）时明确报原因，不当作「已读到」。
7. 来源项目与合并项目口径不同（国企集团含上市子公司）时，按来源口径的单体子表名选表（映射为每张合并表登记两种口径的子表名）。
8. 映射弹窗：模糊 / 按位置 / 上年匹配等非自动确认的建议，确认前弹窗列出由用户确认；删去无效代码。

## R7 离屏披露自动带入

1. D2 披露表的单项计提、转回或收回、核销逐项、前五名四张逐项表：用户未录入时按底稿 D2-3 / D2-11 / D2-5 现有数据派生（与「带入」
   同一映射，不落底稿），底稿披露 Tab 同步与附注刷新离屏同步得到同一载荷。

## R8 存量数据

1. 只读清点：已删除 / 停用规则留下且当前值仍等于推送值的附注格；D2 存量旧结构表。输出清单与修复预演。
2. 写真库修复（清孤儿推送格、重建旧结构表、对和平药房执行全部刷新）须用户放行，本 spec 不擅自写。

## 约束

不新增数据库迁移；不改他会话正在改的文件（`formula_engine.py`、`formula_push/bindings/*` 等）；浏览器写入只用【测试】项目；
行数门不放宽（超阈值的文件抽模块）。

## R9 孤儿推送格回收（第二轮，承接 R8 清点结果）

1. 规则清单里已不存在的 `rule_id` 留下的 `formula_push_state` 行要能回收：删状态行（格里的数回到现行机制维护），
   并对受影响章节重跑附注公式让合计 / 比例按现行口径重算。
2. 修复脚本默认只预演（dry-run），`--apply` 需显式 `--confirm`，执行前把要删的行整行备份成 JSON，逐条打印处置。
3. 清点与修复用同一份判定（规则清单现算），不写第二套。

## R10 推送运行回报孤儿状态

1. 每次推送 run 结束时统计「规则已不存在」的附注推送状态行数，随回执返回；不自动清值。
2. 推送页显示提示并点名可以用哪个脚本清理；没有孤儿时不显示。

## R11 合并附注章节级自动映射

1. 「⚡ 自动映射」能按章节一键执行（当前已是逐章节接口，但界面没给单章入口）。
2. 预览回执带本章可自动确认比例（可自动确认条数 / 建议总条数），映射弹窗与合并附注页都显示，便于判断值不值得人工过一遍。

## R12 账龄表多合计行的推送兜底

1. 表里有「减：…准备」行时，账面余额合计（该行之前最近的汇总行）与账面价值合计（最终合计）语义不同：
   科目余额对应账面余额合计，推送应写它而不是整表拒绝兜底。
2. 其余多合计行形态（分段合计「一、账面原值合计 / …」）保持现状不兜底，并保留原因说明。

## R13 附注权威源对拍

1. 底稿披露表的后端 builder 与前端 `buildXSyncPayload` 对同一份来源算出的载荷必须逐值相等；不等即打红并点名差异单元格。
2. 对拍以 D2 为样板落地（两版口径各一张账龄表 + 分类表），其余 wp_code 登记在清单里只许变短。

## R14 跨口径转置表

1. 合并按期间分列、单体按资产类别分列（固定资产 / 无形资产 / 使用权资产等）时，读取层要能按「行名 × 列名」转置对应，
   不再因为一列都对不上而整表拉不到数。
2. 转置只在「合并列名集合 ⊆ 单体行名集合」且「合并行名集合 ⊆ 单体列名集合」时启用；对不上的部分照旧报原因。

## R15 合并来源可用性必须显式判定（第四轮）

1. 单体附注虽然读到行，但合并模板所需金额列一列都未匹配时，来源状态必须为 `unreadable`，不得进入结构分组、自动确认、apply 或父节点汇总。
2. 预览仍须返回表名、已观察行数、未匹配列和中文原因，不能把「有行、无可用金额」伪装成 `found`，也不能静默变成空表。
3. apply 每次重读来源后必须复核同一可用性判定，不能只在 preview 过滤。

## R16 国企/上市跨口径来源身份必须完整且 fail closed

1. 每张合并表的映射须按来源口径保存单体章节号、章节标题、子表名三件套；国企合并拉上市单体、上市合并拉国企单体均按来源项目口径选取。
2. 另一口径不存在明确章节或表对应时，返回 `no_source` 和中文原因，不得回退到合并项目口径的章节号或表名。
3. 映射生成器与运行时读取必须消费同一结构；保留旧字段只作兼容，禁止形成第二套猜测规则。

## R17 行身份与坏账准备折叠安全

1. 映射建议、分组、已保存行保护和父节点汇总共享附注专用行身份：统一空白、括号、编制提示、可选行括号、区间连接符和全局别名。
2. 结构指纹继续保留原有兼容口径，避免本轮让全部已确认映射无故 stale；只修运行时行对应。
3. 「减：坏账/减值准备」只有在其前紧邻且唯一的小计能提供账面余额时才自动折叠；缺小计时保留原行交用户映射，不以净额冒充账面余额。

## R18 映射确认错误必须可见

1. 「确认映射」与「确认并写入」复用同一错误处理；确认请求 409 时提示来源变化并重新预览，其他错误显示后端原因。
2. 任一结构组确认失败时不得调用 apply，不得关闭弹窗或提示成功。

## R19 公式管理附注节点回归收口

1. 公式中枢后续提交不得回退 R5：附注节点按「可执行有效公式 → 审核要点（不执行）→ 未生成预设及原因」展示。
2. `list_section` 必须返回当前表结构现算的 `preset_notes`；前端按目标单元格显示 `target_label`。
3. 附注公式加载采用 loading / error / data-or-empty 三态；4xx/5xx 必须显示中文错误和重试入口，不得清空后伪装成“没有公式”。

## R20 推送后自动更新与来源保护

1. 所有 `formula_push.run_and_commit` 入口在主推送提交后、通知前，统一对本次实际写入的附注章节执行表内公式；附注页 prepare→headless→push→refill 链须显式关闭该中间 follow-up，避免重复执行。
2. follow-up 使用当前公式中枢的运行记录和来源信封，触发来源标为 `formula_push`；失败不回滚已提交推送，但必须留日志并允许后续刷新重试。
3. 预设公式不得覆盖仍由有效推送规则拥有且当前值等于最后推送值的格；用户公式、人工格和锁定格沿用现有优先级。

## R21 验收边界

1. 后端至少覆盖 unreadable、跨口径缺映射、父级别名对应、无小计不折叠、推送 follow-up 与刷新 opt-out；前端覆盖确认失败和公式加载错误三态。
2. 重跑标题行库、Word 树、模板↔底稿、D2 载荷契约；候选树相对同一远端基线新增失败为 0。
3. 浏览器用 `http://127.0.0.1:3030` 验证单体 D2 刷新、公式管理；合并写入无【测试】集团时只做只读入口与回执走查，并如实保留数据阻塞，不写真实项目。
