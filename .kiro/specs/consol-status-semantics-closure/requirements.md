# 合并链路状态语义收口 — 需求

来源：`docs/proposals/consolidation-three-code-tree-and-formula-chain-review-2026-11-10.md` §7.5、§7.7、§8.1、§8.2、§10 P0-5 / P1-6；按 HEAD `39777a020` 现读收窄（现状与取舍见 `design.md`）。

目标：用户在页面上看到的「已完成 / 待更新 / 失败 / 跳过」与系统实际状态一致；「已提交」不被说成「已完成」。

前置：`consol-note-save-integrity-closure` 先落地（本 spec 在同一 GET 响应上追加字段，并沿用其写入方登记）。

## R1 合并附注「待更新」带原因与时间

1. `consol_note_data` 增加 `stale_reason`（稳定编码）与 `stale_at`（时间）两列，迁移成对（V / R），号在实施时按 `max(磁盘, 共享库) + 1` 取。存量 `is_stale = true` 的行回填原因 `legacy`（「历史标记，未记录原因」），`stale_at` 留空。
2. 原因编码与中文标签放在一个模块里，覆盖全部置「待更新」的写入方：合并推送、推送后公式值变化（拉数行）、子企业单体附注已保存、公式设置变化、新建节点尚未计算；复制行时连同原因与时间一起继承。
3. 所有清除「待更新」的写入方同时清空原因与时间。
4. 新增 AST 守卫：除该模块外，后端不得直接给合并附注行的 `is_stale` 赋值或在 `update(...).values(is_stale=…)` 里写它；构造合并附注行时若 `is_stale` 不是常量 False，必须同时给出 `stale_reason`。
5. 合并附注章节读取接口返回 `is_stale`、`stale_reason`、`stale_reason_label`、`stale_at`；合并附注页在当前章节显示「待更新：{原因}（{时间}）」，不待更新时不显示。
6. `consol.note_stale` SSE 载荷增加 `reason`。
7. 删除死代码 `formula_settings/stale_marks.mark_consol_note_stale`（引用不存在的列 `section_code`，且 `mark_in_txn` 无生产调用方）及 `mark_in_txn` 的合并附注分支。

## R2 重新汇总结果如实

1. 一个章节×节点写入时，若没有任何自动格被写入、且有被保护的手工 / 锁定格，结果状态记为 `kept_manual`（不是 `persisted`），不计入「已更新章节数」，原因写明「全部为手工格，汇总值未写入（其中 N 格与汇总值不同）」。
2. `kept_manual` 照常清除「待更新」：该行的自动部分已按最新上游处理过，再跑一次结果相同（design §2.2）。
3. 结果里每个保留的手工格带本次算出的值，用于统计「与汇总值不同」的格数。
4. 后台重新汇总任务：业务结果为全部失败（`failed`）时，任务记为失败，错误信息取第一处失败原因；部分失败、跳过、待确认映射仍记成功，由结果摘要说明。
5. 合并页的重新汇总完成提示改用与合并附注页相同的摘要函数（`consolNoteView.reaggregateSummary`），不再读不存在的 `result.errors`；只有摘要判定完全成功时才清除页面的「建议重新汇总」提示。

## R3 合并推送附注步骤如实

1. 附注刷新统计增加 `skip_reason`：`no_template_type`（无法确定附注模板）、`no_sections`（模板没有启用的章节）、`no_tree`（无企业树）、`context_failed`（合并计算上下文构建失败）。
2. `context_failed` 时附注步骤记为失败、推送结果不再算全部成功；其余三种记为「已跳过」并附中文原因，不再记为成功。
3. 一键刷新（级联刷新）的附注步骤按同一判定：`context_failed` 计入错误，其余跳过。推送与级联刷新共用一个判定函数。

## R4 抵销分录审批的重算触发可见

1. 审批 / 撤销审批接口的响应增加 `recalc_trigger`：`event_published`（已发出重算事件）、`event_failed`（发事件失败）、`not_applicable`（提交 / 驳回等不触发重算的动作），`event_failed` 时附 `recalc_notice` 中文说明。
2. 重算事件处理器入队失败时，写一条失败的推送运行记录（触发来源为本次审批 / 撤销），并广播 `consol.push_failed`，载荷 `warnings[0]` 为中文原因；合并页已有的失败通知因此可见。
3. 前端审批成功提示改为「已审批，合并数将在后台重算，完成或失败会在合并页提示」；`event_failed` 时改为警告并给出手动推送入口说明。

## R5 调整分录审批回执不暗示下游已完成

1. 批量通过的回执按每笔的 `tb_update_status` 汇总：已计入试算表 N 笔、待来源底稿发布 M 笔、底稿发布无变化 K 笔。
2. 回执增加 `downstream`：本次提交后发布刷新事件的结果（发布数、失败数）；失败数大于 0 时提示「部分刷新事件投递失败，系统会自动重试」。
3. 通过前的确认框不再写「相关报表与附注将在试算表更新后刷新」，改为如实说明「报表与附注由后台刷新，完成后各页面显示最新数」。

## R6 不做与待拍板

1. 不改：推送后拉数行保持「待更新」（已归档 spec 84 §9 / §13.3 的设计）；平台任务状态集合不增加 `partial`；合并页横幅改为持久读取（本 spec 只让章节显示持久原因）。
2. 已定（用户 2026-11-11 按建议）：就绪门的「可执行动作」不在服务端强制，推送、重新汇总、operations 在未就绪时照常受理，前端继续按就绪条禁用按钮。理由与「重复项目、关系冲突只提示不阻断」一致，见 design §8。
3. 收尾时在 review 文档 §0.5 / §10 标注覆盖关系，并在 `.kiro/specs/INDEX.md` 登记。
