# Requirements Document

## Introduction

D4 营业收入循环的 **IPO/上市检查表**（D4-25 经销商检查 / D4-26 境外销售收入检查 / D4-27 识别未披露的关联方 / D4-28 客户信息核查清单）
当前存在三个断点，本 spec 一次收口：

1. **双模式数据不互通**：HTML 表格视图把整份 `rows` 数组 `JSON.stringify` 塞进 `checklist_responses` 的单条
   `{sheet}-rows` 项的 `remark` 字段，Excel 模式由 `GtOnlyOfficeSheet sheet-name="<源 sheet 全名>"` 写入 OO 工作簿
   字节。两处互不读写 —— 审计师在表格视图录入的客户行，切到「在线编辑」看不到；在 Excel 里改的金额，切回表格视图也是空的。
2. **无取数公式**：四张表的全部单元格靠手填。表间提取（D4-25 的「本期销售金额/期末应收账款余额」本可来自 D4-2 收入明细与
   D2-2 客户账龄；D4-26 的「本期销售金额」本可来自境外销售明细）与表内计算（D4-27 的「总计」列源模板就是
   `=SUM(C15:L15)`；D4-25/D4-26 的「占同类交易比例」本可自动算）都没有落点。
3. **导入导出已通一半**：后端 `_d4_import_export.py` 的导出与导入**同一个** `item_id = f"{sheet}-rows"`，
   导入走 `INSERT ... ON CONFLICT (wp_id, item_id)` upsert —— 即导入导出 ↔ HTML rows 已经是同一份数据。
   缺的只有前端「导入成功后切回表格视图并 reload」这一跳。

### 参照系与明确不做的事

- **平台双模式契约**：统一消费 `ContentMutationService`、`useWorkpaperSyncBridge`、durable callback、三方合并及批准的 contract-bundle representation；禁止新增自同步 bridge。
  `no_projection_contract` 的检查表不现实。本 spec 的「双向」是 **HTML 表格视图 ↔ Excel(OnlyOffice) 双模式的数据回写**。
- **不做 trial_balance 回写**：四张表是 IPO 检查表而非审定表（审定表是每个循环的 `xxx-1`）。
- **不接附注同步**：`workpaper_row_change_reachability.json` 把这四张 sheet 记为 `state=blocked`、
  `reason=no_projection_contract`、`managed_sheet_candidates=['底稿目录']`，本 spec 不改变该判定。
- **不新建 DB 表、不写迁移**：数据真源沿用 `checklist_responses` 的 `{sheet}-rows` 项。

## Glossary

| 术语 | 含义 |
|---|---|
| 表格视图 | HTML `el-table` 视图，行数据即本 spec 定义的行记录，写入 `checklist_responses` 的 `{sheet}-rows` 项 |
| 在线编辑 | OO（OnlyOffice）视图，`GtOnlyOfficeSheet sheet-name="<源 sheet 全名>"` 渲染源模板工作簿 |
| rows 项 | `checklist_responses` 中 `item_id = "{sheet}-rows"` 的条目，`remark` 存 JSON 数组 |
| 模式切换回写 | 从一个视图切到另一个视图时，把前者最后一次编辑落盘的数据投影到后者 |
| 表间提取 | 值来自本项目其他底稿/四表（如 D4-2 收入明细、D2-2 客户账龄），走后端 resolver |
| 表内计算 | 值来自本表其他单元格（如 D4-27 总计列、D4-25 占比列），走前端公式引擎 |
| 预设公式 | 平台按源模板与审计常识内置一份公式真源，用户不填也有值 |
| 二次编辑 | 用户在公式条上修改/清除预设公式，改动按 `{wp}/{sheet}/{cell}` 覆盖，不影响其他项目 |

## Requirements

### Requirement 1: 行记录真源与两级表头同构

**User Story:** 作为审计师，我要在四张 IPO 检查表里录入的每一行都有一份明确的、与源模板列完全对齐的记录，
并且 D4-26/D4-28 的两级表头在三个层面（源 xlsx / 行记录 / 表格视图）保持同构，
以便表格视图、在线编辑、导入导出读到的是同一份数据、同一个列结构。

#### Acceptance Criteria

1. 每张 sheet 有一份**声明式列规格**（单一真源），列出每一列的 `key`、中文 `label`、`group`（父组，无父组为 `null`）、
   `type`（`text|number|amount|percent|select|checkbox`）、`options`（`select` 专用）、`width`。
2. 列规格的 `label` 与源模板表头单元格文本**逐列一致**（含 `占同类交易比例`、`视频、电话访谈` 等全角标点与顿号）。
3. 列规格的 `key` 序列、`label` 序列、`group` 序列与 `_SHEET_HEADERS[sheet]` 的后端列头**逐列一致**
   （后端列头是两段摊平的 1D 数组，前端规格是其结构化版本；摊平后必须完全相等）。
4. 两张两级表头的父组不可丢失：D4-26 `group="核查程序执行情况"` 覆盖 5 列、D4-28 `group="核查方式（√）"` 覆盖 5 列。
5. 四张表的行记录都含稳定序号 `seq`（不可用行内文本 `客户1`/`陈XX` 当 key，避免撞键与重名）。
6. 行记录的字段集合 = 列规格的 `key` 集合，不多不少（禁止 `remark` 里出现规格之外的字段）。
7. 新增行的命名字段（D4-25 `客户名称`、D4-26 `客户名称`、D4-27 `姓名`、D4-28 `客户名称`）必须先
   `ElMessageBox.prompt` 输入名称再创建；禁止静默创建无名称空行。
8. 行记录写入 `checklist_responses` 的 `item_id` 恒为 `"{sheet_code}-rows"`，与后端导入导出锚点一致。

#### Properties

- Property 1: 四张 sheet 的列规格 `key` 序列与后端 `_SHEET_HEADERS[sheet]` 摊平后的 label 序列逐列相等。
- Property 2: D4-26 列规格中 `group` 非空的列恰为 5 列且 label 集合为
  `{实地走访, 交易函证, 海关函证, 核对报关单, 电子口岸数据查询}`，其 `group` 全部为 `核查程序执行情况`。
- Property 3: D4-28 列规格中 `group` 非空的列恰为 5 列且 label 集合为
  `{工商资料查询, 互联网信息查询, 函证, 视频、电话访谈, 实地走访}`，其 `group` 全部为 `核查方式（√）`。
- Property 4: 四张表列规格的 `label` 与源模板表头单元格（openpyxl 直读）逐列相等，含全角标点。
- Property 5: 任一行的字段集合 == 列规格 `key` 集合。

### Requirement 2: 双模式回写（表格视图 ↔ 在线编辑）

**User Story:** 作为审计师，我要在表格视图录好数据后切到「在线编辑」继续改、改完切回表格视图数据还在；
反过来在 Excel 里改了金额，切回表格视图也能看到，以便两种视图是同一份数据的两个入口，而不是两份互不相认的账。

#### Acceptance Criteria

1. 切换到「在线编辑」时，先 flush 表格视图的未落库编辑（含 debounce 中的），再投影 rows 项到 OO sheet 字节。
2. 切换到「表格视图」时，先 flush OO 的未落盘内容，再把 OO sheet 的数据区投影回 rows 项。
3. **OO → rows 投影**：只读表头行之后的数据区，按列规格 `key` 反查列号取值；行内全空则跳过（不产生幽灵空行）；
   序号列不参与投影（由 `seq` 派生）。
4. **rows → OO 投影**：写入表头行之下的数据区；行按 `seq` 排序；列按列规格顺序写；空值写空单元格不写 `None` 占位文本。
5. **冲突裁决**：两侧改动经平台三方合并呈现字段级冲突，由用户明确裁决并 durable ack；禁止时间戳、Excel 优先或最后写胜出。
6. 双向投影失败**不得被成功文案掩盖**（fail-visible）：失败时不显示「已同步」，而是显示具体失败原因，
   且保留用户在源视图的编辑不丢失。
7. 表格视图 debounce 保存必须在切模式时同步 flush（禁止 debounce 未落库即投影，导致投影的是旧值）。
8. 只读模式（`isReadonly`）下禁止任一方向的投影写入。
9. 单张 sheet 的数据区行数上限 500（与后端 `_ROW_LIMIT` 一致），超限停止投影并提示。

#### Properties

- Property 6: 表格视图改一行金额 → 切「在线编辑」→ OO sheet 对应单元格值与该金额相等（数值容差 0.005）。
- Property 7: 在线编辑改一个单元格 → 切「表格视图」→ 对应行记录字段值与该单元格相等。
- Property 8: 全空的 OO 数据区行投影后不产生行记录（行数不增）。
- Property 9: 投影失败的失败态在 UI 上可见（非静默），且成功文案未出现。
- Property 10: 双侧都有未同步改动时切换，必须出现冲突确认（不得静默覆盖任一侧）。

### Requirement 3: 取数公式单一真源（预设 + 二次编辑）

**User Story:** 作为审计师，我要打开一张 IPO 检查表就有平台预设好的取数公式和计算，
需要时我可以改成自己的算法；改完之后我的改动只影响我的项目，其他项目仍用预设，
以便公式是治理过的单一真源而不是散在四个组件里各自写一份。

#### Acceptance Criteria

1. 平台有一份**声明式公式真源**（dataclass/声明式对象），每条公式含：
   `sheet_code` / `row_key`（行定位，如 `seq` 范围或 `*` 通配）/ `column_key` / `category`
   （`inter_sheet` 表间提取 | `intra_sheet` 表内计算）/ `resolver`（表间提取对应的后端 resolver 名）
   或 `expression`（表内计算的表达式）/ `depends_on`（依赖的列 key 列表）/ `precision` /
   `source_ref`（指向源 xlsx 单元格或审计依据，如 `识别未披露的关联方D4-27!M15`=SUM(C15:L15)`）。
2. **表间提取**经后端 `auto_data_resolvers` 注册新 resolver 实现，四张表共至少 4 个 resolver，
   注册后 `get_registered_sources()` 可见，且被 `backend/tests/test_auto_data_resolvers.py` 的
   「引用的 auto_data_source 都已注册」契约覆盖。
3. **表内计算**经前端公式引擎实现，表达式可引用本表其他列（`$col` 引用列 key，`$` 前缀区分于字段名）。
4. 预设公式在行创建时自动套用，用户**不填也有值**（表间提取首次进入即预填；表内计算随依赖列变化重算）。
5. 公式编辑统一走 F-SHELL v2 mutation，支持 `expression`/`refs`/`params`，后端权威执行并投影 HTML/OO；默认、custom、删除、恢复默认分开，禁止 `field_overrides` 公式库。
6. 覆盖只影响本项目：同一 sheet 在另一项目打开时仍用平台预设值。
7. 表内计算是**派生列**，用户在表格视图直接编辑派生列时提示「该列为计算列」并按最后一次编辑锁定为手填值。
8. 公式真源必须能被脚本 `--check` 校验（真源 ↔ 组件 ↔ 后端列头三向比对），且脚本对源码读取前 `stripComments()`。
9. 禁止在四个 `.vue` 组件里各写一份公式字面量（守卫断言四张表组件内的公式常量引用统一真源模块）。

#### Properties

- Property 11: 公式真源的 `sheet_code` 全部 ∈ `{D4-25, D4-26, D4-27, D4-28}`，无外部 sheet 混入。
- Property 12: 公式真源的每条 `column_key` 都在该 sheet 列规格的 `key` 集合内。
- Property 13: 每条 `category='inter_sheet'` 的公式，其 `resolver` 名存在于
  `auto_data_resolvers._REGISTRY`。
- Property 14: 每条 `category='intra_sheet'` 的公式，其 `depends_on` 全部是该 sheet 列规格的 `key`。
- Property 15: 表内计算列在列规格中标记为 `derived: true`，且用户手填覆盖后不再重算（锁定为手填）。
- Property 16: 公式真源 `source_ref` 非空的条目，其引用的源 xlsx 单元格坐标存在（openpyxl 直读不抛）。

### Requirement 4: 导入导出闭环

**User Story:** 作为审计师，我要用平台导出的模板填好导入，导入后直接在表格视图看到导入的行，
并且再次导出时内容与导入一致，以便导入导出是一个完整闭环而不是导出有数据导入丢一半。

#### Acceptance Criteria

1. 后端 `_SHEET_HEADERS` 四张表的列头与列规格摊平后**逐列一致**（单一真源守卫，防漂移）。
2. 导入成功后前端必须：切到「表格视图」并 reload rows 项（禁止只弹成功提示而视图仍显示旧数据）。
3. 导入的行记录经列规格映射（列号 → `key`），不依赖列名匹配（列名允许被用户微调，列号是稳定契约）。
4. 导出当前数据与导出空白模板均按列规格顺序输出列，两级表头在导出 xlsx 中保留合并单元格结构
   （D4-26 `O11:S11`、D4-28 `J12:N12` 为父组合并）。
5. 导出→导入往返**无损**：导入 `d4_export_data` 的输出后，rows 项内容与导入前一致（数值容差 0.005，
   空值归一为 `null`）。
6. 导入行数超 `_ROW_LIMIT` 时后端拒绝并返回明确错误，前端提示具体行数上限。
7. 导入失败（解析异常/列数不符）不得写入半批数据（整体回滚）。
8. 导入导出入口统一走既有 `el-dropdown「导入导出▾」`（导出模板 / 导出数据 / 导入数据），四张表行为一致。

#### Properties

- Property 17: 四张表的 `d4_export_data` 输出的列数与列规格列数相等，且列头文本逐列相等。
- Property 18: 导出→导入往返后 rows 项内容与导入前相等（数值容差 0.005，空值归一）。
- Property 19: 导入成功事件后，表格视图当前行集合 == 导入的行集合（按 `seq` 对齐）。

### Requirement 5: D4-25 经销商检查表

**User Story:** 作为审计师，我要在 D4-25 里录入经销商情况（是否关联方、是否非法人、销售费用承担方式、补贴或返利），
并且本期销售金额/期末应收账款余额能从 D4-2 收入明细与 D2-2 客户账龄自动取出、占同类交易比例自动算，
以便这张 IPO 检查表按源模板结构完整可用。

#### Acceptance Criteria

1. 13 列全部落地：序号 / 客户名称 / 经销商 / 本期销售数量 / 本期销售金额 / 占同类交易比例 / 期末应收账款余额 /
   是否关联方 / 个人·企业 / 销售费用承担方式 / 补贴或返利 / 终端销售金额 / 备注。
2. 「是否关联方」「个人/企业」「补贴或返利」为点选字段（`el-select` / 单选 tag），禁止自由文本。
3. 「本期销售金额」表间提取自 D4-2 收入明细（按客户名称匹配）；「期末应收账款余额」表间提取自 D2-2 客户账龄。
4. 「占同类交易比例」表内计算 = 该行本期销售金额 / 全部行本期销售金额合计（分母为 0 时留空，不显示 0%）。
5. 双模式回写与导入导出按 Requirement 2 / 4 生效。
6. 源模板编制说明（A5/A6/A7–A10 红字方法论）嵌入表格视图上方功能区，作审计过程上下文展示。
7. 源模板数据区 10 行（A12–A21 仅序号占位），表格视图初始渲染**不**预置 10 行空占位
   （禁止把占位序号推成占位披露行）；初始行数为 0，由用户按需新增。

#### Properties

- Property 20: D4-25 列规格列数 == 13，且 label 序列与源模板 row 11 逐列相等。
- Property 21: 占比列在分母为 0 时求值为空（不显示 `0%`、不抛除零）。
- Property 22: D4-25 表格视图初始渲染行数为 0（不预置空占位行）。

### Requirement 6: D4-26 境外销售收入检查表

### Requirement 9: 守卫与变异收口

**User Story:** 作为平台维护者，我要有一组可自动运行的守卫把「列结构同构 / 双模式一致 / 公式真源不漂移 /
导入导出闭环」四条不变量钉死，并且每个守卫都做过变异检验（改一字必变红），
以便四张表的结构不会随后续改动悄悄退化成两份互不相认的数据。

#### Acceptance Criteria

1. 列规格三向守卫：列规格 ↔ 后端 `_SHEET_HEADERS` ↔ 源模板 xlsx（openpyxl 直读）三方比对，任一漂移即红。
2. 渲染层守卫：两张两级表头的父组跨列数在**模板形态**层面可断言（外层门控 + 内层嵌套 + 遍历三要素），
   不允许只断言「声明里有 `group`」而 DOM 从不渲染。
3. 公式真源守卫：Requirement 3 的 Property 11–16 全部可自动断言；脚本读源码前 `stripComments()` + 反向自检
   （故意写错一处必失败）。
4. 导入导出闭环守卫：导出→导入往返无损（Property 18）。
5. 变异检验：本 spec 所有守卫至少 15 个锚点全部 RED（改一字/删一处引用即变红）；
   只看退出码不算数，必须区分 RED / GREEN（守卫缺陷）/ ANCHOR-MISS（脚本缺陷）/ WRONG-TEST（打错测试）。
6. 连库守卫（若有）一次 `asyncio.run` 取全部快照，专用 `NullPool` 引擎 + 同 loop `dispose()`，
   禁借共享连接池。
7. 失败态 fail-visible 回归：投影/导入失败必须产生 UI 可见失败态（Property 9），并配变异（把失败吞成成功必红）。
8. 全量前端测试与本 spec 相关后端测试全绿；改 `governance-checks.yml` 只允许 append 自己字节区间，
   不得触碰其他 job。

#### Properties

- Property 35: 列规格 ↔ `_SHEET_HEADERS` ↔ 源模板 xlsx 三向比对 4 张表 × 全部列均相等（0 偏差点）。
- Property 36: 变异检验 15 个锚点全部 RED（非 GREEN / ANCHOR-MISS / WRONG-TEST）。
- Property 37: 守卫脚本读源码前调用 `stripComments()`，且存在反向自检用例（故意写错必失败）。
- Property 38: 本 spec 新增/修改的守卫测试文件在干净 checkout 下可运行（已入库，非未跟踪）。


## Cross-Spec Governance Addendum

本 spec 与共同契约 `d4-dual-mode-formula-governance` 对齐；该共同契约由其他代理创建，实施前必须链接其 requirements/design，禁止猜测其 AC。以下约束优先于本文件中与之冲突的旧表述：

- 双向回写统一消费既有 `ContentMutationService`、`useWorkpaperSyncBridge`、durable callback、三方合并与批准的 contract-bundle representation；禁止新增任何 D4 自同步 bridge、仅 emit 事件、Excel 优先或最后写胜出。冲突须显式呈现并由用户裁决，保留审计记录。
- 公式唯一入口为 F-SHELL v2 mutation；effective definition 的 `expression`、`refs`、`params` 经统一解析、权限、CAS、审计链路同时投影到 OO 与 HTML，后端权威执行，前端仅预览。删除 `field_overrides` 公式库及 remark 冒充公式的方案；默认、custom、删除、恢复默认分开，scope 为 `wp/sheet/row/field`，空/除零/error 不写 0，未知函数显式 blocked。
- 公式预设升级不得覆盖 custom；删除与恢复默认必须区分；作用域稳定为 `wp/sheet/row/field`。百分比等单位必须声明。空值、除零、error 禁写 0；未知函数必须显式 blocked。
- A13 与双向回写分开。发现项须先由人工认定错报金额及方向再推送；定性风险不得以 amount=0 直接进入错报汇总；不得用 `abs(diff)` 丢失方向，也不得把抽凭金额直接等同错报金额。
- 事件必须提供 durable ack 且幂等，不能仅 `emit`。源模板身份必须来自 `backend/wp_templates/` 的实际 finder/index；两组声称不同模板须实施前核定，不能用组件字段替代源模板身份。
- 验收须逐张执行 HTML→OO→HTML、公式编辑重新打开、导出与不同项目隔离；只测 D4-35 不得代表全组。未满足上述前置条件的任务标记 `blocked`，不得冒充验收通过。
