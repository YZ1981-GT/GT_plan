# 需求文档：调整模块实务、联动与完整性闭环

## 1. 目标与范围

本 spec 承接 2026-11-01 对调整模块的二次评估。目标不是继续堆叠入口，而是把 AJE/RJE 从“可录入、可复核”收口为可解释、可恢复、可审计的单一调整账簿。

范围包括：

1. 现金流核查旧调整入口止损；
2. 分录组来源、删除恢复、并发和数据库约束；
3. 内部复核任务、职责分离和权限一致性；
4. 手工调整与底稿来源调整的统一生效门；
5. 批准、试算表、报表、公式、附注和交付件的可靠联动；
6. 既有 `adjustment-client-booking-status` 全部任务；
7. 未更正错报权威源、重要性、证据和 EQCR 快照；
8. 大厅深链、错误态、草稿、查询、导入导出和无障碍体验。

不把合并抵销分录并入单体 AJE/RJE；不自动推断现金流差异的借贷科目；不以 UI 隐藏代替后端门禁。

## 2. 术语与核心不变量

- **内部复核状态**：草稿、待复核、已批准、已驳回，只表示审计团队内部结论。
- **财务处理状态**：纳入工作试算表、客户已入账、不予更正并转错报、撤销。不得复用 `review_status` 表达。
- **系统计算状态**：待更新、更新成功、更新失败、已过期，是派生状态，不替代业务状态。
- **手工来源**：`origin=manual`，批准后进入 `trial_balance.aje_adjustment/rje_adjustment`。
- **底稿来源**：`origin=workpaper`，继续排除于 AJE/RJE 列；只有集中分录已批准后，来源底稿的显式发布门才可写 `wp_adjustment`。
- **未更正错报唯一来源**：`unadjusted_misstatements`。`adjustments.passed_reason` 只能作为兼容读或迁移来源，不再独立决定错报状态。
- **调整分录组**：同一个 `entry_group_id` 的全部行，是编号、来源、复核、删除、恢复和版本控制的最小业务单位。

## 3. R1：活路径止损与领域边界

1. 现金流核查“创建调整”必须打开标准 AJE/RJE 录入流程，由用户选择完整借贷科目；不得创造 `cf` 调整类型。
2. 旧 `/cf-verification/{year}/create-adjustment` 写端点停止写库，返回明确的 410 中文指引；前端不得再调用。
3. 可解释状态机必须与真实四态一致，不得出现 ORM/数据库不存在的 `posted` 状态，也不得声明生产路由不支持的转换。
4. 出具就绪和 EQCR 快照按 `entry_group_id` 聚合，不得把一笔多行分录计成多笔。
5. 旧 `wp-summary` 若无生产调用方则退役；保留时必须改用正式调整取数口径。

## 4. R2：分录组数据完整性与生命周期

1. 底稿来源分录的 `origin/source_ref` 在服务端不可变；只能回来源底稿修改后重新同步。
2. 删除、恢复和永久删除必须按完整分录组处理，同时处理 `adjustments` 和 `adjustment_entries`；恢复不得重建为手工来源或丢字段。
3. 软删除必须写 `deleted_at/updated_at/updated_by`；恢复清除删除字段并记录恢复人。
4. 每组增加内容版本 `content_revision`。编辑、同步、导入覆盖、提交复核、批准和撤回均校验 `expected_revision`；冲突返回 409 和当前版本。
5. 数据库必须兜底项目/年度编号唯一、组内行号唯一、非负金额、同行借贷互斥；组级借贷平衡继续由服务校验。
6. 所有生产写入必须经过统一的分录组 writer；禁止旁路只写 `Adjustment` 而不写 `AdjustmentEntry`。
7. 已批准科目不存在当前年度 TB 行时不得静默跳过。按标准科目建立零未审数 TB 行，无法确定主体时阻断并给出原因。
8. `company_code` 从项目或目标 TB 行解析，不接受无语义的 `default` 进入持久化。

## 5. R3：复核任务、权限和职责分离

1. 提交复核必须生成持久化复核任务，记录分录组、内容版本、指定复核人、提交人、备注和时间。
2. 页面“待我复核”只统计分配给当前用户且仍有效的任务；团队全部待办另行显示。
3. 没有合法复核人时不得进入无人处理的待复核状态。
4. 默认禁止编制人复核自己的分录。小团队例外只能由签字合伙人或 admin 提供不少于 10 字的覆盖理由，并写入审计日志。
5. 草稿不得直接进入已批准。所有批准必须基于有效、未过期的复核任务。
6. 普通分录经理复核即可；达到执行重要性或命中收入确认、管理层凌驾、关联方、重大估计等高风险标志时，需要合伙人终审。
7. 后端和前端统一使用 `adjustment:view/create/edit/submit/review/approve/delete/import/export/convert_to_misstatement`；不得以 `wp:edit` 或泛化项目 edit 替代已定义的细粒度能力。
8. 合并锁、项目归档和项目成员隔离适用于所有状态改变、导入、删除和恢复端点。

## 6. R4：生效门与可靠联动

1. 手工分录批准时，状态改变、受影响 TB 调整列重算、审定数重算、通知、审计记录和耐久事件入队在同一数据库事务中完成。TB 失败则不得批准。
2. 底稿来源分录批准不写 AJE/RJE 列。来源底稿发布审定数前，必须检查相关集中分录均已批准且版本未变化，否则返回 409 和清单。
3. `wp_adjustment` 仍只由统一的 TB 发布服务计算；不得通过调整金额增量累加或绕开 `publish_rows()`。
4. 报表、公式推送、附注、底稿过期和交付件更新通过 durable outbox 投递；失败可重试、重复投递幂等、死信可见。
5. typed outbox 必须完整保存 `account_codes/entry_group_id/context/extra`，重放后逐值一致。
6. 草稿创建、编辑和删除只更新待办与影响预览，不得标正式报表、附注和交付件过期。批准、撤回复核、客户入账及其撤销才触发正式下游。
7. 通知文案以真实计算结果为准。TB 未完成前不得声称“已计入试算表”或“已重算”。
8. 调整大厅展示复核状态与计算状态；失败时提供重试入口和最近错误。
9. 签发与交付门阻断未完成复核、调整快照漂移、下游 pending/failed 和未形成最终处理的调整事项。

## 7. R5：客户已入账

完整实施 `.kiro/specs/adjustment-client-booking-status/requirements.md` 与其所有 `[ ]`、`[ ]*` 任务，并遵守：

1. 客户入账使用平台 `VoucherKey`，不得只存凭证号或单条序时账行 ID。
2. 已入账仅在当前 active 账套确实包含关联凭证时生效；账套回滚后自动恢复计入。
3. 系统只提供精确候选，不自动标记。
4. 标记、撤销、账套激活和回滚都经过 R4 的原子重算与耐久事件链。

## 8. R6：错报、重要性和证据

1. 内部复核驳回不得自动等同于管理层不更正。
2. 复核通过后可选择“纳入工作试算表”“客户已入账”“不予更正并转错报”；三者互斥且有历史。
3. 转错报必须创建或关联 `UnadjustedMisstatement`，并记录管理层原因、沟通时间和支持文件；不得依赖 `passed_reason IS NOT NULL` 形成第二套统计。
4. 调整大厅显示相对明显微小、执行重要性和整体重要性的比例，并标出高风险性质。
5. 重大或高风险调整批准前必须有关联证据；证据复用 `EvidenceRef + AttachmentVersion`，不建调整模块私有附件真源。
6. 影响预览至少覆盖受影响 TB 科目、报表行、底稿、附注、现金流和税务提示；无法自动判断的影响明确标“待判断”。
7. EQCR 快照冻结分录组、明细、来源、复核链、处理结果、重要性、证据、凭证和计算状态。

## 9. R7：工作台体验

1. 深链协议统一：`focus` 定位分录组、`account` 筛科目、`impact` 打开影响、`group` 打开协作；兼容旧 `id`，发送方和接收方由测试对拍。
2. 列表、汇总、科目、模板类型、协作和复核任务加载失败不得伪装为空；显示最后成功时间、错误和重试。
3. 请求带上下文代际或取消控制，旧项目/年度响应不得覆盖新上下文。
4. 草稿 key 包含项目、年度、创建/编辑模式和分录组；取消可明确丢弃，离页前立即保存或确认。
5. 单笔批准也必须二次确认，并展示金额、重要性、影响和计算方式。
6. 批量部分失败后保留失败项选择并提供可复制/下载结果。
7. 列表改为服务端分页、筛选和排序，支持编号、摘要、科目、金额、编制人、复核人、来源、阶段、处理状态和日期；不得静默截断 10,000 笔。
8. 导入批次持久保存文件哈希、上传人、模式、逐组结果；错误清单可下载，外部编号存 `external_reference`。
9. 导出分“汇总、明细、复核历史、处理与证据”工作表，包含来源、复核人、批准时间、驳回原因、客户处理和计算状态。
10. 弹窗适配视口，筛选栏可换行；可点击 div/tag 改成语义按钮或支持键盘，并保留可见焦点。

## 10. R8：验证与治理

1. 真 PG、生产 app 真 HTTP 完成：创建→提交→另一用户批准→TB→报表→公式→附注→通知，全程不得 mock EventBus。
2. 手工与底稿来源各有一条端到端用例，证明不双计且底稿未批准不能发布。
3. 客户已入账、账套回滚、撤销标记逐值验证。
4. 故障注入覆盖批准提交前、TB 后、outbox 发布、Redis 不可用、handler 中途失败和重复投递。
5. 并发覆盖编辑/批准、双人批准、自定义编号、导入覆盖和底稿重同步。
6. Playwright 用审计助理、经理、合伙人、QC/EQCR 走完整流程，刷新后核对数据库。
7. 修复缺失的 `adjustment-hall-entry-review-closure` 归档链接，保持 spec 审计轨迹闭合。
8. 任何完成标记必须有代码、测试和真实行为证据；外部环境未满足则如实保留 `[ ]*`。
