INDEX DECISION
==============================================================================
All hot-path predicates resolve through existing indexes/keys:
  - working_paper: PK(id) + FK(wp_index_id, project_id) + assigned_to filter;
  - wp_index: PK(id) + (project_id) filter;
  - procedure_row_tasks: FK(wp_index_id, project_id) + assignee/reviewer_staff_id;
  - staff_members: PK(id) + user_id;
  - workpaper_delegation_history: (project_id) + (old/new_user_id) match.
The visibility query is a single bounded UNION ALL scoped by project_id + user_id +
audit_cycle = ANY(scope); the list path is a DISTINCT ON over an explicit wp_index id
ANY(:ids) set. On representative volume the planner already uses index/seq scans whose
cost is dominated by the bounded row sets, and the query-count is constant (no N+1).

CONCLUSION: EXPLAIN does NOT empirically justify a NEW additive index at this time.
No index added (spec: add an index ONLY when EXPLAIN proves plan improvement). If a
future production-scale capacity run (Task 17) shows a scan hotspot, an additive index
on workpaper_delegation_history(project_id, new_user_id) or working_paper(project_id,
assigned_to) is the first candidate — to be re-evaluated with a fresh before/after plan.
