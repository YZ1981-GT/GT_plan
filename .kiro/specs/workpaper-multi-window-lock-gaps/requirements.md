# 底稿多窗口编辑锁两处漏洞收口 — 需求

> spec: `workpaper-multi-window-lock-gaps`
> 创建日期: 2026-10-31（用户：「修复那两个漏洞即可」）
> 上游：`_archive/47-multi-window-ledger-workbench`（产品边界「同一底稿两窗口 ⇒ 第二窗只读」）

## 背景（2026-10-31 实测，【测试】公式同步乙有限公司_2025）

- 两个标签页分别开 D4、E1：都能编辑 ✅；第二个标签页开 D4：只读横幅「admin 正在编辑，当前为只读模式（所有保存已禁用）」✅。
- 漏洞 1：浏览器「复制标签页」把 sessionStorage 原样复制、且没有 opener ⇒ 新标签页沿用原标签页的窗口编号
  `gt-client-instance-id`，编辑锁把两个窗口当成一个，两边都能编辑同一张底稿；关掉任一个，锁也被一起释放。
  （模拟复制标签页实测：编辑锁表只有一行、两个窗口都不只读）
- 漏洞 2：只读窗口里底稿工具栏「导入」没禁用，`GtWpRenderer.onImportData` 直接转给子组件导入（D4 等直接 POST
  后端导入接口写库）；后端保存 / 导入接口都不校验编辑锁，只读完全靠前端拦。
- 浏览器实测时另发现：用内网地址 `http://192.168.20.60:3030` 访问不是安全上下文，浏览器不提供 `navigator.locks` 与
  `crypto.randomUUID`。原先生成窗口编号即抛 TypeError ⇒ 编辑锁请求在请求拦截器里就失败，两个窗口都能编辑、锁表无记录；
  本 spec 让所有写请求带编号后，这里会让所有保存都发不出去（提交前已修）。

## R1 每个标签页的窗口编号唯一

- R1.1 同一时刻两个活着的标签页不得共用窗口编号：复制标签页、`window.open` 复制了 sessionStorage 的新标签页，都要换新编号。
- R1.2 同一标签页刷新后保留原编号（编辑锁心跳不断、不把自己挤成只读）。
- R1.3 窗口编号定下来之前不发取锁 / 强制接管请求。
- R1.4 跨窗口认证广播判断「是不是自己发的」按当前编号，不按启动时记下的旧编号。
- R1.5 浏览器不提供 Web Locks（http + 内网地址访问）时同样满足 R1.1 / R1.2：打开着的标签页在 localStorage 登记编号、
  页面隐藏时注销；localStorage 不可用时退回 opener 判断。生成编号不依赖只在安全上下文才有的 `crypto.randomUUID`。

## R2 只读窗口不能写底稿内容

- R2.1 底稿工具栏只读时禁用「导入」「增行」；渲染器层只读时再拦一次「导入」（提示原因、不调子组件）。
- R2.2 Word 类底稿「导入数据」只读时禁用。
- R2.3 后端对底稿内容写入（`{wp_id}` 下导入类、`checklist-responses`、`save`、`save-version` 的写请求）校验编辑锁：
  有效锁的持有人（用户 + 窗口）以外的请求返回 423，说明谁在编辑、本次修改未保存。
- R2.4 持锁人本人的请求没带窗口编号、或锁上没记窗口：放行（无法区分窗口，保持原行为）。
- R2.5 没有有效锁（无锁 / 已释放 / 心跳超过 5 分钟）：放行。
- R2.6 前端写请求带窗口编号：axios 的非 GET 请求、Word 导入的原生请求。

## 第二轮（2026-10-31，用户：「这次没覆盖的 你需要继续修复下」）

第一轮只拦了保存 / 导入（132 条），留下三件事：其余写接口不看编辑锁；升级前打开、没刷新过的标签页复制出来仍同号；
内网 http 下页面崩溃后重开换号，崩溃前的锁让本页只读最长 5 分钟。现算（第二轮开工时）：

- 路径带 `{wp_id}` 的写路由 608 条：挂底稿门禁 585 条（第一轮覆盖 132），不挂 23 条。挂门未覆盖的 453 条里，
  导出 / 校验 / 计算 / AI 生成文本约 380 条不写底稿，其余有 OCR、证据、坏账行、程序表、公式、自定义单元格、结构、上传、
  Univer 保存、模板重建、Word 同步、裁决保存、试算表回写、AI 采纳、计算后写回（`apply_to_sheet`）等写底稿内容的。
- 只读窗口照样能切到在线编辑：通用平台物化房间时参与者一律按编辑身份加入；旧版按 sheet 取 OnlyOffice 配置时后端只看底稿状态，
  前端把模式改成只读不生效（OnlyOffice 容器开着浏览器令牌校验 `JWT_ENABLED=true`，以签名里的 `mode` 为准）。
- 只读窗口自己会发写请求：数据刷新事件触发的模板重建（非静默，会弹 423）、A17 三张底稿切在线编辑时生成 / 回写 Word、
  监盘 Word 双向同步、自定义底稿切回表格时重投影。

## R3 其余写接口按编辑锁拦截

- R3.1 路径带 `{wp_id}`、经底稿门禁的非 GET 请求默认都按 R2.3~R2.5 校验编辑锁。只有下列四类不校验，名单集中在一处：
  ①不写底稿：导出、校验、纯计算、AI 生成文本 / 对话 / 建议、只读比对；
  ②协作与流程：复核意见与批注（含回复 / 解决）、复核状态 / 提交复核 / 底稿状态、分派、提醒、质控检查、签字状态、A21 复核签字 / 解锁；
  ③锁管理：sheet 锁申请 / 释放 / 心跳；
  ④计算后可选写回：只算不写放行，写回那一步校验。
- R3.2 不经底稿门禁但写底稿内容的接口单独校验：版本回滚、程序行裁剪为不适用 / 恢复执行、解除附件关联；
  底稿 id 在表单里的编辑器内写入：H5 导入、A17-7 从 B3 导入独立性期间、附件关联到底稿。
- R3.3 在线编辑平台的入口（建待提交变更、物化、服务端直取物化、首版发布、采纳底版、版本回滚）校验编辑锁，被挡时提示
  「不能进入在线编辑」。会话内的操作（确认、强制保存、关闭、离开、冲突裁决、重试、恢复认领 / 仅下载）与文档服务回调不校验。
- R3.4 按 sheet 取 OnlyOffice 配置：编辑锁挡住本窗口时给只读模式。前端取这份配置的请求带窗口编号。
- R3.5 只读窗口不自动发写请求：上面列的模板重建、A17 Word 生成 / 回写、监盘 Word 同步、自定义底稿重投影在只读时跳过。
- R3.6 守卫：枚举应用的全部 `{wp_id}` 写路由 —— 豁免名单每条都命中路由；「不写底稿」类的处理函数与同模块被调函数没有写库证据
  （登记过理由的非内容写除外）；计算后写回的写回函数都调写回点校验；不经门禁的写路由都登记了「校验 / 不校验」与理由。

## R4 升级前打开的标签页

- R4.1 本版代码认领过的编号在 sessionStorage 另记一个标记。读到没有标记的编号（升级前的页面写的）⇒ 换一次新号。
- R4.2 其余情形（刷新保留、复制标签页换号、内网 http）与 R1 相同。

## R5 内网 http 下崩溃后重开

- R5.1 不提供 Web Locks 时，自己的编号已被登记 ⇒ 先用 BroadcastChannel 问有没有打开着的标签页在用：有回答 ⇒ 换新号；
  1.5 秒无回答 ⇒ 登记是崩溃前的本页留下的，认回原编号（崩溃前持有的编辑锁接着用）。
- R5.2 登记带文档标识，本文档自己的登记不算；被浏览器冻结的标签页答不了询问，冻结时登记里标出，命中冻结的登记直接换号。
- R5.3 每个打开着的标签页回答对自己当前编号的询问。
- R5.4 编号定下来之前，写请求、编辑锁请求、取 OnlyOffice 配置的请求等编号定下来再发。
- R5.5 浏览器不提供 BroadcastChannel ⇒ 不问，按第一轮口径换号。

## 非目标

- 第一轮的「不改 AI 生成、OCR、复核、批注、在线编辑同步等写接口的锁语义」由第二轮 R3 取代：AI 生成文本、复核、批注按 R3.1 ①②
  有意不拦（不改底稿内容；复核人要在编制人持锁时照常提意见），OCR、在线编辑入口等写底稿的接口改为拦。
- 批量 / 跨模块的数据流不按编辑锁拦：批量预填、批量 / 离线导入、试算表 / 调整 / 附注同步、自定义查询回写、抽样记录、ACNR。
  它们不是「第二个编辑窗口」的写入；要拦得先定整批失败还是跳过被锁的底稿。
- 同一人在另一个窗口持锁时在本窗口接管：不做（崩溃重开由 R5 解决；另一个窗口还开着就去那个窗口操作）。
- 不新增「在新窗口打开底稿」入口（用户未要求）。
