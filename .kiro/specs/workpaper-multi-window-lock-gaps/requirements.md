# 底稿多窗口编辑锁两处漏洞收口 — 需求

> spec: `workpaper-multi-window-lock-gaps`
> 创建日期: 2026-10-31（用户：「修复那两个漏洞即可」）
> 上游：`_archive/47-multi-window-ledger-workbench`（产品边界「同一底稿两窗口 ⇒ 第二窗只读」）

## 背景（2026-10-31 实测，【测试】公式同步乙有限公司_2025）

- 两个标签页分别开 D4、E1：都能编辑 ✅；第二个标签页开 D4：只读横幅「admin 正在编辑，当前为只读模式（所有保存已禁用）」✅。
- 漏洞 1：浏览器「复制标签页」把 sessionStorage 原样复制、且没有 opener ⇒ 新标签页沿用原标签页的窗口编号
  `gt-client-instance-id`，编辑锁把两个窗口当成一个，两边都能编辑同一张底稿；关掉任一个，锁也被一起释放。
  （模拟复制标签页实测：编辑锁表只有一行、两个窗口都不只读）
- 漏洞 2：只读窗口里底稿工具栏「导入」没禁用，`GtWpRenderer.onImportData` 直接转给子组件导入（D4 等直接 POST
  后端导入接口写库）；后端保存 / 导入接口都不校验编辑锁，只读完全靠前端拦。
- 浏览器实测时另发现：用内网地址 `http://192.168.20.60:3030` 访问不是安全上下文，浏览器不提供 `navigator.locks` 与
  `crypto.randomUUID`。原先生成窗口编号即抛 TypeError ⇒ 编辑锁请求在请求拦截器里就失败，两个窗口都能编辑、锁表无记录；
  本 spec 让所有写请求带编号后，这里会让所有保存都发不出去（提交前已修）。

## R1 每个标签页的窗口编号唯一

- R1.1 同一时刻两个活着的标签页不得共用窗口编号：复制标签页、`window.open` 复制了 sessionStorage 的新标签页，都要换新编号。
- R1.2 同一标签页刷新后保留原编号（编辑锁心跳不断、不把自己挤成只读）。
- R1.3 窗口编号定下来之前不发取锁 / 强制接管请求。
- R1.4 跨窗口认证广播判断「是不是自己发的」按当前编号，不按启动时记下的旧编号。
- R1.5 浏览器不提供 Web Locks（http + 内网地址访问）时同样满足 R1.1 / R1.2：打开着的标签页在 localStorage 登记编号、
  页面隐藏时注销；localStorage 不可用时退回 opener 判断。生成编号不依赖只在安全上下文才有的 `crypto.randomUUID`。

## R2 只读窗口不能写底稿内容

- R2.1 底稿工具栏只读时禁用「导入」「增行」；渲染器层只读时再拦一次「导入」（提示原因、不调子组件）。
- R2.2 Word 类底稿「导入数据」只读时禁用。
- R2.3 后端对底稿内容写入（`{wp_id}` 下导入类、`checklist-responses`、`save`、`save-version` 的写请求）校验编辑锁：
  有效锁的持有人（用户 + 窗口）以外的请求返回 423，说明谁在编辑、本次修改未保存。
- R2.4 持锁人本人的请求没带窗口编号、或锁上没记窗口：放行（无法区分窗口，保持原行为）。
- R2.5 没有有效锁（无锁 / 已释放 / 心跳超过 5 分钟）：放行。
- R2.6 前端写请求带窗口编号：axios 的非 GET 请求、Word 导入的原生请求。

## 非目标

- 不改其他写接口（AI 生成、OCR、复核、批注、在线编辑同步等）的锁语义。
- 不新增「在新窗口打开底稿」入口（用户未要求）。
